# 푸른통합 온톨로지 — 업체 강제전환 실행 준비서

## 현재 결정

**준비만 완료하고 실행은 보류한다.** 이 문서를 만든 시점에는 다음 작업을 하지 않는다.

- 운영 `data/companies` 실데이터 자동변경
- 업체 물리삭제 또는 삭제표식 일괄 생성
- 기존 업체 저장함수의 강제 전환
- 업체 Firebase 규칙 강화
- 운영 데이터 복원 시험

실행 재개는 대표가 **“업체 온톨로지 강제전환 실행”**이라고 명시한 뒤 시작한다.
그 전까지 ERP는 기존 관찰 모드를 유지한다.

## 준비된 장치

| 장치 | 위치 | 상태 |
|---|---|---|
| 공용 저장계약 | `js/pu-ontology-write.js` | 준비됨 |
| 업체 원자적 저장·삭제표식 | `js/pu-company-write.js` | 준비됨, 운영 저장에는 미연결 |
| 소스 사전점검 | `node scripts/ontology-company-preflight.js` | 읽기 전용 |
| 화면 현황 | ERP → 환경설정 → 온톨로지 | 읽기 전용 |
| 자동검사 | `tests/ontology-company-gateway.test.js` | 동시수정·신규중복·삭제표식 검증 |

현재 소스 사전점검 기준으로 전체 업체 목록 저장 5곳과 물리삭제 호출 2곳이 남아 있다.
숫자는 앞으로 코드가 바뀌면 달라질 수 있으므로 실행 직전에 다시 계산한다.

## 실행 전 승인표

아래 항목이 모두 충족되지 않으면 실데이터 이관이나 서버 강제를 시작하지 않는다.

- [ ] 업무가 적은 시간대를 정했다.
- [ ] 접속 중인 담당자에게 업체관리 저장 중단 시간을 알렸다.
- [ ] ERP의 `erpBackupFull()` 또는 환경설정 백업으로 전체 JSON 파일을 받았다.
- [ ] 백업 파일을 현재 PC 이외의 위치에도 한 벌 보관했다.
- [ ] 백업 파일에서 `companies` 건수와 대표 표본 10건을 확인했다.
- [ ] ERP 온톨로지 화면의 업체 진단에서 중복 ID가 0건이다.
- [ ] 사람 확인 필요 항목이 0건이거나 처리목록과 담당자가 정해졌다.
- [ ] `node scripts/ontology-company-preflight.js`의 차단 항목이 0건이다.
- [ ] 전체 자동검사가 종료코드 0으로 통과했다.
- [ ] 복원 담당자와 중단 판단 담당자를 정했다.

## 추후 실행 순서

### 1. 기준 고정

1. 최신 `main`을 별도 작업 브랜치에서 연다.
2. `node scripts/ontology-company-preflight.js`를 실행해 결과를 작업기록에 남긴다.
3. 업체 건수, 활성·중단·폐업별 건수와 표본 ID를 기록한다.
4. 이 시점부터 완료 선언까지 담당자들의 업체 수정·삭제를 잠시 중단한다.

중단 기준: 소스 사전점검을 실행할 수 없거나 업체 데이터가 배열/ID 맵 예상형식이 아니면 멈춘다.

### 2. 기존 저장경로 정리

1. 전체 목록 저장 5곳을 업체 한 건 단위 저장 또는 명시적 일괄 트랜잭션으로 바꾼다.
2. 물리삭제 호출 2곳을 삭제표식 저장으로 바꾼다.
3. 업체 목록 조회에서 `_deleted: true`는 일반 목록에서 숨기되 관계 조회와 복구에서는 유지한다.
4. 자동이관·엑셀·계약관리 복귀·업체 합치기 경로도 같은 관문을 사용하게 한다.

중단 기준: `whole_list_writes_remain` 또는 `physical_delete_calls_remain`이 하나라도 남으면 강제하지 않는다.

### 3. 백업과 복원 가능성 확인

1. 관리자 계정으로 ERP 전체 JSON 백업을 내려받는다.
2. 백업 파일명에 실행일시와 실행 전이라는 뜻을 남긴다.
3. 원본 파일은 수정하지 않고 복사본으로만 구조와 건수를 검사한다.
4. 별도 시험 환경에서 업체 1건을 복원해 ID·업체명·계약 연결이 살아 있는지 확인한다.

중단 기준: 백업 파일을 열 수 없거나 복원 표본이 원본과 다르면 이관하지 않는다.

### 4. 실데이터 읽기 전용 진단

다음 값을 세되 자료를 고치지 않는다.

- 전체 업체 수
- ID 없음·중복 ID 수
- `Organization` 계약 적용/미적용 수
- 계약·사건·재무가 참조하는데 업체가 없는 고아 관계 수
- 이미 삭제표식이 있는 업체 수

중단 기준: ID 없음, 중복 ID 또는 해석할 수 없는 레코드가 있으면 사람 확인 후 다시 진단한다.

### 5. 소량 시험 이관

1. 실제 업체 중 관계가 적고 확인하기 쉬운 3건만 선정한다.
2. 업체명·주소·사업자번호 등 업무정보는 그대로 두고 계약 필드만 붙인다.
3. 각 건을 서버 트랜잭션으로 저장한다.
4. ERP·계약·사건·재무 화면에서 같은 업체가 정상 표시되는지 확인한다.

붙이는 최소 필드는 `entityType`, `schemaVersion`, `contractVersion`, `createdAt`,
`updatedAt`, `createdBy`, `updatedBy`, `revision`이다.

중단 기준: 한 칸이라도 업무정보가 달라지거나 연결 건수가 바뀌면 즉시 멈추고 백업과 비교한다.

### 6. 동시접속 시험

1. PC A와 PC B에서 같은 업체를 연다.
2. A에서 연락처를 저장한다.
3. 새로고침하지 않은 B에서 주소를 저장한다.
4. B 저장이 충돌 안내와 함께 거부되는지 확인한다.
5. B가 최신값을 다시 읽은 뒤 주소를 저장하면 A의 연락처가 유지되는지 확인한다.
6. 삭제 후 복구 시험에서 계약·사건·재무 관계가 끊어지지 않는지 확인한다.

합격 기준: 마지막 저장자가 조용히 앞사람 값을 덮어쓰는 경우가 0건이어야 한다.

### 7. 전체 이관

1. 시험 3건을 제외한 업체를 작은 묶음으로 나눈다.
2. 각 묶음을 트랜잭션으로 이관하고 성공·충돌·보류 건수를 기록한다.
3. 실패한 건은 자동 재시도하지 않고 최신 서버값을 다시 읽어 별도 검토한다.
4. 이관 전후 전체 건수와 ID 집합을 비교한다.

합격 기준: 업체 ID 집합이 같고 업무필드 변경 0건, 중복 ID 0건, 보류 0건이어야 한다.

### 8. 업체 경로만 강제

1. 업체 저장 호출을 전용 관문으로 전환한다.
2. 업체 경로 Firebase 규칙을 생성하되 곧바로 배포하지 않는다.
3. 살아 있는 규칙과 생성 규칙을 비교해 기존 규칙 삭제가 0개인지 확인한다.
4. 규칙 dry-run과 전체 자동검사를 통과시킨다.
5. 그 뒤에만 `node scripts/rules-deploy.js --deploy`로 게시한다.
6. 신규·수정·충돌·삭제표식·복구를 운영 화면에서 다시 확인한다.

완료 기준: 업체 경로의 우회 저장이 거부되고 정상 업무 저장은 모두 성공해야 한다.

## 즉시 중단하고 복구하는 조건

다음 중 하나라도 발생하면 추가 저장과 규칙 배포를 중단한다.

- 업체 전체 건수 또는 ID 집합이 줄어듦
- 사업자번호·업체명·주소·담당자 등 업무필드가 예상하지 않게 변함
- 계약·사건·입출금·세금계산서의 업체 연결이 끊어짐
- 정상 신규등록·수정이 반복해서 거부됨
- 충돌된 저장이 성공으로 표시됨
- 일부 묶음만 이관된 채 원인을 확인할 수 없음

복구 순서는 `강제 규칙 되돌리기 → 업체 저장을 관찰 모드로 되돌리기 → 실행 중지 공지
→ 실행 전 백업과 현재값 비교 → 손상 범위 확정 → 승인 후 필요한 업체만 복원`이다.
백업 전체를 운영 서버에 바로 덮어쓰지 않는다. 실행 중 생긴 정상 변경까지 사라질 수 있기 때문이다.

## 실행 완료 보고에 반드시 남길 값

- 실행 시작·종료 시각
- 실행자와 검증자
- 이관 전후 업체 수와 ID 집합 차이
- 성공·충돌·보류·삭제표식 건수
- 업무필드 변경 건수
- 관계 고아 건수
- 자동검사와 Firebase dry-run 결과
- 배포한 규칙 판과 Git 커밋
- 복구 여부와 남은 작업
