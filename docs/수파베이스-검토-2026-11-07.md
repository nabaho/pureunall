# 수파베이스(Supabase) 검토 — 파이어베이스에서 옮길까

- 검토 기준일: 2026-11-07 · 요청: 대표
- 상태: **검토 의견(초안)** — 대표 결정 전. 요금 숫자는 견적·계약 전에 공식 요금표로 다시 확인한다.
- 계기: 급여 아웃소싱 프로그램을 만들면 **약 100개 사업장 · 500명**을 관리해야 하고,
  근로자마다 **급여명세서 · 연차관리 · 휴가관리**를 모두 해야 한다(대표, 2026-11-07).
- 앞선 결정: 「백엔드는 Firebase 기본, 3단계 전 Supabase 재검토(급여만 분리 옵션, 마스터 단방향 동기화)」
  — [아웃소싱_세션인수인계_v1.6.md](아웃소싱_세션인수인계_v1.6.md) 2절. 이 문서가 그 «재검토»다.

## 결론

1. **지금 있는 프로그램(이알피·업무관리·기업정보함·사진첩 등)은 통째로 옮기지 않는다.**
   돈은 거의 안 줄고, 고칠 곳이 너무 많고, 옮기는 동안 자료를 잃을 위험이 크다.
2. **새로 짓는 급여 아웃소싱 프로그램은 수파베이스(PostgreSQL)로 짓는 쪽을 권한다.**
   100곳·500명의 명세서·연차·휴가는 «여러 표를 엮어 묻고 합치는 일»이 대부분이라
   실시간DB보다 표 구조(SQL)가 훨씬 잘 맞는다.
3. 단, **6절의 조건**(로그인은 지금 포털 하나 · 업체 원장은 파이어베이스가 주인 · 온톨로지 계약 먼저 ·
   개인정보 칸막이 · 지울 것이 있으면 멈추는 올리개)을 지키고, **가짜 자료로 시범부터** 한다.

## 3. 지금 프로그램을 통째로 옮기지 않는 까닭

- **돈**: 위 2절 — 아끼는 돈이 없다.
- **일의 크기**: 1절의 1,700여 자리 · 함수 131개 · 규칙 1,945줄 · 검사 372개를 모두 다시 짓는다.
  수파베이스 규칙은 SQL 의 행 단위 보안(RLS)이라 지금 규칙을 옮겨 적을 수 없다.
- **자료 손실 위험**: 옮기는 몇 주~몇 달 동안 두 벌을 함께 돌려야 한다.
  «어디서든 데이터가 지워지면 안 된다»(대표, 2026-10-07)를 지키기 가장 어려운 기간이다.
- **이미 다진 안전장치를 다시 지어야 한다**: 규칙 올리기 전 «사라질 규칙» 비교(`rules-deploy.js`) ·
  주민번호·계좌 칸막이(`worker_secret`) · 재직자 확인(`staff-gate`) · 온톨로지 쓰기 관문(`pu-ontology-write.js`).

## 4. 급여 아웃소싱은 왜 표 구조(SQL)가 맞나

### 자료의 크기 — 작다

- 명세서: 500명 × 12개월 = **연 6,000장**. 과거 10년을 넣어도 «상한» 6만 장(실제 근로자 수가 해마다 달라 더 적다).
- 연차·휴가 기록: 사람당 연 수십 줄 → 연 1만~2만 줄 어림.
- PostgreSQL 에는 작은 양이다 — Pro 기본 디스크 8GB 안에 넉넉할 것으로 어림 [시범에서 실측].

크기가 아니라 **«어떻게 묻나»** 가 갈림길이다.

### 하는 일 견주기

| 하는 일 | 실시간DB(지금) | PostgreSQL(수파베이스) |
|---|---|---|
| 이번 달 연차 사용촉진 통보 대상(100곳 전체) | 근로자를 통째 받아 화면에서 거르거나, 따로 색인을 만들어 늘 맞춰야 한다 | 조건 한 줄 조회 |
| 사업장·월별 급여대장 합계, 4대보험 집계 | 그 달 명세서를 모두 받아 화면에서 더한다 — 계약서 양식 통째 받기(10월 요금 사고)와 같은 꼴 | 서버가 더해서 합계만 보낸다(`SUM`·`GROUP BY`) |
| 퇴직금(최근 3개월 평균임금) | 여러 달 명세서를 모두 받아 계산 | 기간 조회 하나 |
| 같은 근로자·같은 달 명세서 두 장 막기 | 코드로 막아야 한다(규칙으로는 어렵다) | 고유 제약(`UNIQUE`) — DB 가 거절 |
| 사업장 담당자는 자기 사업장만 | 경로를 사업장별로 짜면 되지만, 색인 사본을 만들 때마다 규칙도 따로 | 행 단위 보안 정책 하나(`company_id` 기준) |
| 금액 | 숫자가 실수(소수)라 원 단위 정수로 늘 조심 | 정수·`numeric` 열로 DB 가 지킨다 |
| 고친 기록(누가·언제·무엇을) | 저장하는 곳마다 손으로 | 트리거 하나로 모든 고침을 남긴다 |
| 엑셀·신고 서식으로 내보내기 | 받아서 화면에서 맞춘다 | 조회 결과를 그대로 |

### 파이어베이스 안의 다른 길 — Firestore

같은 파이어베이스의 Firestore 는 실시간DB 보다 조회가 낫고, 로그인·규칙 배포를 한 집에 둘 수 있다.
그러나 표끼리 엮기(조인)가 없고 집계가 약하며, **문서를 읽는 수만큼 요금**이 나간다 —
급여대장·집계 화면처럼 «많이 읽고 합치는» 일에는 PostgreSQL 이 더 맞는다고 본다.

## 5. 수파베이스로 지을 때의 걱정과 답

| 걱정 | 답 |
|---|---|
| 직원 로그인이 두 벌이 된다 | 수파베이스는 **파이어베이스 로그인 증표를 그대로 믿을 수 있다**(공식 «서드파티 인증 — Firebase Auth»). 카카오·지문 로그인도 결국 파이어베이스 증표라 함께 된다 |
| 업체 목록이 두 곳에 생긴다 | 업체 원장은 파이어베이스가 주인. 수파베이스는 `companyId` 그대로 «받아 쓰기만»(한쪽 방향 복사) |
| 주민번호·계좌 | 서울 지역(ap-northeast-2)에 둔다. 별도 표 · 별도 권한(`worker_secret` 원칙 그대로) |
| 새 기술을 익혀야 한다 | 표 바꾸기(migration)·RLS 를 저장소에 파일로 두고 검사로 지킨다 — 지금 규칙 만들개와 같은 방식 |
| 수파베이스 회사가 문을 닫으면 | 속은 표준 PostgreSQL 이라 통째 내보내 다른 곳에서 그대로 연다 |

## 6. 지킬 조건 (짓기 전에 정한다)

1. **로그인은 지금 포털 하나.** 수파베이스 서드파티 인증으로 파이어베이스 증표를 믿게 한다.
   - 수파베이스는 증표의 `role` 표시로 권한을 가른다. 파이어베이스 증표에는 기본으로 없다 →
     서버가 붙여야 한다. 이미 재직자에게 `staff` 표시를 붙이는 함수(`functions/staff-claim.js`)가
     있으니 **같은 자리에서 재직자에게만** 붙이는 안이 자연스럽다.
   - ⚠ «로그인했으니 직원»으로 짓지 말 것. 파이어베이스는 가입이 열려 있고(익명 로그인 때문에 못 끈다)
     익명 사용자도 증표를 받는다. 수파베이스 정책도 **재직자 표시**를 봐야 한다.
2. **업체 원장은 파이어베이스가 주인.** 수파베이스로는 `companyId` 로만 복사한다. 이름으로 맞추지 않는다.
3. **온톨로지 계약 먼저.** `PuOntology.PROGRAMS` 등록 · 민감 자료라 `READ_ADAPTERS` 는 `strategy:'in_app'`.
   지금 쓰기 관문(`pu-ontology-write.js`)은 파이어베이스 저장만 보므로, «수파베이스 표에 쓰는 프로그램»의
   계약 꼴(`writeContracts`)을 먼저 정한다 — 이것 없이 짓기 시작하면 배포검사(`ontology-contract`)와 부딪힌다.
4. **개인정보.** 서울 지역 · 주민번호·계좌는 별도 표와 담당자 권한 ·
   수파베이스(미국 회사)를 처리 수탁자로 쓰게 되므로 처리위탁 고지·계약을 검토한다.
   국외이전 해당 여부는 [확인 필요 — 담당 노무사·법률 검토]. (지금 파이어베이스도 같은 물음이 있다.)
5. **지울 것이 있으면 멈추는 올리개.** 표 바꾸기·정책(RLS)도 `rules-deploy.js` 처럼
   «사라지는 표·열·정책이 있으면 올리지 않고 멈춘다». `--force` 같은 우회로는 만들지 않는다.
6. **백업.** Pro 의 매일 백업(7일)에 더해, 우리 쪽에서 정기적으로 통째 내보내 따로 둔다.
7. **요금 상한(spend cap)을 켜 둔다.** 넘을 일이 생기면 알림을 보고 사람이 판단한다.

## 7. 다음 단계 (제안)

1. 대표 결정: 급여 아웃소싱의 저장소 = 수파베이스로 갈지.
2. 정할 것: **사업주·근로자가 직접 로그인해** 명세서·연차를 보나?(고객앱 설계) — 로그인 설계가 달라진다.
   500명이 로그인해도 MAU 기본 10만 명 안이다.
3. 시범: 서울 지역 Pro 프로젝트 하나, **가짜 자료**로 사업장 2곳 · 근로자 20명 · 명세서 · 연차 촉진 대상 조회까지.
   확인할 것 — 파이어베이스 로그인 증표 연결 · 재직자만 열리는지 · 사업장 칸막이 · 화면 속도 · 실제 디스크 크기.
4. 시범이 통과하면 본 설계. 지금 프로그램은 그대로 둔다.
