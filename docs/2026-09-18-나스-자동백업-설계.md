# 나스 자동 백업 — 「브라우저를 빼고 나스가 스스로 받아 온다」 설계

2026-09-18 · 대표 지시 「자동화 설계해라」
앞선 기록: `status/2026-09-18-nas-reverse-proxy-dead-end.md`

> **한 줄 결론 — 방향을 뒤집는다.**
> 브라우저가 나스에 «올리는» 대신, **나스가 서버에서 «받아 온다».**
> 그러면 오늘 저녁 내내 막힌 CORS·인증서 벽이 **통째로 사라진다.**

---

## 0. 왜 오늘 것이 안 됐나 (다시 밟지 않게)

```
[브라우저] ──올림──▶ [나스]        ← 오늘 판. 막혔다.
   https://nabaho.github.io      192.168.0.21
```

브라우저는 «남의 집»에 자료를 보낼 때 그 집이 써 준 쪽지(CORS 응답 머리글)를 요구한다.
대표님 나스(DSM)에는 **그 쪽지를 붙일 자리가 아예 없다** — 제어판 → 로그인 포털의
세 탭을 다 확인했다. 역방향 프록시의 「사용자 지정 머리글」은 **뒤쪽(DSM)으로 가는 요청
머리글**이라 브라우저는 영영 못 본다(WebSocket 미리설정이 `Upgrade`·`Connection` 을
넣는 것이 그 증거다).

**이 길은 닫혀 있다. 되풀이하지 말 것.**

---

## 1. 새 그림

```
[관리자 브라우저]  앱을 열 때  →  RTDB  serverBackups/{YYYY-MM-DD}     ← 이미 매일 돈다. 안 건드린다.
                                        (주민번호는 PuRrnSeal 로 «잠긴» 채)
                                          │
[나스 작업 스케줄러] 매주 새벽 3시        │  wget (HTTPS, 바깥으로 나가는 쪽)
                    ───────────────────▶ Cloud Function  nasBackupExport
                                          │  관리자 SDK 로 읽어 JSON 을 준다
                                          ▼
                    /업무자료/pureun_erp/pureun_erp_auto_2026-09-18.json
                    + 오래된 날짜 파일 정리(새 30개만)
                    + 결과 한 줄을 RTDB nas_backup_status 에 → 이알피 「지금 상태」가 읽는다
```

**CORS 가 «없다».** CORS 는 브라우저가 지키는 울타리다. 나스의 `wget` 은 브라우저가 아니다.
인증서도 구글 것이라 그냥 된다. 자체서명을 믿게 할 일이 없다.

---

## 2. 브라우저가 올리던 것과 견주면

| | 브라우저 → 나스 (오늘) | **나스 → 서버 (새 설계)** |
|---|---|---|
| CORS | 막힌다 — 이 DSM 판으로는 길이 없다 | **없다** |
| 인증서 | 자체서명을 사람이 믿게 해야 | 구글 인증서 — 그냥 된다 |
| 사무실 밖 | 안 된다 | 나스만 인터넷 되면 된다 |
| 언제 도나 | **브라우저를 켜 둬야** 돈다 | 새벽에 **스스로** |
| 실패하면 | 조용했다(고쳤지만 여전히 화면을 봐야 안다) | 나스 로그 + 서버에 한 줄 |
| 주민번호 | localStorage 원문 = **평문** | **이미 잠긴 것**(PuRrnSeal) |
| 비밀 열쇠 | `SECRET_KEYS` 로 걸러냄 | 서버가 같은 규칙으로 걸러냄 |

⚠★ **주민번호 대목은 보안이 «좋아지는» 것이다.**
지금 「💾 백업 파일 다운로드」가 만드는 파일은 `collectLocal()` 이 localStorage 를 그대로
담은 것이라 **주민번호가 평문**이다. `PuRrnSeal` 은 `erpSealSnap` 경로(= `serverBackups`)
에만 걸려 있다. 새 설계는 그 잠긴 것을 받아 오므로, 나스에 놓이는 파일에 평문 주민번호가
없다.

---

## 3. 무엇을 받아 오나 — 그리고 «빠진 칸» 하나

받아 올 것: `serverBackups/{가장 최근 날짜}`.
이미 `serverBackupDaily()` 가 관리자 기기에서 매일 쓴다. 우리는 **읽기만** 한다.

⚠★ **빠진 칸이 있다 — 이번에 드러났다.**

| 목록 | 칸 수 | 무엇 |
|---|---|---|
| `FB_ALL_SYNC_KEYS` (서버와 맞추는 칸 전부) | 약 50 | 업무·재무·인사·설정 전부 |
| `SERVER_BACKUP_KEYS` (서버 백업에 담는 칸) | **21** | 업무·재무 일부 |

`user_accounts` · `user_dir` · `employment_contracts` · `retirement_settlements` ·
`finance_expense` · `finance_invoice` · `pay_items` · `accounts` · `external_staff` 등이
**서버 백업에 안 들어간다.** 자료가 사라진 것은 아니다(`data/*` 에 살아 있다) —
그러나 **「백업」이라고 부르는 것에 그 칸들이 없다.**

이것은 이번 설계와 별개의 흠이므로 **0단계에서 먼저 확인하고**, 늘릴지 말지는 대표님께
여쭌 뒤 정한다(늘리면 잠금·용량·규칙이 함께 움직인다).

---

## 4. 나스가 서버를 부르는 길 — 왜 Cloud Function 인가

두 갈래를 놓고 골랐다.

| | ㉠ 나스가 RTDB REST 를 직접 | ㉡ **Cloud Function 하나를 거쳐** |
|---|---|---|
| 나스가 가진 것 | 파이어베이스 계정 아이디·비밀번호 | **열쇠 글자 하나** |
| 권한 | 보안규칙을 새로 짜야(칸마다) | 함수가 «줄 것만» 준다 |
| 규칙이 흘러갈 위험 | 규칙이 두 벌이 되어 어긋난다 | 규칙을 안 건드린다 |
| 끊을 때 | 계정을 지운다 | **열쇠 한 줄만 바꾼다** |
| 걸러내기 | 나스가 받은 «뒤에» 걸러야 | **서버가 보내기 전에** 거른다 |

㉡ 을 고른다. 특히 **걸러내기가 서버 쪽**이라는 점이 크다 —
비밀(`SECRET_KEYS`)이 나스로 «갔다가 지워지는» 것과 «애초에 안 가는» 것은 다르다.

⚠ 이 함수는 **브라우저용이 아니다.** CORS 머리글을 **일부러 안 붙인다.**
열쇠가 새더라도 브라우저에서는 읽을 수 없다(울타리를 한 겹 더 둔다).

---

## 5. 열쇠와 흔적

- 열쇠는 `NAS_BACKUP_KEY` — **파이어베이스 비밀값**에 넣는다(저장소에 안 남는다).
  `firebase functions:secrets:set NAS_BACKUP_KEY --project pureun-erp`
  (대표님이 `RESEND_API_KEY` 를 넣으신 것과 같은 방법이다)
- 견주기는 **길이가 같아도 시간이 안 새는 방법**(`timingSafeEqual`)으로 한다.
- 부를 때마다 `nas_backup_log/{시각}` 에 한 줄 남긴다 — 언제·몇 바이트·어느 날짜 것.
  **누가 언제 받아 갔는지 모르면 열쇠가 샜을 때 알 길이 없다.**
- 열쇠가 서버에 없으면 **500 으로 멈춘다.** 열쇠 없이 여는 길을 만들지 않는다.

---

## 6. 나스 쪽 — 도커가 없어도 된다

DSM **제어판 → 작업 스케줄러 → 생성 → 예약된 작업 → 사용자 정의 스크립트**.
Container Manager(도커)가 **필요 없다.** `wget` 하나면 된다(DSM 에 늘 있다).

스크립트가 하는 일 넷:
1. 받는다 (`wget` + 열쇠 머리글)
2. **받은 것이 진짜 JSON 인지 본다** — 아니면 파일을 안 덮는다
   (⚠ 빈 파일·오류 쪽지로 지난 백업을 덮는 것이 가장 나쁜 고장이다)
3. 날짜 파일로 저장하고 `pureun_erp_latest.json` 도 갱신
4. 새 30개만 남기고 오랜 날짜 파일 정리 · 로그 한 줄

스크립트 전문은 `docs/나스-백업-스크립트.sh` 에 둔다 — 대표님은 **붙여넣기만** 하시면 된다.

---

## 7. 이알피 화면은 어떻게 아나

나스가 끝나면 그 결과를 서버에 한 줄 남긴다(`nas_backup_status/last`).
이알피 「NAS 자동 백업」 화면의 **「지금 상태」 칸이 그것을 읽어** 이렇게 말한다 —

> ✅ **나스가 스스로 받아 둡니다** — 마지막 2026-09-18 03:00 · 1.8MB

지금 그 칸은 «이 브라우저가 나스에 닿는가»만 말한다. 그건 이제 **중요하지 않다.**
중요한 것은 «나스에 파일이 쌓이고 있는가»다. 화면이 말하는 것을 그쪽으로 옮긴다.

---

## 8. 단계 — 작게, 숫자로 보고 늘린다

| 단계 | 무엇 | 되는지 보는 숫자 |
|---|---|---|
| **0** | 나스가 인터넷에 나가는지 · 작업 스케줄러 스크립트가 도는지 · `wget` 이 있는지. 그리고 **§3 의 빠진 칸**을 대표님께 보고 | 시험 스크립트가 `echo` 한 줄을 남기는가 |
| **1** | `functions/nas-backup-export.js` 올리고 열쇠 넣기 | `wget` 으로 한 번 받아 JSON 크기(MB) |
| **2** | 작업 스케줄러에 스크립트 등록(주 1회 새벽 3시) | 다음 주 월요일 아침에 파일이 있는가 |
| **3** | 이알피 「지금 상태」가 `nas_backup_status` 를 읽게 | 화면이 «나스가 받아 둔 시각»을 말하는가 |
| **4** | 브라우저 쪽 7일 자동 업로드를 **끈다**(CORS 로 어차피 안 된다). 수동 내려받기는 **남긴다** | 실패 기록이 더는 안 쌓이는가 |

⚠ 3단계 전까지 화면에 아무것도 안 붙인다. 2단계까지는 «되는지»만 본다.
⚠ 4단계에서 **수동 백업 단추는 지우지 않는다** — 늘 되는 길은 늘 있어야 한다.

---

## 9. 안 하는 것 (지금은)

- 나스를 인터넷에 여는 것 — 하지 않는다. 나스는 **나가기만** 한다.
- `data/*` 전부를 통째로 내려받는 것 — 거기에는 주민번호가 **평문**으로 있다.
  담으려면 서버가 먼저 잠가야 하고, 그 잠금(`PuRrnSeal`)은 지금 브라우저 쪽에만 있다.
  §3 의 «빠진 칸»을 `SERVER_BACKUP_KEYS` 에 늘리는 쪽이 먼저다 — 그 길에는 잠금이 이미 있다.
- 나스가 파이어베이스에 **쓰는** 것 — 상태 한 줄(`nas_backup_status`)만 쓴다. 그 이상은 안 준다.

---

## 10. 되돌리기

전부 «더하는» 것이라 되돌리기가 쉽다.

- 나스 작업 스케줄러에서 그 작업 하나를 끄면 멈춘다.
- 함수는 열쇠를 지우면 그 자리에서 500 으로 멈춘다(`firebase functions:secrets:destroy NAS_BACKUP_KEY`).
- 이알피 화면은 `nas_backup_status` 가 없으면 예전처럼 말한다.
- 이미 받아 둔 파일은 그대로 남는다.
