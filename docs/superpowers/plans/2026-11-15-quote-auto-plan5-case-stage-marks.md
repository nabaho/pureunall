# 견적·계약 자동화 계획 5 — 계약의 «심급·단계»(노동위원회·산재) 읽어 표시·확인 (계획 문서만)

작성 2026-11-15 · 대표 요청 2026-11-15 · 기준 `origin/main` `566cb0a1` · **코드는 한 줄도 바꾸지 않았다**(새 파일 둘).
상태: **대표 확인 대기** — 아래 §6 의 네 가지를 정하기 전에는 구현을 시작하지 않는다.

## 1. 대표 요청 (2026-11-15)

> 푸른이알피에 견적서 등이 들어오면 자동으로 접수·협의·확정까지 된다. 사업장이 계약서를 작성해 푸른노무법인으로 보내면 내용을 파악해서 계약확정 이관까지 해 달라.
> 노동위원회는 지방노동위원회·중앙노동위원회 등 절차를 여러 번 거친다 — 그 부분을 계약서 내용에서 확인해 표시하고 체크해 달라.
> 산업재해도 최초신청·심사청구·재심사청구 단계가 있고 단계마다 진행 상황에 대한 계약이 세분화돼야 한다 — 계약 내용에서 확인 가능하게 표시해 달라.

## 2. 대표가 정한 것

- **자동은 «계약확정»까지만, 이관은 사람이 한 번 누른다** (2026-11-15 대표 답 「네, 확정까지만」). 지금 설계·코드가 이미 그렇다 — 바꾸지 않는다.
- 그 밖(§1 의 단계 표시·세분화)은 아직 대표가 정하지 않았다. §4 는 «권고안»이다.

## 4. 만들 것 (권고안)

### 4-1. 읽기 — 순수 함수 하나
`detectCaseStages(text, hint)` → `[{ code, hits:[…], strength:'strong'|'weak', where }]`
- 입력 글: 계약서에서 읽은 `docName`·`scope`(업무 범위)·`memo` + 메일 제목·첨부 이름. **계약서 본문 전체가 아니라 이미 읽혀 요청에 실려 오는 칸만** 쓴다(주민번호·금액이 AI 요청에 실리지 않게 해 둔 기존 울타리 그대로).
- 단계 코드는 `BIZ_CASE_STAGE_SEED` 의 것만: `lrc-local`(지방노동위원회·지노위·초심) · `lrc-central`(중앙노동위원회·중노위·재심신청) · `court-admin`(행정소송·취소소송) · `wc-apply`(요양급여 신청·최초요양) · `wc-review`(심사청구) · `wc-rereview`(재심사청구).
- **한 계약서에 단계가 여럿 나올 수 있다**(「지노위 및 중노위 재심 포함」) → 목록으로 돌려준다.
- **사건류 계약일 때만** 돌린다(`kinds` 에 `case` 또는 메일 분석의 `inferredKind==='case'`). 컨설팅·자문 글에 «노동위원회» 낱말이 나와도 표시하지 않는다.
- «참고·사례» 문맥(「…판정례 참고」)은 `weak` — 표시는 하되 «확인 필요»를 더 크게.
- 근거 글 조각(앞뒤 약 24자)을 함께 돌려준다 — 금액·주민번호는 기존 가림 함수로 지운 뒤.

### 4-2. 계약에 적는 자리 — `stageMarks`
`stageMarks: [{ code, state:'auto'|'checked'|'dismissed', evidence, srcDoc, at, bySid }]`
- 기계가 읽은 것은 `auto`. 사람이 ☑ 하면 `checked`(누가·언제), ✕ 하면 `dismissed`(다시 안 띄움).
- **`stageCode`(기존 «현재 단계»)는 자동 읽음만으로 안 바꾼다.** 사람이 `checked` 한 단계가 생기면 그때 «가장 이른 미완료 단계»를 제안만 하고, 이미 사람이 적은 `stageCode` 는 덮지 않는다(기존 «사람이 적은 칸은 기계가 안 덮는다» 규칙). 이관 때 사건 단계로 승계되기 때문이다.
- 계약 상태(`consult`·`review`·`signed`)·금액·계약번호는 **건드리지 않는다.**

### 4-3. 화면
- **계약 카드(칸반)**: 사건계약 카드에 «⚖ 지노위 · 중노위», «산재 요양 · 심사» 칩. `auto` 는 점선 + «확인 필요», `checked` 는 실선. 한 칸은 한 줄(넘치면 … + title).
- **계약 창**: «⚖ 심급·단계» 상자 — 읽은 단계 목록 + 근거 글 조각 + ☑ / ✕ + 「단계 추가」, 단계별 법정 기한 안내는 기존 `dueNote`(「확인 후 사용」 표시 그대로).
- 폰: 칩은 카드 안 한 줄, 상자는 한 겹. 단추는 그림 + `title`.

### 4-4. 단계마다 계약 «세분화»
**권고: 한 계약 안에 단계 체크표 + 다음 단계는 «후속 계약 후보 줄»로 제안만.**
- `checked` 된 마지막 단계의 다음 단계(`caseNextStageCode`)를 계약 창에 «후속 계약 후보»로 보여 주고, 사람이 누르면 **기존 «후속사건 계약 등록» 길**(`erpCaseToFollowupContract` 와 같은 씨앗: `parentContractId`·`stageCode`)로 새 계약 창을 연다.
- 자동으로 새 계약을 만들지 않는다 — «이관은 사람» 과 같은 결.
- 대안(단계마다 자동으로 계약을 쪼개 만들기)은 권하지 않는다: 수임 계약서 한 장에 단계가 다 들어 있으면 계약이 여러 건이 되어 금액이 겹쳐 잡히고 0원 계약이 쌓인다.

### 4-5. 하지 않는 것
자동 이관 · 자동 후속 계약 생성 · 상태·금액 변경 · 읽음만으로 `stageCode` 덮기 · 서버 계약 일괄 소급.

## 6. 대표가 정해 주실 네 가지 (권고 포함)
1. **읽은 단계는 «확인 필요»로 시작하고, 사람이 ☑ 해야 굳는다** (권고: 예 — 잘못 읽은 단계가 이관 때 사건에 그대로 승계되지 않게).
2. **단계마다 계약을 자동으로 쪼갤지** (권고: 아니오 — 한 계약 안 체크표 + 후속 계약 «후보»만 제안).
3. **지노위·중노위와 산재를 함께 만들지** (권고: 함께 — 같은 읽기 함수, 화면은 사건계약에만).
4. **이미 있는 계약(서버 약 170건)에는 «다시 읽기» 단추로만** (권고: 자동 소급 없음).

- **«자동»이 지금 어떻게 도는지.** 메일 → 계약서 길은 **누군가 푸른사진첩을 열 때 한 번, 최대 3건**씩 브라우저에서 돈다(`pu-photos.html` `mailContractSweep`, 서버·시간표가 아님). 이알피 쪽 처리도 계약관리 화면을 열 때(`runContractRequests`) 돈다. 견적서 서버 감시 훅(`functions/mail-quote-watch.js`)은 **기본 꺼짐**이고 지금 켜져 있는지는 이 방이 서버를 못 봐 모른다(`pucards/config/quoteWatch/on`). 대표가 말한 «들어오면 저절로»를 사람이 화면을 열지 않아도 되게 하려면 별도 일이다 — 이 계획 밖.
- **계획 4(#2983, 2026-11-09)와의 겹침.** 계획 4 의 B(계약서 읽어 채우기)·C(서명본 자동 확정)는 문서가 쓰이기 전·후에 main 에 들어온 «계약서 자동 정리 길»과 일부 겹친다. 계획 4 를 맡은 방이 현재 코드와 맞춰 다시 읽어야 한다(이 계획은 그 문서를 고치지 않았다).
