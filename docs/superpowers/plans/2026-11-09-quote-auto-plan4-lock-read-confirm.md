# 견적·계약 자동화 — 계획 4: 금액 잠금 → 계약서 읽어 채우기 → 서명본 자동 확정 (계획서)

> **이 문서는 계획만이다. 코드를 바꾸지 않았고, 대표가 순서와 아래 「정해 주실 것」을 확인하기 전에는 구현을 시작하지 않는다.**
> 설계: `docs/superpowers/specs/2026-11-07-quote-contract-auto-design.md` · 앞 계획: 계획 1(작업 기록·지난 견적, 병합) · 계획 2(서류 만들기 — 계획 문서만) · 계획 3(견적 감지 → 이알피 대기열, PR #2970 병합 + 후속 PR #2974 `[보류]`)

## 0. 출처와 확인 상태

- 대표의 새 지시 두 건이다. **사진첩 방이 대표 말씀을 전한 것**(2026-11-09)이고, 이 방(계약서등관리)이 대표께 직접 확인한 것이 아니다 **[확인 필요]**. 전언 원문은 아래 §1.
- 이 계획이 기대는 것: ① PR #2974(계획 3 검토 반영)가 합쳐지고 ② 규칙 게시 ③ 함수 배포 ④ 「자동 감지 켜기」가 끝난 뒤 — 이 넷은 모두 대표 승인이 필요하고 **아직 하지 않았다**.
- 코드 사실 확인은 이 문서를 쓴 2026-11-09 의 main 기준이다(부록 A). 못 확인한 것은 **[확인 필요]**로 표시했다.

## 1. 한눈에 (쉬운 말로)

**대표가 원하신 것**
1. 계약서를 이알피로 보내면, 이알피가 내용을 읽어 **사업장·금액·상황을 정리하고 «저장» 까지 알아서** 한다.
   - 대표가 고르신 것: 저장까지 자동 · 읽은 금액은 **계약 금액 칸에 채우되 «권한자»만 보이게**(대표·총괄관리자·재무·그 건 확정 담당자).
2. **서명본이 오면 «계약확정»도 자동**으로 한다.

**왜 순서가 중요한가**
- 지금은 계약 금액 칸이 **직원 누구나** 읽을 수 있다(계약 목록이 한 덩어리라서). 그 칸에 AI 가 읽은 금액을 자동으로 채우면 **모든 직원이 금액을 보게 된다**. 그래서 «금액을 권한자만 보게» 하는 일(설계 단계 5)이 **먼저**여야 한다.
- 자동 확정은 실수의 값이 가장 크다(엉뚱한 회사·다른 금액·서명 안 된 파일로 확정). 그래서 **조건을 모두 맞을 때만** 자동으로 하고, 하나라도 빠지면 «후보»로만 띄워 사람이 한 번 누른다. 틀렸을 때 **되돌리는 길**도 같이 만든다.

**제안 순서 (대표 확인 필요)**

| 순서 | 무엇 | 끝나면 |
|---|---|---|
| 0 | 계획 3 마무리 — PR #2974 병합 → 규칙 게시 → 함수 배포 → «자동 감지 켜기» | 견적·계약 메일이 상담접수·계약협의로 올라온다(금액 없이) |
| **A** | **금액 잠금** — 계약의 금액을 잠긴 자리로 옮기고 이알피 화면을 거기서 읽게 | 권한 없는 직원에게는 «금액 비공개» |
| **B** | **계약서 읽어 채우기** — 보낸 계약서 메일부터, 읽은 값을 검증해 저장까지 | 카드에 사업장·기간·금액이 채워지고 «AI 가 읽음» 표시·되돌리기 |
| **C** | **서명본 자동 확정** — 전자서명 → 서명본 올리기 → 메일 회신 순으로 | 조건이 다 맞는 서명본은 계약확정, 아니면 후보 띠 |

각 칸(A·B·C)은 **따로 PR**로 올리고, 규칙 게시·옛 자료 이사·자동 기능 켜기는 **그때마다 대표 승인**을 받는다.

## 2. 바뀌는 선 / 안 바뀌는 선

| | 지금 (계획 3까지) | 이 계획 이후 |
|---|---|---|
| 금액 | 요청·카드에 **안 담는다**(대기열·메모에서도 글자를 가린다) | 읽어서 **채운다 — 잠긴 자리에서만, 권한자만 본다** |
| 계약협의 → 확정 | 사람이 누른다 — 설계 §7 은 «전자서명·서명본 올리기는 자동, **메일 회신 서명본만** 담당자가 한 번»이었고, 계획 3 의 사진첩 방 전언은 «담당자가 한 번 눌러 확정(자동 아님)»으로 읽었다. 어느 쪽이든 **지금 코드에는 자동 확정이 없다** | **세 신호 모두 «조건 다 맞을 때만» 자동** — 대표 새 지시로 바뀜 |
| 계약 저장 | 사람이 저장 단추 | 자동(이알피 기존 저장 문을 그대로 지난다) |

**안 바뀌는 선**(코드·시험이 지키고 있다)
- 사업장은 **`companyId` 로만** 잇는다 — 이름·주소 모양으로 카드를 찾지 않는다. 못 이으면 걸림.
- 주담당은 **사람이 정한다**(이름으로 사번을 채우지 않는다).
- 같은 메일은 **한 번만** 반영한다(`srcMails`·서버 «본 메일» 표식).
- 비교견적(`compare` 표시) 건은 **사람이 «선정»**해야 계약협의로 간다 — 자동 확정도 하지 않는다.
- **외부 발송·이관·청구·출력은 자동으로 시작하지 않는다**(설계 §2 «안 할 것»). 자동 확정은 «확정»만 한다.
- 규칙 게시·함수 배포·자동 기능 켜기·옛 자료 이사는 **대표 승인**.

| ② | 읽은 값 검증(합계 = 공급가 + 부가세, 자릿수) · 못 읽으면 0 이 아니라 **빈칸 + «확인 필요»** · «AI 가 읽음» 표시와 **출처** | **B3** — 검증 규칙표(§6-B). 한 번이라도 어긋나면 금액은 비우고 후보만 잠긴 자리에 둔다 |

## 4. 대표가 정해 주실 것 (한 줄씩)

1. **금액 잠금을 먼저 해도 되는지.** 일반 직원이 지금 이알피에서 보던 계약 금액이 **«금액 비공개»**로 바뀐다(설계 §2 목표 6은 이미 대표 결정). 합계·통계 화면도 권한 없는 사람에게는 숨는다. 해당 직원이 일에 금액이 꼭 필요한 경우가 있는지 한 번 더 확인해 주세요.
2. **자동 확정 조건의 세기.** 설계 §7 은 «메일로 회신된 서명본은 담당자가 한 번 눌러 확정»(전자서명·올리기는 자동)이었고 계획 3 에서는 «전부 사람이 한 번»으로 읽혔다. 이번 지시로 전부 «자동»이 되었는데(어느 쪽이 대표 뜻인지 **[확인 필요]**) — 전자서명(서명 증거가 확실)은 바로 자동, **메일 회신 서명본은 조건을 모두 맞을 때만 자동(아니면 후보 띠)**을 권한다. 이대로 괜찮은지.
3. **읽는 곳.** 권한자 브라우저(권장) vs 서버(§5-D2). 서버는 개발·비용이 더 든다.
4. **자동 확정·자동 채움 뒤 알림.** 담당자에게 알려야 하는지, 어디로(이알피 알림 / 카톡정리 …).
5. **기존 계약 금액 이사 시점.** 서버 계약 약 170건의 금액을 잠긴 자리로 옮긴다(백업 → 옮김 → 합계 대조 → 계약에서 비움). 승인 단계를 셋으로 나눈다(§6-A4).
6. **사람이 적은 값과 AI 가 읽은 값이 다를 때.** 권고: **사람 값을 덮어쓰지 않고** «차이»로만 표시.
7. **수정계약·추가금(확정 뒤 금액 변경).** 이번 범위 **밖**으로 둔다(자동으로 안 건드린다).

## 5. 설계 판단 (이 방이 정한 것 — 반대 의견 있으면 알려 주세요)

### D1. 금액 잠금 방식 — 계약에서 금액을 떼어 «잠긴 자리»로 (원안 §4 단계 5)
- `data/contracts` 는 한 덩어리 배열이라 규칙으로 **금액 칸만** 가릴 수 없다 → 금액(`amounts`·`contractFee`·`successFee`·`contractFeeVatIncluded` 등)을 계약에서 떼어 **계약 id 별 잠긴 자리** `contract_amt/{contractId}` 로 둔다.
- 계획 1의 견적 금액 자리 `pu_quote_amt` 와 같은 모양·같은 사람(대표·총괄관리자 `isAdmin` · 재무 `fin` · 그 건의 **확정** 담당자). 부관리자·일반 직원은 못 본다.
- 새 자리의 «담당자 접근자»는 계약의 주담당·보조 담당(`managerMain`·`managerSubs`)과 맞아야 한다 — **담당자가 바뀌면 접근자도 바뀌어야** 한다(동기화 방법은 §6-A1에서 정함. 사번(sid) ↔ 로그인 uid 대응은 계획 1이 이미 쓰는 방식을 따른다) **[확인 필요]**.
- 저장 층은 이미 같은 모양을 쓴다: `dbUpsert`/`dbPatch` 가 근로자 주민번호·계좌를 떼어 «담당자 칸»으로 보내는 `PuWorkerSecret.split` 패턴이 있다(부록 A-4). 금액 분리도 그 패턴을 따라 «떼기 → 잠긴 자리로 보내기»를 저장 문 안에서 한다.
- **하지 않는 것**: 계약 칸에 금액을 두고 화면에서만 가리기(설계 §2 «실패로 볼 것»), 규칙 없는 «숨은 칸».

### D2. 누가 읽나 — 권한자 브라우저가 읽는다(권장), 서버는 다음 단계
- **권장(1단계)**: 이알피를 연 **금액 볼 권한이 있는 사람(대표·총괄관리자·재무·확정 담당자)의 브라우저**가 처리한다. 기존 길을 그대로 쓴다 — 첨부 받기(`readMailAttachment`) · 글자 뽑기(`extractText`) · AI(서버 대리인 `functions/doc-read.js`, 열쇠는 브라우저에 없음). 금액이 «볼 권한이 있는 사람의 화면 안»에서만 다뤄지므로 **비공개 선과 어긋나지 않는다**. 계획 3 의 «열려 있는 동안 1분마다 이어서 처리»가 이미 있어 근무 시간에는 사실상 연속이다.
- **한계**: 권한자가 이알피를 열어 둔 동안에만 돈다(완전 무인 아님). 대표가 «아무도 안 열어도»를 원하시면 2단계(서버 처리)가 필요하다.
- **2단계(선택, 별도 승인)**: 서버(메일 동기화 뒤 훅)가 읽는다. 첨부 글자 뽑기(PDF·HWP)를 서버로 옮겨야 하고(지금은 브라우저 쪽 도구) **[확인 필요]**, AI 호출이 서버 비용으로 바로 잡힌다. 지금은 하지 않는다.
- 대기열에는 지금처럼 **금액·본문을 싣지 않는다**. 요청은 «어느 메일의 어느 첨부»를 가리키는 칸만(`srcKey`·첨부 번호).

### D3. 자동으로 채우는 칸 — «빈 칸만», 사람 값은 덮어쓰지 않는다
| 칸 | 어디서 | 규칙 |
|---|---|---|
| 사업장 | 요청의 `companyId`(계획 3 길) | 문서의 회사 이름이 업체관리와 크게 다르면 **걸림**(다른 회사 문서일 수 있다). 이름으로 `companyId` 를 만들지 않는다 |
| 계약 기간(시작·종료) | 문서 | 비어 있을 때만 채움 |
| 종류(`kinds`) | 문서 + 요청 | 사람이 정한 종류가 있으면 그대로 |
| 금액(`amounts`·`successFee`…) | 문서 | **잠긴 자리**에만 저장, 검증 통과 때만 |
| 사업자번호·대표자 | **문서에서 읽지 않는다** | 업체관리(업체 마스터)가 원본 — 마스터를 덮어쓰지 않는다 |
| 상황(상담접수·계약협의·계약확정) | 신호 | B 는 «계약협의»까지, **확정은 C 만** |
- 사람이 이미 적은 값과 읽은 값이 다르면 **카드에 «읽은 값과 다름»으로만** 표시한다(덮어쓰지 않음).

### D4. 자동 반영의 기록과 되돌리기
- 자동으로 카드를 만들거나 고칠 때마다 카드에 `auto = { kind, at, srcKey, by:'auto', before:{바뀐 칸의 이전 값}, after:{…}, model, readAt }` 를 남긴다(금액 값은 이 기록에 넣지 않는다 — 금액은 잠긴 자리의 `src` 에만).
- 카드에 **«🤖 자동 반영 · 되돌리기»** 단추(권한자·그 건 담당자). 되돌리면 `before` 로 복원하고 작업 기록에 `auto_undo`.
- 작업 기록(`pu_worklog`, 총괄관리자만 읽기)에 `auto_fill`·`auto_confirm`·`auto_undo` 를 남긴다 — **금액 글자는 넣지 않는다**(건수·카드 id 만).
- 자동 확정 취소: `signed` → `review`, 사유 필수, 작업 기록. 이관·청구가 이미 시작된 건은 **취소 단추를 막고** 사람이 본다 **[확인 필요 — 이관 시작 표시가 계약에 있는지]**.

### D5. 켜고 끄는 스위치 — 단계마다 따로, 기본 «꺼짐»

**검증 규칙표(②)** — 모두 통과해야 **금액을 채운다**. 하나라도 어긋나면 금액 칸은 비우고 «확인 필요» + 후보만 잠긴 자리에 둔다(카드는 만들거나 고칠 수 있다).
1. 금액 후보가 문서 안에서 **서로 맞는다**: 합계 = 공급가액 + 부가세(±1원). 합계만 있으면 «부가세 포함 여부 불명»으로 표시.
2. **자릿수**: 문서의 원 단위 숫자에 «만·억» 표기가 함께 있으면 둘이 일치해야 한다(1만 배 오독 전례 방지 — 사진첩 방 전언 **[확인 필요: 저장소에서 근거를 못 찾음]**).
3. **견적과 대조**: 같은 `companyId` 의 견적 기록(`pu_quote_amt`)이 있고 금액 차이가 크면(예: 5배 이상) 채우지 않고 걸림.
4. **회사 대조**: 문서의 회사 이름이 요청의 업체와 크게 다르면 걸림(다른 회사 문서일 수 있다).
5. **못 읽음 = 0 이 아니다**: 빈칸 + «확인 필요». 0 이나 기본값을 넣지 않는다.
6. 모든 자동 값에 «AI 가 읽음» 표시 + 출처(메일 key·파일 id·sha256·모델·읽은 시각).

**개인정보·비용(④)**
- **원본 파일을 AI 에 보내지 않는다** — 브라우저에서 글자를 뽑아(`TEXT_MAX` 상한) 그 글자만 보낸다.
- 글자를 보내기 **전에** 주민등록번호·계좌번호 모양을 가린다(정규식), AI 응답에서도 같은 모양이 나오면 버린다(이중). 계약서에는 대표자 주민번호·계좌가 드물지 않다.
- **AI 비용**: 판독은 유료 등급이고 «이번 달 요금 한도 ₩50,000 · 경고 ₩45,000»(`functions/doc-read.js`)가 있다. 한도에 닿으면 «나중에»로 남기고 사람이 채울 수 있게 한다. 같은 파일(sha256)은 다시 읽지 않는다. 건수 규모: 2026-08-05~11-07 보낸메일함에 우리 계약서 약 39건·견적서 약 24건(설계 §3·§4) — 한 달 십여 건. 코드의 계산 기준값은 «건당 4원»(`AI_BUDGET_DEFAULT.wonPerRead`, 추정치)이라 이 규모의 비용은 작다 — 실제 건당 비용은 **기록으로 확인**한다 **[확인 필요]**.

## 8. «실패로 본다» — 이게 일어나면 멈추고 되돌린다

- 금액이 **DB 에서** 권한 없는 직원에게 읽힌다(화면에서만 가려진 것은 실패).
- 한 계약이 자동 등록·확정으로 **겹쳐 생긴다**(같은 사업장·같은 업무).
- **다른 금액·다른 회사**로 계약확정이 저절로 된다.
- **보낸 원본을 그대로 돌려받은 파일**로 확정된다.
- **1만 배 틀린 금액**이 검증 없이 저장된다.
- 자동 확정이 **이관·발송·청구·출력**을 시작한다.
- 비교견적 건이 선정 없이 계약협의·확정으로 간다.
- AI 비용이 월 한도를 넘는다.
- 작업 기록·요청·토스트·로그에 **금액 글자**가 남는다.

## 9. 시험 방침 (이 저장소 관례)

- 규칙은 글자가 아니라 **판정기**로(`tests/quote-watch-switch.test.js` 방식 — 이름 칸·`$변수` 칸을 둘 다 맞는 것으로 센 «엄격» 해석 포함).
- 순수 판정(`erpFillPlan`·`erpSignedPlan`·`PuContractRead`)은 입력·출력만으로, 저장하는 쪽은 실제 함수를 `cutFn` 으로 잘라 가짜 파이어베이스로(저장 확인 `landed`·거절·시간 초과 포함 — 계획 3 방식).
- «하나씩 빼 보기»: 조건표의 칸을 하나씩 빼면 `confirm` 이 `candidate` 로 바뀌는지.
- 금액이 새지 않는지: 요청·작업 기록·카드 메모·토스트·`console` 에 금액 글자가 없는지 글자 검사.
- 정규식·긴 입력은 **시간 상한**(`ReDoS`) 시험.
- 화면은 가짜 파이어베이스 + 지어낸 자료로 직접 띄워 PC·폰 모두(`tools/phone-audit`). 진짜 파이어베이스·메일은 첫 건을 사람이 보며.
- 코드를 만든 뒤에는 사용자 지침대로 Antigravity(기능 검증)·Codex(보안 검토) 자동 검토를 돌린다 — 보조일 뿐이고 사람의 최종 검토가 필요하다.

## 10. 이 계획 밖

- 수정계약·추가금·갱신 자동 처리(확정 뒤 금액 변경).
- 서버가 읽는 2단계(D2) — 대표가 «아무도 안 열어도»를 원하실 때 별도 계획.
- 사진 계약서(카톡 사진·팩스·스캔) 판독 — 사진첩 길이 따로 맡는다.
- 비교견적 선정/탈락 단추 전체(계획 3 Task 5)·앱에서 보낸 서류 신호(Task 4)·서명본 후보 띠 일부(Task 6) — 계획 3 에 남은 일. C 의 «후보 띠»는 Task 6 과 겹치므로 **같이 만든다**.
