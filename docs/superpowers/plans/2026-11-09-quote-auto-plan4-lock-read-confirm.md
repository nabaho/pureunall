## 0. 출처와 확인 상태

- 대표의 새 지시 두 건이다. **사진첩 방이 대표 말씀을 전한 것**(2026-11-09)이고, 이 방(계약서등관리)이 대표께 직접 확인한 것이 아니다 **[확인 필요]**. 전언 원문은 아래 §1.
- 이 계획이 기대는 것: ① PR #2974(계획 3 검토 반영)가 합쳐지고 ② 규칙 게시 ③ 함수 배포 ④ 「자동 감지 켜기」가 끝난 뒤 — 이 넷은 모두 대표 승인이 필요하고 **아직 하지 않았다**. 2026-11-15 현재 PR #2974 는 열려 있고 **main 과 충돌하는 상태**라 병합 전에 main 을 합쳐야 한다.
- 코드 사실 확인은 2026-11-15 의 main 기준이다(부록 A). 그 사이 main 이 크게 움직였지만(약 250건) 계약 레코드의 금액 칸 모양은 바뀌지 않았다. 못 확인한 것은 **[확인 필요]**로 표시했다.

## 1. 한눈에 (쉬운 말로)

**대표가 원하신 것**
1. 계약서를 이알피로 보내면, 이알피가 내용을 읽어 **사업장·금액·상황을 정리하고 «저장» 까지 알아서** 한다.
   - 대표가 고르신 것: 저장까지 자동 · 읽은 금액은 **계약 금액 칸에 채우되 «권한자»만 보이게**(대표·총괄관리자·재무·그 건 확정 담당자).
2. **서명본이 오면 «계약확정»도 자동**으로 한다.

**왜 순서가 중요한가**
- 지금은 계약 금액 칸이 **직원 누구나** 읽을 수 있다(계약 목록이 한 덩어리라서 — 규칙 `contracts: .read LOGIN`). 그 칸에 AI 가 읽은 금액을 자동으로 채우면 **모든 직원이 금액을 보게 된다**. 그래서 «금액을 권한자만 보게» 하는 일(설계 단계 5)이 **먼저**여야 한다.
- 이 일은 **처음이 아니다.** 2026-10-15 에 «근로자 주민번호·계좌를 그 건의 담당자와 대표만»을 같은 이유(계약이 한 덩어리)로 이미 해냈고, 규칙(`worker_secret`)·분리 모듈·이사 스크립트·배포 순서가 그대로 남아 있다. 금액 잠금 A 는 **그 방식을 따라 하는 일**이라 처음부터 설계할 때보다 안전하다(§5 D1).
- 자동 확정은 실수의 값이 가장 크다(엉뚱한 회사·다른 금액·서명 안 된 파일로 확정). 그래서 **조건을 모두 맞을 때만** 자동으로 하고, 하나라도 빠지면 «후보»로만 띄워 사람이 한 번 누른다. 틀렸을 때 **되돌리는 길**도 같이 만든다.

**제안 순서 (대표 확인 필요)**

| 순서 | 무엇 | 끝나면 |
|---|---|---|
| 0 | 계획 3 마무리 — PR #2974 병합 → 규칙 게시 → 함수 배포 → «자동 감지 켜기» | 견적·계약 메일이 상담접수·계약협의로 올라온다(금액 없이) |
| **A** | **금액 잠금** — 계약의 금액을 잠긴 자리로 옮기고 이알피 화면을 거기서 읽게 | 권한 없는 직원에게는 «🔒 금액 비공개» |
| **B** | **계약서 읽어 채우기** — 보낸 계약서 메일부터, 읽은 값을 검증해 저장까지 | 카드에 사업장·기간·금액이 채워지고 «AI 가 읽음» 표시·되돌리기 |
| **C** | **서명본 자동 확정** — 전자서명 → 서명본 올리기 → 메일 회신 순으로 | 조건이 다 맞는 서명본은 계약확정, 아니면 후보 띠 |

각 칸(A·B·C)은 **따로 PR**로 올리고, 규칙 게시·옛 자료 이사·자동 기능 켜기는 **그때마다 대표 승인**을 받는다.

**대표 답을 기다리는 동안 «안전하게» 할 수 있는 일** (원하시면 — 화면·실제 자료를 건드리지 않고, 자동 기능은 꺼진 채)
- A0 **금액 읽는 곳 전수 조사** — 읽기만(코드 안 바꿈), 표 하나가 나온다.
- B1·C1 **판단 부분만 따로**(`PuContractRead` 읽은 값 검증 · `erpSignedPlan` 서명본 판정) — 아무 데도 연결하지 않는 순수 모듈 + 시험. 나중에 연결만 하면 된다.

## 2. 바뀌는 선 / 안 바뀌는 선

| | 지금 (계획 3까지) | 이 계획 이후 |
|---|---|---|
| 금액 | 요청·카드에 **안 담는다**(대기열·메모에서도 글자를 가린다) | 읽어서 **채운다 — 잠긴 자리에서만, 권한자만 본다** |
| 계약협의 → 확정 | 사람이 누른다 — 설계 §7 은 «전자서명·서명본 올리기는 자동, **메일 회신 서명본만** 담당자가 한 번»이었고, 계획 3 의 사진첩 방 전언은 «담당자가 한 번 눌러 확정(자동 아님)»으로 읽었다. 어느 쪽이든 **지금 코드에는 자동 확정이 없다** | **세 신호 모두 «조건 다 맞을 때만» 자동** — 대표 새 지시로 바뀜 |
| 계약 저장 | 사람이 저장 단추 | 자동(이알피 기존 저장 문을 그대로 지난다) |

**안 바뀌는 선**(코드·시험이 지키고 있다)
- 사업장은 **`companyId` 로만** 잇는다 — 이름·주소 모양으로 카드를 찾지 않는다. 못 이으면 걸림.
- 주담당은 **사람이 정한다**(이름으로 사번을 채우지 않는다).
- 같은 메일은 **한 번만** 반영한다(`srcMails`·서버 «본 메일» 표식).
- 비교견적(`compare` 표시) 건은 **사람이 «선정»**해야 계약협의로 간다 — 자동 확정도 하지 않는다.
- **외부 발송·이관·청구·출력은 자동으로 시작하지 않는다**(설계 §2 «안 할 것»). 자동 확정은 «확정»만 한다.
- 규칙 게시·함수 배포·자동 기능 켜기·옛 자료 이사는 **대표 승인**.

## 4. 대표가 정해 주실 것 (한 줄씩)

1. **금액 잠금을 먼저 해도 되는지.** 일반 직원이 지금 이알피에서 보던 계약 금액이 **«🔒 담당자·재무·대표만»**으로 바뀐다(주민번호 때와 같은 모양, 설계 §2 목표 6은 이미 대표 결정). 목록 합계·월별 통계도 권한 없는 사람에게는 못 보여 준다. 일에 금액이 꼭 필요한 직원이 있는지 한 번 더 확인해 주세요.
2. **자동 확정 조건의 세기.** 설계 §7 은 «메일로 회신된 서명본은 담당자가 한 번 눌러 확정»(전자서명·올리기는 자동)이었고 계획 3 에서는 «전부 사람이 한 번»으로 읽혔다. 이번 지시로 전부 «자동»이 되었는데(어느 쪽이 대표 뜻인지 **[확인 필요]**) — 전자서명(서명 증거가 확실)은 바로 자동, **메일 회신 서명본은 조건을 모두 맞을 때만 자동(아니면 후보 띠)**을 권한다. 이대로 괜찮은지.
3. **읽는 곳.** 금액 볼 권한이 있는 사람의 이알피 화면(권장) vs 서버(§5-D2). 서버는 개발·비용이 더 든다.
4. **자동 확정·자동 채움 뒤 알림.** 담당자에게 알려야 하는지, 어디로(이알피 알림 / 카톡정리 …).
5. **기존 계약 금액 이사 시점.** 서버 계약 약 170건의 금액을 잠긴 자리로 옮긴다. 주민번호 때처럼 «복사 → 되읽어 대조 → 공개 덩어리에서 비우기 → 쓰기 막는 규칙»을 **각각 승인**으로 나눈다(§6-A6).
6. **사람이 적은 값과 AI 가 읽은 값이 다를 때.** 권고: **사람 값을 덮어쓰지 않고** «차이»로만 표시.
7. **수정계약·추가금(확정 뒤 금액 변경).** 이번 범위 **밖**으로 둔다(자동으로 안 건드린다).
8. **«이관»하면 금액이 어디로 가나.** 계약확정 뒤 사람이 «이관»하면(계약 → 사건·컨설팅·기금·기타) 금액이 그쪽 레코드로 옮겨 쓰이는데, 그쪽 덩어리도 직원 누구나 읽는다. 설계 §7 대로 **이번에는 계약 금액만 잠그고 이관 쪽은 지금처럼** 두는 것을 권한다(자동으로 이관하지 않으므로 사람이 누를 때만 금액이 그쪽으로 간다). 이관 쪽 금액까지 잠그려면 범위가 훨씬 커진다 — 어느 쪽인지.

## 5. 설계 판단 (이 방이 정한 것 — 반대 의견 있으면 알려 주세요)

### D1. 금액 잠금 방식 — 주민번호 선례(`worker_secret`)와 같은 방식으로 «잠긴 자리»에 (원안 §4 단계 5)

**선례**: 2026-10-15 «사건·계약 근로자 주민번호·계좌를 담당자만»(`status/2026-10-15-rrn-owner-only.md`, 규칙 `rules.worker_secret`, 모듈 `js/pu-worker-secret.js`, 이사 `scripts/worker-secret-migrate.js`). 계약·사건이 «한 덩어리»라 칸 하나만 규칙으로 막을 수 없어서 값을 `worker_secret/{표}/{건 id}/…` 로 떼고, **규칙이 그 건의 지금 담당자 칸을 직접 읽어** 허용 여부를 따졌다. 실서버에서 끝까지 배포·이사까지 했다.

**금액에 같은 방식을 쓴다**
- 금액(`amounts`·`contractFee`·`balanceFee`·`successFee`·`contractFeeVatIncluded` … 정확한 칸 목록은 A0 에서 확정)을 계약에서 떼어 **건 id 별 잠긴 자리** `contract_amt/{계약 id}` 에 둔다.
- **읽기·쓰기 = 대표·총괄관리자(`isAdmin`) ∨ 재무(`fin`) ∨ 그 건의 담당자**. 담당자는 규칙이 `data/contracts/v/{id}` 의 **지금** `managerMain`·`managerSubs`(사번)를 직접 읽어 따진다 → **담당자가 바뀌면 바로 따라간다. 접근자 목록을 따로 두거나 동기화하지 않는다**(전에 «동기화 방법 미정»이라 적었던 것이 이 선례로 풀렸다).
- 선례에서 물려받는 주의(주석에 이미 적혀 있다): **부담당은 앞 다섯 자리까지** · **위임관리인은 «담당일 때만»**(SUB 를 규칙에 넣지 않는다) · **내 사번이 비어 있으면(null) 통째로 거절**(담당 칸도 빈 건이 null === null 로 열리는 것을 막음) · 값이 `data/contracts/v/{id}` **지도 형식**임을 전제(주민번호 이사가 같은 전제로 이미 작동). 부관리자(`isSubAdmin`)·일반 직원은 못 본다. **재무(`fin`)를 더하는 것은 주민번호 규칙과 다른 점**이다(대표 결정 설계 §7).
- 뿌리(`contract_amt`)에는 `.read` 를 두지 않거나, 두면 `isAdmin ∨ fin` 만 둔다(계획 1 `pu_quote_amt` 와 같은 이유 — 파이어베이스는 위에서 준 `.read` 를 아래에서 거둘 수 없다).

**화면의 원칙(선례 그대로)**
- 화면은 «누가 볼 수 있나»를 **흉내 내지 않는다.** 읽어 보고 서버가 거절(`permission_denied`)하면 «🔒» 로 보인다. 잣대는 규칙 한 곳이다.
- 공개 덩어리(계약)에는 값 대신 **«금액 있음» 표시**(`hasAmount` 같은 칸)만 남긴다 — 권한 없는 직원이 «🔒 금액 비공개»와 «금액 없음»을 가른다.
- **«없음 = 모름 / 빈칸 = 지웠다»를 구분한다**: 못 읽은 것(거절)은 **0 이 아니다**. 합계·통계에 0 으로 넣지 않고 «합계 비공개»로 낸다. 권한 없는 직원이 계약을 저장해도 금액은 그대로 남는다(손대지 않는다).
- **이 PC 사본에도 남기지 않는다** — 저장 입구(`dbUpsert`·`dbPatch`·`dbUpsertMany`·`dbSet`) 맨 앞에서 뗀다(성공한 자리에서만 잠긴 자리로 보냄). 휴지통·백업·복원도 같은 방식.

**하지 않는 것**: 계약 칸에 금액을 두고 화면에서만 가리기(설계 §2 «실패로 볼 것»), 규칙 없는 «숨은 칸», 담당자 접근자 목록을 따로 두고 사람이 맞추기.

### D2. 누가 읽나 — 권한자 화면이 읽는다(권장), 서버는 다음 단계
- **권장(1단계)**: 이알피를 연 **금액 볼 권한이 있는 사람(대표·총괄관리자·재무·그 건 담당자)의 화면**이 처리한다. 기존 길을 그대로 쓴다 — 첨부 받기(`readMailAttachment`) · 글자 뽑기(`extractText`) · AI(서버 대리인 `functions/doc-read.js`, 열쇠는 브라우저에 없음). 금액이 «볼 권한이 있는 사람의 화면 안»에서만 다뤄지므로 **비공개 선과 어긋나지 않는다**. 담당자가 정해지지 않은 카드는 대표·총괄관리자·재무가 연 화면만 읽는다. 계획 3 의 «열려 있는 동안 1분마다 이어서 처리»가 이미 있어 근무 시간에는 사실상 연속이다.
- **한계**: 권한자가 이알피를 열어 둔 동안에만 돈다(완전 무인 아님). 대표가 «아무도 안 열어도»를 원하시면 2단계(서버 처리)가 필요하다.
- **2단계(선택, 별도 승인)**: 서버(메일 동기화 뒤 훅)가 읽는다. 첨부 글자 뽑기(PDF·HWP)를 서버로 옮겨야 하고(지금은 브라우저 쪽 도구) **[확인 필요]**, AI 호출이 서버 비용으로 바로 잡힌다. 지금은 하지 않는다. (서버는 보안규칙을 우회하므로 «누가 읽나»를 코드로 직접 지켜야 한다.)
- 대기열에는 지금처럼 **금액·본문을 싣지 않는다**. 요청은 «어느 메일의 어느 첨부»를 가리키는 칸만(`srcKey`·첨부 번호).

### D3. 자동으로 채우는 칸 — «빈 칸만», 사람 값은 덮어쓰지 않는다
| 칸 | 어디서 | 규칙 |
|---|---|---|
| 사업장 | 요청의 `companyId`(계획 3 길) | 문서의 회사 이름이 업체관리와 크게 다르면 **걸림**(다른 회사 문서일 수 있다). 이름으로 `companyId` 를 만들지 않는다 |
| 계약 기간(시작·종료) | 문서 | 비어 있을 때만 채움 |
| 종류(`kinds`) | 문서 + 요청 | 사람이 정한 종류가 있으면 그대로 |
| 금액(`amounts`·`successFee`…) | 문서 | **잠긴 자리**에만 저장, 검증 통과 때만 |
| 사업자번호·대표자 | **문서에서 읽지 않는다** | 업체관리(업체 마스터)가 원본 — 마스터를 덮어쓰지 않는다 |
| 상황(상담접수·계약협의·계약확정) | 신호 | B 는 «계약협의»까지, **확정은 C 만** |
- 사람이 이미 적은 값과 읽은 값이 다르면 **카드에 «읽은 값과 다름»으로만** 표시한다(덮어쓰지 않음).

### D4. 자동 반영의 기록과 되돌리기
- 자동으로 카드를 만들거나 고칠 때마다 카드에 `auto = { kind, at, srcKey, by:'auto', before:{바뀐 칸의 이전 값}, after:{…}, model, readAt }` 를 남긴다(금액 값은 이 기록에 넣지 않는다 — 금액은 잠긴 자리의 `src` 에만).
- 카드에 **«🤖 자동 반영 · 되돌리기»** 단추(권한자·그 건 담당자). 되돌리면 `before` 로 복원하고 작업 기록에 `auto_undo`.
- 작업 기록(`pu_worklog`, 총괄관리자만 읽기)에 `auto_fill`·`auto_confirm`·`auto_undo` 를 남긴다 — **금액 글자는 넣지 않는다**(건수·카드 id 만).
- 자동 확정 취소: `signed` → `review`, 사유 필수, 작업 기록. 이관·청구가 이미 시작된 건은 **취소 단추를 막고** 사람이 본다 **[확인 필요 — 이관 시작 표시가 계약에 있는지]**.

### D5. 켜고 끄는 스위치 — 단계마다 따로, 기본 «꺼짐»
- `pu_docs/config/autoFill/on`(B) · `pu_docs/config/autoConfirm/on`(C) — 계획 3 후속 PR #2974 의 `quoteWatch` 와 같은 모양·같은 규칙(총괄관리자만 쓰기). 하나가 꺼져 있으면 그 단계는 «후보»만 띄운다.

### D6. 한 건이 지나가는 길

**B — 계약서 읽어 채우기**
1. 보낸메일함에 우리 계약서 메일이 나간다 → 서버 훅(켜져 있으면)이 «계약서 메일» 요청을 남긴다(제목·첨부 이름·받는 주소만, 금액 없음).
2. 권한자가 이알피를 열어 둔 화면이 요청을 «맡았다» 표시로 잡는다(두 화면이 동시에 하지 않게).
3. 첨부를 받아 **글자만** 뽑고, 주민번호·계좌 모양을 가린다.
4. AI 가 칸을 읽는다(월 한도 확인 · 같은 파일은 다시 읽지 않음).
5. 검증표를 통과하면 카드(빈 칸만)와 잠긴 자리에 저장, 못 통과하면 금액은 빼고 «확인 필요».
6. **서버에 닿은 것을 확인한** 뒤 요청을 지운다.
7. 카드에 «🤖 자동 반영 · 되돌리기»가 붙는다.

**C — 서명본 자동 확정**
1. 서명 신호가 온다(전자서명 완료 / 서명본 올리기 / 메일 회신) → `confirm` 요청.
2. 권한자 화면이 신호별 조건표를 적용한다.
3. **모두 맞음** → 계약협의 카드를 계약확정 + 서명일(서류 보내기·이관은 하지 않음), 담당자 알림, 작업 기록. **하나라도 빠짐** → «서명본 후보» 띠 → 사람이 한 번.
4. 틀렸으면 «확정 취소»(사유 필수).

**검증 규칙표(②)** — 모두 통과해야 **금액을 채운다**. 하나라도 어긋나면 금액 칸은 비우고 «확인 필요» + 후보만 잠긴 자리에 둔다(카드는 만들거나 고칠 수 있다).
1. 금액 후보가 문서 안에서 **서로 맞는다**: 합계 = 공급가액 + 부가세(±1원). 합계만 있으면 «부가세 포함 여부 불명»으로 표시.
2. **자릿수**: 문서의 원 단위 숫자에 «만·억» 표기가 함께 있으면 둘이 일치해야 한다(1만 배 오독 전례 방지 — 사진첩 방 전언 **[확인 필요: 저장소에서 근거를 못 찾음]**).
3. **견적과 대조**: 같은 `companyId` 의 견적 기록(`pu_quote_amt`)이 있고 금액 차이가 크면(예: 5배 이상) 채우지 않고 걸림.
4. **회사 대조**: 문서의 회사 이름이 요청의 업체와 크게 다르면 걸림(다른 회사 문서일 수 있다).
5. **못 읽음 = 0 이 아니다**: 빈칸 + «확인 필요». 0 이나 기본값을 넣지 않는다.
6. 모든 자동 값에 «AI 가 읽음» 표시 + 출처(메일 key·파일 id·sha256·모델·읽은 시각).

**개인정보·비용(④)**
- **원본 파일을 AI 에 보내지 않는다** — 브라우저에서 글자를 뽑아(`TEXT_MAX` 상한) 그 글자만 보낸다.
- 글자를 보내기 **전에** 주민등록번호·계좌번호 모양을 가린다(정규식), AI 응답에서도 같은 모양이 나오면 버린다(이중). 계약서에는 대표자 주민번호·계좌가 드물지 않다. **가림 정규식은 겹치는 반복이 없게 짜고 입력 길이 상한을 둔다**(계획 3 에서 금액 가림 정규식이 56자 입력에 8초 걸리는 ReDoS 가 나온 적이 있다).
- **AI 비용**: 판독은 유료 등급이고 «이번 달 요금 한도 ₩50,000 · 경고 ₩45,000»(`functions/doc-read.js`)가 있다. 한도에 닿으면 «나중에»로 남기고 사람이 채울 수 있게 한다. 같은 파일(sha256)은 다시 읽지 않는다. 건수 규모: 2026-08-05~11-07 보낸메일함에 우리 계약서 약 39건·견적서 약 24건(설계 §3·§4) — 한 달 십여 건. 코드의 계산 기준값은 «건당 4원»(`AI_BUDGET_DEFAULT.wonPerRead`, 추정치)이라 이 규모의 비용은 작다 — 실제 건당 비용은 **기록으로 확인**한다 **[확인 필요]**.

## 8. «실패로 본다» — 이게 일어나면 멈추고 되돌린다

- 금액이 **DB 에서** 권한 없는 직원에게 읽힌다(화면에서만 가려진 것은 실패).
- **읽지 못한 금액을 0 으로 보여** 합계·통계가 틀린다(못 읽음 ≠ 0).
- 한 계약이 자동 등록·확정으로 **겹쳐 생긴다**(같은 사업장·같은 업무).
- **다른 금액·다른 회사**로 계약확정이 저절로 된다.
- **보낸 원본을 그대로 돌려받은 파일**로 확정된다.
- **1만 배 틀린 금액**이 검증 없이 저장된다.
- 자동 확정이 **이관·발송·청구·출력**을 시작한다.
- 비교견적 건이 선정 없이 계약협의·확정으로 간다.
- AI 비용이 월 한도를 넘는다.
- 작업 기록·요청·토스트·로그에 **금액 글자**가 남는다.
- 이사 중 **옮긴 것을 되읽어 맞추기 전에** 공개 칸이 비워진다.

## 9. 시험 방침 (이 저장소 관례)

- 규칙은 글자가 아니라 **판정기**로(`tests/quote-watch-switch.test.js` 방식 — 이름 칸·`$변수` 칸을 둘 다 맞는 것으로 센 «엄격» 해석 포함). 규칙 에뮬레이터 시험도 한다(통짜 값·삭제는 자식 규칙이 안 불리는 함정에 주의).
- 순수 판정(`erpFillPlan`·`erpSignedPlan`·`PuContractRead`)은 입력·출력만으로, 저장하는 쪽은 실제 함수를 `cutFn` 으로 잘라 가짜 파이어베이스로(저장 확인 `landed`·거절·시간 초과 포함 — 계획 3 방식).
- «하나씩 빼 보기»: 조건표의 칸을 하나씩 빼면 `confirm` 이 `candidate` 로 바뀌는지. **고장넣기**: 분리·규칙·검증을 일부러 망가뜨려 시험이 빨개지는지.
- 금액이 새지 않는지: 요청·작업 기록·카드 메모·토스트·`console` 에 금액 글자가 없는지 글자 검사. **새 읽는 곳이 모듈 밖에 생기지 않는지** 글자 검사.
- 정규식·긴 입력은 **시간 상한**(`ReDoS`) 시험.
- 화면은 가짜 파이어베이스 + 지어낸 자료로 직접 띄워 PC·폰 모두(`tools/phone-audit`). 진짜 파이어베이스·메일·**로그인(담당자 계정·비담당 계정)**은 AI 가 못 하니 첫 건을 사람이 보며.
- 코드를 만든 뒤에는 사용자 지침대로 자동 검토(기능 검증·보안 검토)를 돌린다 — 보조일 뿐이고 사람의 최종 검토가 필요하다.
