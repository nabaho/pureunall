## 0. 결론

1. **데이터관리는 대표 전용 그대로 둔다.** 다른 앱으로 가는 것은 제미나이 판의 «모양»뿐이다 — 둥근 카드·옅은 그림자·알약 단추·섹션 머리말·숫자 카드·표 머리·배지·알림·검토 창의 생김새.
2. **대표 전용 숫자와 화면은 옮기지 않는다.** 입금 총액, 사람별 실적(구슬·산맥), 3D 관제, 다년·세무 대조, 영상 브리핑, 현황판, 연결 지도, 채팅은 데이터관리 안에만 있다(2-3).
3. **보는 사람은 그대로다.** 디자인을 바꿔도 앱마다 «누가 무엇을 보는지»(로그인·권한·보안규칙)는 바뀌지 않는다. 직원이 쓰는 앱은 직원이 지금 보는 것만 새 모양으로 본다.
4. **값만 바꾸고 기능·위치는 그대로다**(2026-11-15 푸른 캘린더 되돌림 교훈). 탭·거르개·칸·줄·단추를 숨기거나 서랍에 넣거나 옮기지 않는다. 위치가 바뀌는 일(위쪽 탭 → 왼쪽 메뉴 등)은 앱마다 그림을 보여 주고 대표가 고른다.
5. **방법: 공용 디자인 파일 하나 + 앱마다 PR 하나.** 공용 파일은 «켜는 앱에만» 먹게 만들어(5절), 아직 켜지 않은 앱은 한 점도 안 바뀐다. 시범 앱 1~2개로 시작해 대표가 바뀐 그림을 보고 합친 뒤 넓힌다.
6. **지금 앱들은 디자인 부품을 함께 쓰지 않는다.** 31개 앱이 색 변수·카드·창·알림을 저마다 복사해 두었다(4-1). 그래서 공용 파일을 하나 만들면 이번 일뿐 아니라 앞으로 모양을 바꿀 때도 한 곳만 고치면 된다.
7. **추천 시범**: 컨설팅정산(작은 앱 10개의 본보기) + 업무관리(목업과 같은 변수 이름, 매일 쓰는 앱). 이알피는 가장 크고 모두가 쓰니 시범 뒤 마지막 쪽에(4-2, 결정 Ⓑ).

## 1. 요청과 해석

- «다른 앱도 계획» = 데이터관리 목업에 적용한 제미나이 디자인을 포털의 다른 앱에도 넓히는 **계획**을 세운다. 구현은 결정 뒤.
- «지금 프로그램은 오로지 대표인 나만 보는 것» = 데이터관리는 대표 혼자 보는 프로그램이다. 그래서 다른 앱(직원도 쓰는 앱)으로는 데이터관리의 **자료·숫자·대표 전용 기능을 끌고 가지 않고 모양만** 넓힌다고 해석했다. [확인 필요] «다른 앱에는 넓히지 말라»는 뜻이었다면 이 계획은 접는다(결정 Ⓐ).
- «모든 디자인 적용»(11-18)은 제미나이가 실제로 다시 그린 화면(데이터관리)에 대한 지시다. 다른 앱은 제미나이가 그린 적이 없으니, 다른 앱에서는 «모양 값»을 맞추는 일이고 새 기능을 더하는 일이 아니다. 새 기능(2-2)은 앱마다 대표가 고를 때만 넣는다.

## 2. 제미나이 판에서 무엇을 넓히나 — 세 갈래

### 2-1. 넓힌다 — 모양 값 (기능·자리는 그대로)

### 2-3. 넓히지 않는다 — 대표 전용 (데이터관리 안에만)

- 3D 장면(입금 막대 숲·사람 구슬·업무량 산맥·한 해 입금 고리·업체 도시)과 3D+2D 나란히 보기
- 사람별 실적·업무량 숫자, 입금 총액·종류 비중
- 다년(2022~2029) 매출·장기 전망·세금계산서·재무제표 대조
- 영상화 브리핑·시네마 무대, 포함·제외 검토 창(입금 자료 전용)
- 프로그램 현황판, 연결 지도, 이 컴퓨터 전용 채팅, 잠금 화면

까닭: 데이터관리는 대표 혼자 보는 프로그램이다(대표 지시 11-18·11-19). 같은 그림을 다른 앱에 두면, 그 앱을 쓰는 직원에게 대표 전용 숫자가 보이거나 «보일 수 있는 길»이 생긴다. 모양(CSS)만 넓히고 숫자를 그리는 코드는 데이터관리 밖으로 꺼내지 않는다.

## 3. 지킬 것

1. **값만, 기능·자리 그대로.** 바꾸기 전 화면에 보이던 단추·입력칸·고르개·표 머리칸·탭이 바꾼 뒤에도 같은 자리에 같은 수만큼 보여야 한다. «서랍 안에 있다»는 «없다»로 본다(2026-11-15 되돌림).
2. **보는 사람 그대로.** 디자인 PR 은 보안규칙(`scripts/make-firebase-rules.js`)·로그인 관문(`PuGate`)·읽는 자료 경로를 바꾸지 않는다. 바꿀 일이 생기면 그 PR 에서 빼서 따로 묻는다.
3. **색**: 팔레트 안에서만(`tests/color-palette.test.js`·`tests/color-palette-apps.test.js`), 글자 대비 4.5:1 이상.
4. **표 한 칸 한 줄**(`tests/one-line-cells.test.js`), **☐+№**(`docs/규칙/고르기칸-번호.md`).
5. **폰**: 폰 구간에서만 따로 바꾸고, 입력칸 16px 이상, 확대를 막지 않는다(`tests/phone-screen-rules.test.js`·`tests/phone-input-zoom.test.js`). 떠 있는 단추는 공용 앱바(`js/pu-appbar.js`)가 정리한다 — 디자인 파일이 `bottom` 을 박거나 숨기지 않는다.
6. **바깥 것 없음**: 외부 라이브러리·CDN·웹 글꼴을 싣지 않는다.
7. **자료는 안 건드린다**: 디자인 PR 은 저장·삭제·이관 코드를 만지지 않는다. 그래서 온톨로지 쓰기 계약(`tests/ontology-contract.test.js`)·끝난 건 불변(`tests/anti-resurrection-guards.test.js`)에 걸릴 일이 없어야 하고, 걸리면 그 PR 은 디자인 PR 이 아니다.
8. **검사는 규칙을 박는다**: 새 검사는 «공용 디자인 파일을 싣는가»·«켠 앱의 보이는 단추 수가 줄지 않았는가»처럼 보고, 16px·그림자 값을 글자 그대로 박지 않는다(`tests/test-pin-guard.test.js`).

## 4. 앱별 현황과 적용 안

조사: 2026-11-19, `enter.html` `APPS` 31개 앱의 소스를 읽어 판단했다(화면을 직접 열어 본 것은 아니다 — 10절). 줄 수는 그날 기준.

### 4-1. 지금 모양 — 알게 된 것

- **여러 앱이 함께 싣는 디자인 파일이 없다.** 앱마다 자기 `<style>` 에 `:root` 색 변수와 카드·단추·탭·창·알림을 따로 두었다. 알림 함수 `toast` 는 HTML 18곳·JS 11곳에, `.modal` 은 16곳에 따로 있다. 공용은 JS 가 끼워 넣는 몇 조각(`js/pu-appbar.js` 떠 있는 단추, `js/pu-gate.js` 로그아웃 화면, `js/pu-version.js` 새 버전 알림)뿐이다.
- **색 변수 이름이 네 벌이다.**
  - A: `--ink`·`--mute`·`--blue`·`--green`·`--amber`·`--red` … — 작은 새 앱들
  - B: `--acc`·`--acc2`·`--acc-soft`·`--ink`·`--sub`·`--faint` — **데이터관리 목업과 같은 이름**(업무관리·기금관리·푸른 캘린더)
  - C: `--navy`·`--violet`·`--ok`·`--warn`·`--bad` — 급여아웃소싱·급여데이터함
  - D: `--navy`·`--paper`·`--ok`·`--warn`·`--bad` — 홈페이지·뉴스레터
- **그래프 라이브러리를 쓰는 앱은 없다.** 막대는 거의 다 CSS 폭(%)으로 그린다. 손으로 짠 SVG 그래프는 공공임단협 하나다. 그래서 2D 그래프 «모양 바꾸기»가 걸리는 앱은 적다.
- **이알피에는 이미 «전역 디자인 통일» 절이 있다**(`css/pu-erp.css` 914줄~: 창 모서리 12px·입력칸·표 글자 규격). 이알피는 새 층을 겹치지 않고 이 절의 값을 바꾸는 식으로 간다(«이미 있는 것부터»).
- **색 검사가 안 보는 곳이 있다.** `tests/color-palette.test.js` 는 `pu-erp.html` 만, `tests/color-palette-apps.test.js` 는 HTML 30개만 본다. `css/pu-erp.css`(팔레트 밖 `#dbeafe`·`#fee2e2`·`#2a3656` 등이 있다), 앱 JS 안의 CSS, `gov.html`·`pu-news.html`(팔레트 밖 `--brown`)·공공임단협·한글 편집기는 안 본다. 디자인을 켜는 앱은 그때 검사 대상에 넣는다.
- 폰 현황표(`docs/폰화면-현황.md`)는 2026-10-18 에 잰 것이고 그 뒤 생긴 9개 앱이 빠져 있다. 1단계에서 다시 잰다.

### 4-2. 무리별 적용 안

같은 틀을 복사해 쓴 앱끼리 묶었다. 같은 무리는 앱 전용 CSS 가 거의 같아져서 한 번 맞춘 것을 되풀이한다.

| 무리 | 앱 (key · 파일 · 줄 수) | 지금 틀 | 넓힐 것 | 조심할 것 |

## 5. 어떻게 — 공용 디자인 파일 하나, «켜는 앱에만»

- 새 파일 `css/pu-design.css`(이름 겹침 확인: `css/`·`js/` 에 같은 이름 없음. `js/pu-photo-look.js` 는 사진첩 것이라 피했다).
- 안의 모든 규칙은 `body.pu-design` 아래에만 먹는다. 변수는 `--pu-` 를 붙인다(`--pu-acc` 등) — 앱마다 이미 `--acc`·`--line` 같은 같은 이름 변수를 따로 갖고 있어, 머리말 없이 넣으면 켜지도 않은 앱 색이 바뀐다.
- 값은 데이터관리 목업 `:root`(10~19줄)와 2-1 의 틀에서 옮긴다. 한 곳에서 바꾸면 켠 앱 모두에 같이 간다.
- 앱의 변수 이름 네 벌(4-1 A~D)은 그대로 두고, 켠 앱에서만 그 변수가 공용 값을 가리키게 한다(예: B 계열 `--acc: var(--pu-acc)`). 앱 코드 곳곳의 `var(--acc)` 를 고쳐 쓰지 않는다.
- 새 파일은 색 검사 대상에 바로 넣는다(`tests/color-palette-apps.test.js` 는 지금 HTML 만 본다 — CSS 파일도 읽게 할지 1단계에서 정한다 [확인 필요]).
- 알림·창의 **동작**(JS `toast`·창 여닫기)은 앱마다 따로 있는 그대로 둔다. 공용 파일은 생김새만 맞춘다 — 동작까지 하나로 모으면 디자인 PR 이 아니라 기능 PR 이 된다.
- 앱 하나 켜기 = 그 앱 HTML 에 `<link rel="stylesheet" href="css/pu-design.css">` 와 `body` 의 `pu-design` 한 단어 + 그 앱 고유 이름표(예: 이알피의 `.sb`)를 공용 모양에 잇는 짧은 앱 전용 CSS. 화면 구조(HTML)·이름표·`id`·`data-*` 는 바꾸지 않는다.
- 되돌리기 = `pu-design` 한 단어를 빼면 옛 모양으로 돌아간다.
- 어두운 모드: 앱마다 지금 방식 그대로 둔다(예: 이알피는 `body.dark-mode` 뒤집기). 공용 파일은 어두운 모드를 새로 만들지 않는다. 데이터관리의 «시네마 무대»는 3D 캔버스 전용이라 넓히지 않는다.

## 10. 위험과 아직 모르는 것

- **직원 화면 전체가 바뀐다.** 한꺼번에 바꾸면 «어디 갔나»가 생긴다 → 한 앱씩, 전후 그림, `[보류]`, 3절 1번(보이는 단추 수 대조).
- **같은 이름 변수 충돌.** 머리말 없는 공용 변수는 켜지 않은 앱 색도 바꾼다 → `--pu-` 머리말 + `body.pu-design` 범위(5절).
- **이알피는 공용 CSS 로 못 덮는 곳이 많다.** 97,850줄에 Preact 화면과 줄마다 박은 `style` 이 많다. `!important` 를 늘려 덮으면 뒤에 손보기가 어려워진다 → 이알피는 «전역 디자인 통일» 절 값을 바꾸는 데서 그치고, 못 덮는 곳은 목록으로 남겨 대표에게 묻는다.
- **어두운 모드.** 이알피는 색 뒤집기 필터, 캘린더·경력관리·공공임단협·P박스는 자기 어두운 판이 있다. 둥근 그림자·그라데이션이 뒤집혀 이상해 보일 수 있다 → 어두운 판도 그림으로 확인.
- **폰.** 폰 현황표가 10-18 자료이고 9개 앱이 빠져 있다. 디자인 PR 이 폰 문제(작은 단추 등)를 함께 고치기 시작하면 범위가 커진다 → 폰 문제는 따로 둔다. 단, 디자인 때문에 «새로» 생긴 폰 문제는 그 PR 에서 고친다.
- **확인하지 않은 것.** 앱을 브라우저로 열어 보지 않았다 — 틀·대시보드 유무는 소스의 이름표·주석으로 판단했다. «대시보드 못 찾음» 앱(정부지원금·오케스트레이션·정부사업신청·전광판·계약서등관리)은 낱말로 못 찾았다는 뜻이고 없다는 뜻이 아니다. CSV 를 내보내는 앱이 어디이고 수식 막기가 있는지는 아직 보지 않았다(2-2) [확인 필요].
- **동시 작업.** 여러 방이 같은 앱을 고친다 → 4-2 끝의 열린 PR 이 합쳐진 뒤에.
- **데이터관리 자체는 아직 목업이다.** 이 계획은 데이터관리 앱 구현(계획서 2026-11-18)과 따로 갈 수 있다. 공용 디자인 파일을 먼저 만들면, 데이터관리를 만들 때 같은 파일을 쓴다.
