# 취업규칙 프로그램 새로 짓기 — 설계 (2026-10-03)

대표 지시: 「메일함에 푸른노무법인에서 보낸 취업규칙의 종류들이 모두 다 있다. 이 부분을 모두
가지고 와서 별도로 보관하고, RAG 로 데이터 처리하고, 취업규칙 프로그램 다시 만들 수 있나?」

## 1. 왜 새로 짓나 (대표 답, 넷 다)

- 흐름이 복잡하다 — 단추·창이 많아 어디서 무엇을 할지 모른다.
- **우리 문안이 중심**이어야 한다 — 지금은 표준규칙·검토 기준이 중심이다.
- 사업장별 이력을 한눈에 — 메일·회차·신고·동의서를 한 자리에서.
- 파일이 너무 커서 고치기 어렵다 — `rules.html` 한 파일 약 9,000줄(720KB).

## 2. 정한 것

| 물음 | 결정 |
|---|---|
| 만드는 방식 | 처음부터 새로 짓기 |
| 짜임새 | **A. 작은 파일로 새 앱** — 빌드 단계 없음, 이 저장소 방식 그대로 |
| 갈아타기 | 옛 규정관리와 **나란히** 두고, 새 앱이 신고서류까지 다 하면 옛 것을 내린다 |
| 첫 화면 | **사업장 목록** — 고르면 그 회사의 취업규칙 이력 한 줄 |
| 문안 추천 | **가장 최근에 쓴 것 + 비슷한 회사 것** 2~3개를 나란히. 검토 기준에 어긋나면 표시 |
| 모을 범위 | **지금 들어와 있는 메일부터**(2023-09 ~). 지난 메일은 들어오는 대로 뒤에 붙인다 |
| 모으는 길 | **서버가 매일 저절로** |
| 보관 모습 | **가린 사본만** + 원본은 메일로 잇는다 |
| AI | 검색은 AI 없이, **문안 다듬기에만** Gemini(가린 글만 보낸다) |

실측(2026-10-03, 메일 목록 22,265통): 제목에 「취업규칙」 약 320건(답장 겹침 걷음), 회사 약 80곳,
개정안 송부 72 · 검토·자문 60 · 신고 42 · 동의서 33. 지난 메일(POP3)은 30,000통 중 13,488통만
들어와 있어 2023-09 이전은 아직 없다.

## 3. 세 덩어리로 나눈다

각 덩어리는 따로 설계 → 승인 → 만들기를 거친다. 이 문서는 **전체 짜임새 + 덩어리 ①** 이다.

1. **메일 → 보관함** (이 문서 §4) — 어떤 화면을 짓든 먼저 있어야 하는 자료.
2. **조문 색인·검색** — 보관함의 «규칙 본문»을 조로 쪼개 찾는다. AI 없이(제목·낱말·사업장 규모·업종).
   「가장 최근 + 비슷한 회사」 추천의 바탕이 된다. (다음 설계)
3. **새 앱 화면** — 사업장 목록 → 이력 → 개정 작업(우리 문안 추천, 문안 다듬기에만 AI) → 신고서류.
   **UI 는 목업을 먼저** 보이고 승인받는다. (다음 설계)

### 3-1. 새 앱의 짜임새 (A)

- 새 화면 파일(이름은 덩어리 ③ 에서 정한다, 임시 `rules-v2.html`) + `js/rules-v2/` 아래 화면별 작은 파일.
  한 파일 300~800줄을 넘기지 않는다.
- **그대로 다시 쓰는 부품**: `pu-rules-casebook.js`(서고 판정) · `pu-rules-lawlink.js`(법조문 연결) ·
  `pu-rules-lawwatch.js`(법 개정 감시) · `pu-hwp-keep.js`(원본 살려 고치기) · `pu-kordoc-text.js`(읽기·가림) ·
  `pu-rules-filecmp.js`(두 파일 견주기).
- **옛 앱에서 떼어 낼 부품**(덩어리 ③ 에서): 검토 기준 87개와 판정(`RULES`·`evaluate`) ·
  신고서류 만들기(신구대조표·의견청취서·동의서·신고서 HWPX). 떼어 낸 뒤 **옛 앱도 그 부품을 싣게** 바꿔
  두 앱이 한 벌을 쓴다 — 기준을 고치면 두 앱이 함께 따라온다.
- 온톨로지: 새 앱은 `PuOntology.PROGRAMS`·`READ_ADAPTERS`·`writeContracts` 에 먼저 등록한다
  (등록 안 하면 배포검사 실패 + 저장 거절). 새 개체 `RulesDocument`(모은 취업규칙 서류)는 `TERMS` 에 먼저 정의한다.

## 4. 덩어리 ① — 메일 → 보관함

### 4-1. 흐름 (서버, 매일 새벽 5시)

```
메일 목록(mailbox/msgs · mailbox/old/msgs)
  → ① 고르기: 제목·미리보기에 취업규칙 말이 든 메일, 아직 안 본 것(seen 에 없음)
  → ② 첨부 받기: 지금 메일함은 IMAP 조각 이름으로, 지난 메일은 POP3 RETR 로(이미 있는 길)
  → ③ 첨부 고르기: .hwp · .hwpx · .pdf · .docx 만. 원본 지문(sha256)이 이미 있으면 건너뜀(답장마다 같은 파일)
  → ④ 가리기: kordoc 로 서버 메모리 안에서
  → ⑤ 갈래 짓기: 규칙 본문 · 신구대조표 · 신고서 · 동의서 · 의견청취 · 기타
  → ⑥ 사업장 후보: 보낸·받은 주소 → 업체관리 이메일 / 회사 도메인(공용 도메인 제외)
  → ⑦ 담기: 가린 파일(창고) + 가린 글(DB) + 목록 한 줄(DB) + seen 표시
```

- 한 번에 **60통**까지만(함수 9분 안에 끝나게). 처음 밀린 약 320통은 관리자가 새 앱의
  「지금 더 모으기」(HTTPS, 관리자만)로 앞당길 수 있다. 같은 함수 몸통을 쓴다.
- 고르는 말: `취업규칙` · `사규` · `인사규정` · `복무규정` · `규정 개정/정비/제정`. 첨부 이름에
  `취업규칙` 이 들면 제목에 없어도 고른다(IMAP 은 bodyStructure 로 이름을 먼저 본다).

### 4-2. 가림 — 지키는 선

- 쓰는 규칙은 서고 가림(②, #1780)과 **같은 한 벌**: 주민·외국인번호 · 계좌·카드 · 전화 · 전자우편 · 여권·면허.
  사업자번호는 사업장 열쇠라 두고, 이름·주소는 헛잡기가 많아 끈다.
- 한글(.hwp·.hwpx)은 파일째 서식 그대로 가리고, **가린 파일을 다시 읽어 남은 것을 센다.**
  PDF·워드는 파일째 못 가리므로 **글만 담고 파일은 안 담는다.**
- **남은 것이 하나라도 있거나, 읽지 못했거나(그림뿐인 PDF 등) → 아무것도 담지 않는다.**
  목록에 「보류」 한 줄(까닭과 가린 셈만)만 남긴다. 관리자는 메일함에서 원본을 직접 볼 수 있다.
- 원본 바이트는 **서버 메모리에서만** 다루고 창고·DB·로그 어디에도 쓰지 않는다. 로그에는 셈만 찍는다.
- ⚠ **원칙이 바뀐다**: 지금은 「문서는 브라우저 밖으로 안 나간다」(`tests/kordoc-mcp.test.js`).
  새 원칙은 「가리기 전 원본은 서버 메모리에서만, 저장되는 것은 가린 것뿐」이다.
  그 검사를 새 뜻으로 고치되, 서버에서 kordoc 를 부르는 자리는 **이 수집기 하나**만 허락한다.
  (첨부는 이미 서버 함수 `readMailAttachment`·`readOldMail` 을 지나고 있다 — 새로 밖으로 나가는 길은 아니다.)

### 4-3. 담는 자리

새 최상위 자리를 만들지 않는다 — 이미 규칙이 있는 `rules_mgmt` 아래에 둔다.

| 자리 | 내용 | 읽기 | 쓰기 |
|---|---|---|---|
| `rules_mgmt/library/docs/{docId}` | 목록 한 줄(아래) | 직원 | 서버만 |
| `rules_mgmt/library/text/{docId}` | 가린 글(무거워서 목록과 가른다) | 직원 | 서버만 |
| `rules_mgmt/library/seen/{mailKey}` | 이 메일을 봤다 · 나온 docId · 건너뛴 까닭 | 관리자 | 서버만 |
| `rules_mgmt/library/run` | 마지막 회차 요약(본 메일·담음·보류·걸린 시간) | 직원 | 서버만 |
| 창고 `pureun-erp-hrphotos` · `rules_lib/{docId}.{ext}` | 가린 한글 파일 | 직원 | 서버만 |
| `rules_mgmt/library/docs/{docId}` 의 사람이 고치는 칸(아래 «사람 칸») | 사업장 확정 · 최종본 · 갈래 · 회차 | 직원 | **재직 직원 누구나 — 사람 칸만**(규칙으로 서버 칸은 막는다) |

목록 한 줄:

```
{ id, entityType:'RulesDocument', schemaVersion:1, createdAt, updatedAt, revision,
  kind: '규칙본문'|'신구대조표'|'신고서'|'동의서'|'의견청취'|'기타',
  name,                      // 첨부 이름
  mail: { src:'imap'|'pop3', box, key, date, from, subject },   // 원본으로 가는 길
  sha,                       // 원본 지문 — 겹침 거르기용(내용을 되살릴 수 없다)
  file: { path, format, size } | null,   // PDF·워드는 null(글만)
  textLen, pii: { count:{rrn:1,…}, residual:0 },
  status: '담김'|'보류', holdWhy,
  companyId: null, companyCand: [{ companyId, why:'주소'|'도메인' }],
  companyLinkStatus: 'pending'|'linked',     // TERMS.companyLinkStates
  dir: '보냄'|'받음',          // 푸른이 보낸 판인지 회사가 보낸 판인지
  round: null,                // 회차 열쇠 — 사업장 확정 뒤 서버가 짚고 사람이 고친다(§4-6)
  finalCand: [ '신고서 메일 바로 앞 판' | '파일 이름에 「최종·신고용」' | '동의서와 같은 메일' ],
  // ── 사람 칸 ──
  // companyId · companyLinkStatus · linkedBy · linkedAt · kindFix(갈래 고침) · round
  // final:{ by, at } | null  — 한 사업장·한 회차에 하나
  // updatedAt · revision
}
```

### 4-4. 사업장 잇기

- 서버는 **후보만** 붙인다(`companyCand`). 이름이 같다는 것만으로는 후보도 안 만든다.
- 사람이 새 앱 「모은 자료」 화면에서 후보를 고르거나 직접 찾아 확정한다 →
  `PuOntology.validateCompanyLink` 로 검사 → `companyId`, `companyLinkStatus:'linked'`.
  확정은 `revision` 비교 트랜잭션으로 한다(두 사람이 동시에 눌러도 하나만).
- 확정 전 자료도 검색에는 나오되 «사업장 미확정» 으로 표시한다.

### 4-5. 실패 처리

- 메일 하나가 실패하면 그 메일만 `seen` 에 까닭을 적고 넘어간다. 다음 회차에 **다시 시도하지 않는 것**
  (보류·그림뿐)과 **다시 시도할 것**(연결 끊김·시간 초과)을 가른다 — 다시 시도할 것은 seen 에 안 적는다.
- 회차 요약(`run`)이 3일 연속 «담음 0, 오류 > 0» 이면 `systemAlerts/{관리자 uid}` 에 한 줄.
- 첨부 하나가 20MB(`ATT_MAX`)를 넘으면 받지 않고 보류.
- 지운 메일(404)은 «없어짐» 으로 seen 에 적고 끝.

### 4-6. 화면 — 「📥 모은 자료」 (목업 1·2 승인, 2026-10-03 「추천대로」)

새 앱의 첫 뼈대. 위쪽 줄에 마지막 모으기 요약(담음·보류·남은 메일·사업장 미확정·최종본·최종본 후보)과
관리자만 「지금 더 모으기」.

**보기 둘** (위쪽 버튼으로 바꾼다)

1. **메일 순** — 새로 온 것이 위. 메일 한 통 줄 아래에 그 첨부들을 묶는다.
   번호는 «모은 차례»(새것이 큰 수).
2. **사업장별 순서** — 회사·회차마다 규칙 본문을 날짜 차례로: 현행 0 → 1판 → 2판 … → 신고서.
   번호는 «회사 안의 판 순서». 회차 머리줄에 흐름 한 줄(현행→1판→…→신고서 ✉ 날짜)과 최종본 후보 근거.
   줄마다 «보낸 쪽(푸른/회사)» 과 «앞 판과 달라진 조 수» — 누르면 두 파일 견주기(`pu-rules-filecmp.js`)가 열린다.
   기본 차례는 «최종본 미정인 회사 먼저».

**맨 왼쪽 ☐ 고르기 + 번호.** 고르면 위에 일괄 단추: ★ 최종본으로 · 사업장 확정… · 갈래 고치기… · 고르기 풀기.
보류 줄은 고를 수 없다(담은 파일이 없다).

**★ 최종본**
- **한 사업장·한 회차에 하나.** 새로 고르면 앞의 것은 «이전 판»으로 내려간다(트랜잭션 — 둘이 동시에 눌러도 하나).
- 회차는 서버가 짚는다: 같은 사업장에서 «신고서 메일» 이 나오면 거기서 끊고, 6개월 넘게 메일이 없어도 끊는다.
  사람이 줄마다 회차를 고칠 수 있다(`round` 사람 칸).
- **후보는 서버가 짚고 확정은 사람**: 신고서·접수증 메일 바로 앞 판 / 파일 이름에 「최종·신고용」 /
  동의서와 같은 메일. 근거를 줄에 그대로 적는다.
- **직원 누구나** 정하고, 정한 사람·날짜가 줄에 보인다. 「풀기」로 되돌린다.
- **다음 덩어리(조문 색인·검토·문안 추천)는 최종본만 쓴다.** 최종본이 없는 회차는 색인에 안 들어간다.

**사업장 확정은 메일 단위로 한 번에** — 같은 메일의 첨부가 함께 확정된다. 다르면 파일 하나만 따로 고친다.
**보류 줄은 직원 전체가 본다** — 담은 것 없이 까닭·가린 셈만 있다.

오른쪽 칸: 사업장 후보(근거)·확정, 가린 글, 「메일 열기(원본)」·「가린 파일 받기」·「갈래 고치기」, 보류 까닭.
표의 칸은 한 줄(넘치면 … + title).

### 4-7. 규칙·배포

- 실시간DB 규칙은 `scripts/make-firebase-rules.js` 에 넣고 `node scripts/rules-deploy.js --deploy` 로 바로 올린다.
  보고에 «어느 칸이 누구에게 보이게 됐는지» 적는다(가린 글·목록이 직원 전체에게).
- 창고 규칙은 `docs/firebase-storage-전체(붙여넣기용).txt` 에 `rules_lib/` 를 넣고
  `node scripts/storage-rules-deploy.js --deploy`.
- 함수는 이름을 찍어 배포한다(`collectRulesMail`, `collectRulesMailNow`). 서울 지역, 1GB.
- kordoc 를 `functions/package.json` 에 넣는다 — 함수 묶음이 커지므로 다른 함수가 무거워지지 않게
  수집기만 따로 불러 쓴다(`require` 를 함수 몸통 안에서).

### 4-8. 검사

- 가짜 메일함·가짜 DB 로 **한 회차를 실제로 돌리는** 검사(메일 동기화 검사와 같은 방식):
  고르기 · 겹침 거르기 · 60통 한도 · 다시 시도 가르기.
- **진짜 kordoc** 로 가짜 한글 파일(홍길동 900101-1234567 · 가나상사)을 가려
  «DB·창고에 쓰인 바이트 어디에도 원래 번호가 없다» 를 본다. 남은 것이 있으면 아무것도 안 쓰는지도.
- 사업장 후보: 이름만 같은 회사는 후보가 안 되는지.
- 최종본: 한 사업장·한 회차에 둘이 생기지 않는지(동시에 두 번 눌러도), 풀면 되돌아가는지,
  회차 끊기(신고서 메일·6개월 공백), 후보 근거 셋. 사람 칸 밖(서버 칸)을 직원이 못 쓰는지(규칙 검사).
- 되돌려 보기(뮤테이션)로 검사가 실제로 우는지 확인.

### 4-9. 다 됐다고 보는 기준

## 4-10. 코드를 읽고 고친 것 (계획 쓰며, 2026-10-03)

1. **사람 칸을 따로 둔다.** 새 앱은 저장 관문(`pu-ontology-write.js`)이 enforce 다 — 물리 삭제 금지,
   레코드 통째로 revision 트랜잭션 저장. 서버 칸과 사람 칸을 한 레코드에 두면 서버가 덮을 때 사람 칸이 사라진다.
   - `rules_mgmt/library/human/{docId}` — `{id, entityType:'RulesDocument', companyId, companyLinkStatus,
     linkedBy, linkedAt, kindFix, round, …관문 칸}`
   - `rules_mgmt/library/rounds/{companyId}_{roundKey}` — `{id, entityType:'RulesRound', companyId, roundKey,
     finalDocId|null, finalBy, finalAt, …}`. **최종본은 이 한 칸**이라 «회차에 하나»가 저절로 지켜진다
     (트랜잭션 하나). 풀기 = finalDocId:null 로 저장(지우지 않는다).
   - `TERMS.entityTypes` 에 `RulesDocument:'취업규칙 서류'`, `RulesRound:'취업규칙 회차'` 를 더한다.
2. **회차·판 순서·최종본 후보는 화면 쪽 순수 모듈이 셈한다**(`js/rules-v2/lib-order.js`). 셈은 사업장 확정을
   딛고 서므로 서버가 미리 적을 수 없다. 서버는 근거 재료(갈래·날짜·보낸 쪽·메일 열쇠·파일 이름)만 적는다.
3. **서버도 브라우저와 «같은» kordoc 묶음과 `pu-kordoc-text.js` 를 쓴다** — `functions/vendor/kordoc/` 에 복사하고
   같은 바이트인지 검사가 본다. 가림 규칙이 한 벌이고, 무거운 npm 설치(onnx·sharp…)가 없다.
   이 묶음에는 PDF 부품이 없다 → **1판에서 PDF 는 보류**(「PDF — 아직 못 읽음」). 보류 수를 보고 다음에 정한다.
4. **「지금 더 모으기」는 새 공개 HTTPS 함수가 아니라 DB 신호로** — 관리자가 `rules_mgmt/library/ask/{id}` 를 쓰면
   데이터베이스 트리거가 돈다. 새 HTTPS 함수는 공개호출 권한을 콘솔에서 따로 열어야 해서 피한다.
5. 임시저장함·예약편지함은 고르지 않는다(보내지 않은 것).

## 5. 위험

- 서버에서 kordoc 가 메모리를 많이 쓸 수 있다 — 1GB 로 시작하고, 큰 첨부(ATT_MAX 초과)는 보류.

## 6. 덩어리 ② 조별 문안 + 두 앱 합치기 (2026-10-04 대표 승인 「추천대로」)

목업 1(찾기 결과 목록)은 대표 의견 「너무 혼란스럽지 않을까」로 버렸다 — 거의 같은 조가 회사 수만큼 줄지어
나오고, 다른 곳은 눈으로 찾아야 했다. 목업 2 «조별 문안 모음»과 «두 앱 합치기» 목업이 승인됐다.

### 6-1. 두 앱을 하나로

- 포털 타일은 **「취업규칙」 하나**(rules.html). 「취업규칙(새)」 타일은 걷는다 — 프로그램 등록은 남기고
  `portal:false`.
- 머리줄 왼쪽에 **세 갈래 단추**: ✏️ 검토·개정(rules.html) · 📚 조별 문안(rules-v2.html#topics) ·
  📥 모은 자료(rules-v2.html#lib). 같은 창에서 갈래만 바뀌고 뒤로가기로 돌아온다.
- 코드는 나뉜 채로 둔다(큰 파일을 키우지 않는다). 참고 서랍의 「문안 은행」·「조문 검색」은 그대로.

### 6-2. 조별 문안 (목업 2)

- 왼쪽: **조 주제** — 표준취업규칙 2026(`std_2026.js`)의 조 차례대로, 장 제목 아래. 걸린 회사 수를 곁에.
  표준에 없는 주제는 맨 아래 「그 밖의 조」. 찾기 칸은 주제 이름만 거른다.
- 자료: 「모은 자료」의 **규칙 본문 «담김» 전부**(★최종본 아닌 것도 — 지금 최종본 0건). 가린 글만.
- 오른쪽: 고른 주제의 문안을 **같은 글끼리 묶은 덩어리**. «같은 글» = 회사 이름·호칭(사원/근로자/직원/
  종업원)·띄어쓰기·조 번호·문장부호 띄움만 다른 것. 덩어리 대표 글은 호칭을 `{근로자}`, 회사 이름을 `{회사}` 로.
- 차례: **★최종본이 많은 덩어리 → 쓴 회사가 많은 덩어리 → 최근**.
- 맨 위 덩어리를 기준으로 아래 덩어리는 **다른 곳만 색칠**(`PuRulesFileCmp.wordDiff`)하고 한 줄 요약
  (「15일 → 12일」·「④ 덧붙임」).
- 덩어리마다 검토 기준을 돌려 **위반 의심이면 한 줄**(그 조에 걸린 것만).
- 단추: 📋 복사(대표 글) · 쓴 회사 보기(회사·조·판·날짜, ★표시) — 사업장 미확정은 「(미확정)」.
- 「비슷한 회사」·나란히 보기·옛 화면 연결은 ③(회사가 정해지는 개정 작업)으로.

### 6-3. 검토 기준 떼어 내기 (③ 에서 하려던 것을 앞당김)

조별 문안의 위반 표시에 판정이 필요하다. `rules.html` 안의 `RULES` 와 판정(`evaluate` 와 그것이 부르는
`applies`·`isFuture`·`bestHit`·`allHits`·`ncEval`·`RULES_OFF`)을 `js/pu-rules-criteria.js` 로 옮기고
**두 화면이 한 벌**을 싣는다.
- ⚠ **판정이 한 글자도 바뀌면 안 된다** — 옮기기 전 코드로 표준취업규칙(규모 넷)을 판정한 결과를 고정 자료로
  남기고, 옮긴 뒤 같은지 본다.
- `const RULES = [...]` 를 rules.html 에서 글자로 읽던 검사·스크립트는 새 파일을 읽게 고친다.

### 6-4. 성능

가린 글을 화면이 읽어 조로 쪼갠다(서버·규칙·저장 자리 늘지 않음). 읽은 글은 브라우저(IndexedDB)에 두고
문서 `updatedAt` 이 바뀐 것만 다시 받는다. 못 쓰면(사생활 창 등) 그냥 매번 받는다.

## 7. 덩어리 ③-ⓐⓑ 🏢 사업장 갈래 (2026-10-04 대표 승인 「추천」)

목업 `mockup-rules-v2-sites.html`(저장소 밖)의 세 물음은 모두 추천대로 정했다:
① 「취업규칙」 타일의 첫 화면은 **🏢 사업장**, ② 후보 확정은 **목록 줄에서 바로**,
③ 최종본이 없으면 **가장 최근 판으로 열고 「최종본 아님」을 알린다.**
③-ⓒ(우리 문안 추천·AI 다듬기)는 다음 덩어리다.

### 7-1. 갈래 넷

- rules-v2.html 의 갈래: `#sites`(🏢 사업장, **빈 주소의 기본**) · `#topics`(📚) · `#lib`(📥).
  `RV2_MODE`: `#topics`→topics, `#lib`→lib, 그 밖→sites.
- 머리줄 단추 넷(두 파일 같은 모양·차례): 🏢 사업장 · ✏️ 검토·개정 · 📚 조별 문안 · 📥 모은 자료.
- 포털 타일·앱바의 「취업규칙」은 `rules-v2.html` 로 간다(첫 화면 🏢). 프로그램 등록(`PROGRAMS.rules`)은 그대로 둔다.
- 틀 고정(#1888)과 같은 짜임새: 넓은 화면에서 거르개·표 머리는 서 있고 목록·이력이 제 상자에서 스크롤한다.

### 7-2. 사업장 목록 (순수 모듈 `js/rules-v2/lib-sites.js`)

- 대상: 업체관리(`data/companies`)의 `status` 가 `closed` 아닌 곳 + 닫힌 곳이라도 취업규칙 자료가 있는 곳.
- 열(한 줄씩): # · 사업장 · 규모 · 업태 · 취업규칙 자료 · 최근 · ★최종본.
  - 규모 = `employmentInsuredCount` 명 + 띠(5인 미만 · 5~9인 · 10~29인 · 30인 이상). 모르면 「—」.
  - 업태 = `bizType`.
  - 취업규칙 자료 = 「확정 n」(사람이 이은 문서) · 「후보 n」(아래) + 후보가 있으면 「✓ 이 회사 자료 맞음」.
  - 최근 = 그 사업장 자료(확정·후보)의 가장 늦은 메일 연월.
  - ★최종본 = 가장 최근 회차의 최종본 날짜(「★ 26-09」), 그 회차에 없으면 「미정」, 확정 자료가 없으면 「—」.
- **후보**: 사람 칸(human)이 `linked`·`not_required` 가 아닌 문서 가운데 서버의 `companyCand` 에 그 사업장이 든 것.
  후보는 메일마다 붙으므로 「✓ 이 회사 자료 맞음」은 «메일 단위로» 같은 메일의 첨부가 함께 확정된다.
  누르면 「가나상사 자료로 3건(메일 2통) 확정합니다」 확인 → 지금 있는 `S.linkCompany`(관문·`validateCompanyLink`).
  한 문서가 두 사업장의 후보이면 먼저 확정한 쪽으로 가고, 다른 쪽 후보 셈에서 빠진다.
- 거르개: 「취업규칙 자료 있는 곳」(확정 또는 후보 ≥1, **기본**) · 「확정 기다림」(후보 ≥1) · 「모든 거래처」. 칩에 셈.
  찾기: 회사 이름(띄어쓰기·㈜ 무시) · 사업자번호(숫자만 견줌).
- 차례: 후보 있는 곳 → 최근 자료가 늦은 곳 → 이름.

### 7-3. 오른쪽 — 그 사업장의 이력

- 머리: 이름 · 사업자번호 · 규모 · 업태.
- 「✏️ 이 사업장 개정 시작」 상자 + **어느 파일을 여는지** 한 줄(★최종본 / 최종본 아님 — 몇 판).
- 회차 카드(최근 회차가 위): 「2026-07 회차」·메일 n통·★최종본 정함/미정 · 흐름 한 줄(현행/n판 날짜 → … → 신고서 ✉ 날짜) ·
  서류 줄(이름 · 날짜 보냄/받음 · 「📥 에서 보기」 · 「✉ 메일」). 「📥 에서 보기」는 `#lib` 로 가서 그 줄의 오른쪽 칸을 연다.
- 후보만 있는 사업장: 이력 대신 후보 자료 목록과 확정 단추.
- 자료가 없는 사업장: 「📄 파일 올려 개정 시작」 → `rules.html#co=<companyId>`.
- 회차·판·최종본 셈은 「모은 자료」와 **같은 셈**(`PuRulesV2Order.companyGroups`)을 쓴다 — 두 화면이 다르게 말하지 않는다.

### 7-4. 개정 시작 — 원본을 메일에서 바로

- 고르는 판(`lib-sites.startDoc`): 규칙 본문(담김)이 있는 **가장 최근 회차**에서 ★최종본이 있으면 그것,
  없으면 그 회차의 가장 늦은 판 + `notFinal`. 규칙 본문이 하나도 없으면 단추 대신 「📄 파일 올려 개정 시작」.
- rules-v2 → `rules.html#open=<docId>`(최종본 아니면 `&nf=1`). 같은 창, 뒤로가기로 돌아온다.
- rules.html 이 받으면(새 공용 모듈 `js/rules-v2/mail-orig.js`):
  1. `rules_mgmt/library/docs/<docId>` 와 `human/<docId>` 를 읽는다(직원 읽기 — 이미 열린 자리).
  2. 메일에서 원본: 지금 메일함은 `readMailMessage{slug:box, uid:key}` 로 첨부 목록 → 이름이 같은 첨부를
     `readMailAttachment{slug,uid,index,part}` 로. 지난 메일(POP3)은 `readOldMail{key}` → `readOldMail{key,index}`.
     (서버 함수는 그대로 — 재직 직원이면 이미 부를 수 있다.)
  3. **받은 바이트의 sha256 이 문서의 `sha` 와 같을 때만 연다.** 이름이 같은 첨부가 여럿이면 차례로 받아 맞는 것을.
     하나도 안 맞으면 열지 않고 알린다(「메일의 첨부가 모은 때와 다릅니다」).
  4. 지금 있는 `loadFile(file, opts)` 로 연다 — `opts.site`·`opts.bizno` 에 확정 사업장의 이름·사업자번호를 넣어
     사업장 이름을 본문에서 짐작하지 않고, ERP 짝짓기가 사업자번호로 맞게 한다.
  5. `nf=1` 이면 원본 미리보기 위에 한 줄: 「⚠ 최종본 아님 — 이 회차의 가장 최근 판을 열었습니다」.
- ⚠ 원본이 옛 앱 보관함(`rules_mgmt/orig`)에 담기는 것은 **지금 손으로 파일을 올릴 때와 같다**(새로 생기는 길 아님).
- 실패: 메일이 지워졌거나(404) 서버가 못 받으면 「메일에서 원본을 못 받았습니다 — 📥 에서 가린 파일을 받거나 메일함에서 직접」.
- `rules.html#co=<companyId>`: 원본 위 한 줄 「가나상사 개정 — 파일을 올리세요」 + 다음 `loadFile` 에 그 사업장을 붙인다.

### 7-5. 늘지 않는 것

서버 함수·보안규칙·저장 자리·온톨로지 쓰기 선언 모두 그대로. 새 저장은 「✓ 이 회사 자료 맞음」(이미 있는 `linkCompany`)뿐.

### 7-6. 검사

- lib-sites: 대상(닫힌 곳 + 자료) · 규모 띠 · 후보 셈(linked·not_required 빼기, 두 사업장 후보) · 거르개 셈 · 차례 ·
