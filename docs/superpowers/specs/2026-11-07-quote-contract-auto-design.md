# 견적·계약 자동화 설계 (2026-11-07)

대표 권형하와 대화로 정한 것을 적는다. 「대표 결정」은 대표가 말한 것, 「설계 판단」은 Claude가 정한 것이다.
작업 방: 이 프로젝트는 문서관리 방에서 이알피(pu-erp.html) 코드까지 함께 고친다(대표 「이방에서」 2026-11-07, 이 프로젝트 한정).

## 1. 왜 하나

- 직원이 견적·계약서를 만들 때 매번 계약서등관리에서 서식을 찾아 채우고, 금액은 대표에게 묻는다.
- 그동안 보낸 견적서가 푸른 메일 보낸메일함에 흩어져 있어, 비슷한 일의 지난 금액·조건을 직원이 스스로 찾아볼 수 없다.
- 보낸 견적서와 들어온 최종 계약서가 이알피 계약관리와 따로 논다 — 손으로 다시 등록한다.

**성공한 모습:** 담당자가 「○○회사, 직원 30명, 직무분석 컨설팅, 3개월, 400만원」이라고 적거나 말하면 서류가 채워져 나오고, 옆에 같은 종류 지난 견적(내용·기간·인원·금액)이 보이며, 카톡으로 대표 검토를 받고, 담당자가 메일로 보낸다. 보낸 견적은 이알피에 계약협의로 저절로 올라가고, 서명된 최종 계약서가 오면 계약확정으로 저절로 넘어간다. 누가 언제 무엇을 했는지 모두 남는다.

## 2. 목표 / 안 할 것 / 실패로 볼 것

**목표**
1. 작업 기록: 계약서등관리에서 내용 넣기(서식·서류 수정)·내려받기·올리기·메일 발송·자동 등록·자동 확정을 모두 「누가·언제·무엇을」 남기고, 대표가 모아 본다(대표 결정 「가」).
2. 지난 견적 모음: 보낸 견적서·계약서를 업무 종류별로 모아, 한 건마다 날짜·의뢰처·업무 종류·금액·과업 내용·기간·인원(의뢰처 직원 수)·원본 파일을 보여 준다(대표 결정).
3. 서류 만들기 창: 글 또는 음성 설명 → 서식 선택·채우기 → 지난 견적 곁보기 → 보관 → 카톡 검토 요청 → 담당자가 확인하고 메일 발송(대표 결정).
4. 견적 → 이알피 계약협의 자동 등록: 서류 만들기 창으로 보낸 것과 푸른 메일에서 직접 보낸 것 **모두**(대표 결정 「모두 자동등록」).
5. 최종 계약서(서명본) → 이알피 계약확정 자동 전환(대표 결정).
6. 금액 공개 범위: 견적 금액과 계약확정 뒤 금액 모두 **대표·그 건의 담당자·총괄관리자·재무 담당**만 본다(대표 결정).

**안 할 것**
- 카톡 단톡방에 프로그램이 저절로 글·파일을 올리기(카카오가 막아 둠, 비공식 자동조작은 약관 위반 — 대표에게 설명함).
- 메일을 담당자 확인 없이 자동 발송(대표 결정: 담당자가 확인하고 보낸다).
- 사건 이관·청구 자동 시작(계약확정은 지금도 이관·출력 버튼만 열어 준다 — pu-erp.html:26226, 26750 — 그대로 둔다).
- 알림톡(사업자 채널·건당 요금, 별도 승인 사안).

**실패로 볼 것**
- 금액이 화면에서만 가려지고 데이터베이스에서는 직원 누구나 읽히는 것.
- 같은 회사·같은 업무 계약 카드가 자동 등록으로 겹쳐 생기는 것.
- 견적과 다른 금액·다른 회사로 계약확정이 저절로 되는 것.
- 비교견적서 요청 같은 남의 견적, 물품 견적(예: 루나랩 책상)이 우리 견적으로 등록되는 것.

## 4. 만드는 것 — 단계별

### 단계 0. 작업 기록 (먼저)
- 한 줄 = {누가 uid·이름, 언제, 무엇(종류: 내용수정·내려받기·올리기·메일발송·검토요청·검토완료·이알피등록·계약확정·자동감지), 대상(서식 id·파일 id·계약 id·메일 key), 한 줄 설명, 자동이면 무엇 때문에}.
- 계약서등관리의 내려받기·올리기·서식 저장·서류 만들기·메일 발송 지점마다 남긴다. 자동 처리(단계 3·4)도 남긴다.
- 대표(isAdmin)용 「작업 기록」 화면: 날짜·사람·종류로 거르기.
- 설계 판단: 쓰기는 누구나(자기 uid로만), 읽기는 isAdmin만. 지우기·고치기는 막는다(덧붙이기만).

### 단계 1. 지난 견적 모음 + 금액 잠금 자리
- 한 건(견적 기록) = {업무 종류, 의뢰처(이알피 회사 id 있으면 연결), 날짜, 과업 내용, 기간, 인원(의뢰처 직원 수), 담당자 uid, 원본 파일 id(🔒), 출처(창·메일 key), 이알피 계약 id}. **금액은 따로** 잠긴 자리에 {금액, 부가세 포함 여부}로 둔다.
- 잠긴 자리 읽기 규칙: isAdmin(대표·총괄관리자) ∨ fin ∨ 그 건의 담당자 uid. 다른 직원 화면에는 「금액 비공개」.
- 인원이 견적서에 없으면 이알피·기업정보함의 그 회사 직원 수로 채우고, 그것도 없으면 빈칸(직원이 채움). (설계 판단)
- 업무 종류 묶음(설계 판단, 지난 견적을 보고 조정): 노무자문, 인사노무 컨설팅(직무분석·규정정비·진단·인건비 원가산출), 산업안전 컨설팅, 직장 내 괴롭힘·성희롱 조사, 교육·강의, 임금·단체교섭, 사내·공동근로복지기금, 의견서, 사건 대리(위임).
- 처음 채우기: 보낸메일함(2026-08-05~)에서 우리 견적·계약 메일(견적서 약 24건, 자문·위임·용역 계약서 약 39건)을 단계 3의 감지기로 한 번 훑는다.
- 화면: 계약서등관리 안 「지난 견적·계약」 — 업무 종류별 목록, 한 건 펼치면 위 항목과 원본 열기.

### 단계 2. 서류 만들기 창
- 계약서등관리 어디서나 여는 버튼. 글 입력 + 🎤(크롬 Web Speech API, ko-KR).
- AI 판독(서버 Gemini)이 설명에서 {의뢰처, 업무 종류, 금액, 기간, 인원, 과업 내용, 원하는 서류}를 뽑는다 → 서식 고르기 → 기존 채우기 흐름으로 채운다. 의뢰처는 이알피 회사와 맞춰 본다(없으면 새 회사로 둔다 — 이알피 등록은 단계 3이 한다).
- 옆에 같은 업무 종류 지난 견적(내용·기간·인원·금액 — 금액은 볼 권한 있는 사람에게만).
- 담당자가 확인·수정 → 확정하면 보관(원본 보관함 🔒, 작업 기록).
- 「카톡으로 검토 요청」: 휴대폰은 Web Share API로 PDF를 붙인 공유 창 → 카카오톡 → 법인 단톡방. PC는 PDF를 받아 두고 폴더를 연다(끌어다 놓기). 서류마다 짧은 검토 번호(예: `Q-1107-3`)를 붙인다. 상태: 검토요청 → 검토완료(담당자가 누름) → 메일 보내기 열림. (설계 판단: 검토완료 전에도 대표·총괄관리자는 보낼 수 있다 [확인 필요])
- 메일: 받는 사람·제목·첨부가 채워진 메일 쓰기 창을 연다. 담당자가 「보내기」.

### 단계 3. 견적 → 이알피 계약협의 자동 등록
- 감지 두 갈래:
  1. 서류 만들기 창에서 보낸 견적 — 값을 이미 안다.
  2. 푸른 메일에서 직접 보낸 메일 — 보낸메일함 새 메일 중 제목·첨부 이름에 「견적」이 있고, 제외어(비교견적서 요청·견적 요청·견적의뢰·물품 견적 등)가 없는 것. 첨부(PDF·HWP·HWPX)를 `readMailAttachment`로 받아 AI 판독으로 금액·기간·과업·인원을 읽는다. 받는 주소로 이알피 회사를 찾는다. 담당자는 메일의 「누가 보냈나」 값, 없으면 대표에게 「누가」 고르기.
- 설계 판단: 감지는 서버(메일 동기화 뒤)에서 돌린다 — 누가 화면을 열지 않아도 된다. 결과는 견적 기록(단계 1) + `data/contract_requests`에 `{kind:'quote', state:'pending', …}`로 넣는다.
- 이알피 `runContractRequests`가 `kind:'quote'`를 받아 **계약협의(review)** 카드를 만든다. 같은 회사·같은 업무로 진행 중 카드가 있으면 새로 만들지 않고 그 카드에 견적을 덧붙인다. 회사 연결이 안 되면 `blocked` + 사유.
- 계약 카드에는 금액을 넣지 않는다(단계 5 전까지는 금액 칸이 직원 모두에게 읽히므로). 카드에서 견적 기록으로 링크.
- AI 판독이 금액을 못 읽거나 확신이 낮으면 「확인 필요」로 남긴다.

### 단계 4. 서명본 → 계약확정
- 신호: 전자서명 완료 저장(docs-esign.html:760~789) 또는 서명본 올리기(`gotAwait`).
- 그 서류의 `sourceContractId/No`(계약서등관리에서 계약을 골라 만든 경우)로 이알피 카드를 찾아 **계약확정(signed)** + 서명일. 이것도 `data/contract_requests`에 `{kind:'confirm', contractId, …}`로 넣고 이알피가 처리한다(설계 판단: 한 길로).
- 계약번호가 없거나, 계약서 금액이 견적 기록 금액과 다르거나, 회사가 다르면 확정하지 않고 「확인 필요」.
- 선택(단계 4b): 카톡정리가 모으는 법인 단톡방에서 대표의 「OK·승인 + 검토 번호」 글을 보면 검토완료로 바꾼다. 법인 단톡방이 KAKAO_ROOMS에 있어야 한다 [확인 필요].

### 단계 5. 이알피 계약 금액 잠금 (마지막, 조심)
- `data/contracts`는 한 덩어리라 규칙으로 금액 칸만 가릴 수 없다 → 금액(`amounts`, `successFee`)을 계약에서 떼어 잠긴 자리(계약 id별)로 옮긴다. 읽기: isAdmin ∨ fin ∨ 그 계약의 담당자(managerMain·managerSubs의 uid).
- 이알피 안 금액 쓰는 곳(약 25곳)을 잠긴 자리에서 읽게 고친다. 권한 없는 사람에게는 「비공개」.
- 기존 계약 금액을 한 번 옮긴다(옮기기 전 백업, 옮긴 뒤 합계 대조).
- 계약을 읽는 다른 화면(업무관리·사진첩·기업정보함·중진공 접수·재활광고·온톨로지·NAS 백업 내보내기)이 금액을 쓰는지 하나씩 확인한다.
- 규칙 바꾸기는 문안을 만들어 대표가 콘솔에 붙인다.

## 5. 지키는 것

- 실시간DB 규칙으로 막는다 — 화면 숨기기만으로 끝내지 않는다.
- 자동 처리는 모두 대기열을 거쳐 이알피의 기존 검증(회사 연결·중복·월 잠금)을 그대로 받는다.
- 공용 서식 원본은 고치지 않는다 — 채운 사본만 만든다.
- AI 판독은 서버 경유(열쇠를 브라우저에 두지 않는다). 무료 등급 한도에 걸리면 「나중에 다시」로 남기고 사람이 채울 수 있게 한다.
- 개인정보: 견적 기록에는 회사 정보만. 직원 개인정보를 담지 않는다.
- 다른 앱 화면 변경은 이 프로젝트에 필요한 만큼만.

## 6. 만드는 사람에게 맡기는 것

- 데이터 자리 이름과 모양, 화면 배치, 업무 종류 분류표의 세부.
- 감지기의 제외어 목록과 AI 프롬프트.
- 단계 안 작업 순서, 테스트 방식(이 저장소 관례: `tests/*.test.js`, node:test).

## 7. 검토 뒤 정한 것 (2026-11-07)

**대표 결정**
- 금액 숨김 범위: 이번에는 새로 만드는 자리(견적 기록·금액 잠금 자리·작업 기록)와 이알피 계약(단계 5)만 막는다. 푸른 메일 보낸메일함의 견적서 첨부·미리보기는 그대로 둔다(메일 앱 규칙은 안 고친다). `data/contract_requests`에는 금액을 담지 않는다.
- 금액을 보는 사람: 대표·총괄관리자(`isAdmin`)·그 건의 **확정된** 담당자·재무 담당(`fin`). 부관리자(`isSubAdmin`)는 뺀다(대표가 넣으라 하면 넣는다). 작업 기록 읽기도 `isAdmin`만.
- 보낸 사람 확인: 견적서·계약서는 **앱에서만 보낸다**(서류 만들기 창·자료 보내기 — 로그인한 직원이 기록된다, pu-cards.html 보낸 자료함 `by`). 다음 메일에서 직접 보낸 것은 본문 끝 **서명**(직원별 서명 고르기)을 읽어 「담당(추정)」으로 둔다. 다음 메일이 서명 여러 개를 지원하는지 [확인 필요] — 안 되면 받는 업체 담당자 짐작(지금의 「누가 보냈나」)만 쓴다.
- 서명본이 메일로 회신되는 경우: 받은메일함에서 서명본으로 보이는 메일(첨부 이름·본문에 계약서·서명, 보낸 주소가 견적 보낸 회사)을 찾아 「서명본 같음」으로 띄우고, **담당자가 한 번 눌러** 확정 대기열에 넣는다(자동 확정 아님). 전자서명·서명본 올리기는 단계 4대로 자동.

**설계 판단**
- 추정 담당자에게는 금액 권한을 주지 않는다. 대표·총괄관리자가 「담당 확정」을 누르면 그때 준다. 앱에서 보낸 견적은 보낸 직원이 곧 확정 담당자.
- 견적 길의 계약협의 카드는 사업자번호 없이도 만든다(지금 `ctReqWhy` pu-erp.html:25949가 막는 것을 `kind:'quote'`에만 푼다). 겹침은 회사 이름·메일 도메인으로 가린다. 사업자번호는 계약확정 때 필요 — 없으면 「확인 필요」. 업무 종류 → 이알피 `kinds`(consult·consulting·case·fund·other)로 옮겨 적는다(지금의 consulting 고정을 풀어).
- 이미 계약확정된 거래처에 다시 보낸 견적(재계약)은 기존 확정 카드는 두고 「재계약」 표시 새 계약협의 카드를 만든다(`erpContractDupBlock`을 `kind:'quote'` + 기존이 signed일 때만 예외). 옛 계약 종료는 사람이.
- 메일에서 감지한 견적 카드와 서명본 잇기: 담당자가 계약서등관리에서 위임·자문계약서를 만들 때 그 카드를 고르면(`ctxRef`) 계약번호가 붙는다. 계약번호 없는 서명본은 회사가 같은 계약협의 카드가 하나뿐일 때만 후보로 띄우고, 확정은 사람이.
- 지난 메일 첨부를 못 받거나 금액을 못 읽으면 「확인 필요」로 남기고 직원이 채운다(IMAP 폴더당 400통 한도 — functions/index.js:7524 — 때문에 POP3로 더 받는 일은 하지 않는다).
