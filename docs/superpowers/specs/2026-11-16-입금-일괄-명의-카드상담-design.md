# 입금 — 밀린 돈 일괄입금 · 분할 기록 · 명의가 다른 입금 · 카드 상담료 — 설계

- 날짜: 2026-11-16
- 요청: 대표 («재무관리에 입금될 때 …» 네 건, 2026-11-16)
  1. 몇 달 밀렸다가 한 번에 입금되는 경우를 자동으로 처리하게. 사업장 이름이 아닌 **다른 사람·다른 사업장 이름**으로 들어오면 어떻게 처리할지 명확히.
  2. **분할**해서 입금되는 것도 기록에 남기게.
  3. **신용카드로 낸 상담료**는 업무 기록이 정확히 남지 않는다 — 구체적으로 관리하는 시스템.
  4. (별도 문서) 세금계산서와 상관없이 정부 지원금을 받을 때 회계처리 → `docs/규칙/정부지원금-회계처리.md`
- 대상: `pu-erp.html`(거래내역 `FinanceLedger`·입금관리) — 단일 파일, ES5

## 2. 비어 있는 것 — 이번에 채운다

| # | 빈 자리 | 어떻게 보이나 |
|---|---|---|
| ① | **밀린 달이 많으면 못 맞춘다** — 합계 후보는 3건, 거슬러 보는 달은 3달 | 5달 치를 한 번에 내면 «더 들어옴»으로만 뜬다 |
| ② | 합쳐서 확정해도 **«한 번에 들어온 돈»이라는 연결이 안 남는다** | 8·9·10월 입금 세 줄이 따로 보이고, 같은 통장 줄에서 나왔다는 흔적이 없다 |
| ③ | 자문료 분할 입금의 **약정·받은·남은 이력이 기록에 없다**(합산해서 그때그때 계산만) | 「이 달 자문료는 언제 얼마씩 들어왔나」를 한눈에 못 본다 |
| ④ | **대납 관계를 적어 둘 곳이 없다** — 별칭은 «적요 → 업체 하나»뿐 | 대표 개인 계좌·계열사·대행업체가 대신 낸 돈은 매번 손으로 찾는다. 다른 사업장 이름이 찍혀 금액이 맞으면 **엉뚱한 곳에 붙을 위험**도 있다 |
| ⑤ | 상담료 직접 등록이 `consultId`(상담접수 번호)를 **저장하지 않는다**(`saveDirectIncome`) | 상담접수 카드에는 «얼마 받았나»가 남지 않고, 입금에는 «어느 상담인가»가 남지 않는다 |
| ⑥ | 카드 상담료의 **승인 정보(카드사·승인번호·승인일)** 와 **카드사 정산 입금**을 잇는 기록이 없다 | 승인일과 입금일이 다르고, 수수료 뺀 합계로 들어오면 어느 상담 몫인지 알 수 없다 |

## 3. ① 밀린 돈 일괄입금 — 규칙

**원칙: 돈이 걸린 결정은 사람이 한다.** (2026-08-09 설계서 §0 과입금 방침과 같다) 앱은 «찾고·제안하고·한 번에 처리»까지만 한다. 완전 자동 확정은 하지 않는다.

1. **어느 업체인가** — 적요 이름·신뢰된 별칭·**등록된 관계 입금자**(§4)로 업체가 «하나»로 정해질 때만 시작한다. 금액만으로는 시작하지 않는다.
2. **받을 달 목록** — 그 업체의 안 걷힌 달을 **오래된 달부터** 모은다. 거슬러 보는 한도는 **24개월**(계약 시작월·중단일 안쪽만). 업체 «한 곳»만 뒤지므로 전체 후보가 불어나지 않는다.
3. **채우는 순서** — 오래된 달부터. 입금액이 첫 달 남은 몫보다 크면 그 달을 채우고 다음 달로 넘어간다. 마지막 달이 모자라면 그 달은 **일부입금**(남은 금액이 계속 미수).
4. **정확히 맞으면**(±1,100원 = 기존 «확정 가능» 허용치) → 「N개월분 일괄 (5~7월)」 한 줄로 제안, 단추 한 번.
5. **모든 밀린 달을 채우고도 남으면** → 남은 돈은 «다음 달 미리 받음»으로 제안하되 **사람이 고른다**(기존 과입금 3갈래).
6. **일괄 확정 단추는 모두확정(⚡)에 넣지 않는다.** 줄마다 눌러야 한다.
7. 되돌리기: 같은 `lumpId` 의 줄은 **한 번에** 되돌린다(확정 이력).

### 기록 (§5 와 함께)
같은 통장 줄에서 나온 입금 줄은 모두 `lumpId` 를 공유한다.

```js
{ …기존 칸…,
  lumpId:'lp-…', lumpSeq:2, lumpN:3, lumpTotal:660000,   // 한 번에 들어온 돈
  bankRowKey:'…' }                                       // 통장 줄 지문(있을 때)
```

## 4. ② 명의가 다른 입금 — 한 장짜리 처리 기준

**입금자 이름을 네 종류로 나눈다.** 업체는 «계약 사업장»이고, 입금자는 «돈을 낸 사람»이다 — 둘은 따로 기록한다.

| 종류 | 어떻게 알아보나 | 자동으로 | 사람이 할 일 |
|---|---|---|---|
| **본인** | 사업장명·별칭(신뢰)·대표자·근로자 명단 | 지금 그대로(금액이 맞으면 🟢) | 없음 |
| **등록된 관계인** | 이 사업장의 «관계 입금자»로 등록(대표 개인·직원·계열사·세무대행…) | 🟢 가능하지만 **«대납(관계 등록됨)»** 딱지를 남긴다 | 없음 |
| **다른 사업장 이름** | 적요가 «다른 업체»와 ≥85% 닮음 | **막는다(🟡)** — 그 업체 자기 몫이 먼저 | 사유 선택(계열사·대표 겸직·대행·기타) + 관계 등록 여부 |
| **모르는 이름** | 어느 근거에도 없음 | **자동 확정 금지.** 금액이 «한 업체의 밀린 합계» 또는 «발행한 세금계산서»와 정확히 맞으면 **후보(🟡)** 로만 | 확인 후 사유 선택, 근거가 없으면 보류함 + 「직원에게 묻기」 |

- 입금 줄에 **`payerName`(실제 입금자) · `payerKind`(self/related/other_company/third) · `payerReason`** 을 남긴다. 매출·미수는 **계약 사업장**에 붙는다(세금계산서 상대와 같다).
- **관계 등록**은 «이 이름 → 이 사업장, 관계 ○○»를 `payer_relations` 에 한 줄 적는 것이다. **다른 사업장 이름으로 들어온 경우는 사람이 사유를 골라야 등록된다.** 한 번 등록하면 다음부터 «등록된 관계인»이다.
- ⚠ **CMS 통로 적요(더빌이체 등)는 관계로 등록하지 않는다** — 달마다 주인이 바뀐다(2026-09-15 건의). 기존 `erpIsCmsMemo` 를 그대로 쓴다.
- ⚠ 관계 등록은 **지울 수 있어야** 한다(잘못 등록하면 계속 같은 곳으로 끌려간다 — 별칭과 같은 교훈).

## 5. ③ 분할 입금 — 기록

- 자문료 입금 줄에 **`dueAmount`(그 달 약정) · `paidBefore`(그 전까지 받은 돈) · `remainAfter`(이 입금 뒤 남은 돈) · `splitSeq`(몇 번째 나눠 받음)** 를 남긴다. 합산으로 다시 계산해도 같은 값이 나와야 한다 — 기록은 «그때의 사실»이다.
- 사건·계약·컨설팅 `splitPayments` 는 이미 날짜·금액·종류·적요가 있다. 거기에 **`lumpId`** 만 더한다(§3).
- 화면: 입금 상세에 **「📥 이 달 자문료 입금 이력」**(날짜·금액·적요·남은 돈). 일괄로 들어온 줄에는 «5·6·7월 일괄» 딱지.
- 이미 쌓인 옛 기록은 건드리지 않는다. 읽을 때 없으면 계산해서 보여 준다.

## 6. ④ 카드 상담료 — 업무 기록

**한 가지를 기록으로 묶는다: 상담접수 카드 ⇄ 상담료 입금 ⇄ 카드 승인 ⇄ 정산 입금.**

1. 상담접수(`contracts` 의 `status:'consult'`)에 **`consultPayments[]`** 를 둔다.
   `{ id, date, amount, method:'card'|'account'|'cash', cardCompany, approvalNo, cardLast4, fee, settleDate, incomeId, by }`
   — **카드번호 전체·CVC 는 저장하지 않는다.** 끝 네 자리와 승인번호까지만.
2. 직접 등록(상담료)에서 상담접수를 고르면 **그 번호(`consultId`)를 입금 줄에 저장**하고, 상담접수 쪽에도 결제 한 줄을 남긴다(양쪽 연결). 지금은 팝업에만 넘기고 저장하지 않는다.
3. **카드 승인만 먼저 기록하는 길**(`💳 카드 상담료 등록`) — 정산 입금이 며칠 뒤에 오므로, 승인 때 «미정산 카드 상담료»로 먼저 남긴다.
4. **정산 입금 대사** — 통장에 카드사 정산(수수료 뺀 합계)이 들어오면, 미정산 카드 상담료 중 «승인일이 정산일 앞 N일 안»인 것을 합쳐 **합계 − 수수료**가 맞는 조합을 찾는다. 맞으면 한 번에 확정(§3 과 같은 `lumpId`), 수수료는 지출로(기존 `exp-cardfee`).
5. 상담접수 카드·입금 상세에 **«💳 카드 · 승인 12345678 · 11/14 · 정산 11/17»** 한 줄이 보인다.
6. **현금영수증·세금계산서·카드전표 중 증빙이 없는 상담료**는 목록에서 노랑으로 표시한다(증빙 누락 점검).

## 7. 안 만드는 것

- **완전 자동 확정**(일괄·대납 모두) — 돈 문제다.
- **다른 사업장 이름 → 자동으로 이쪽 사업장** — 절대 하지 않는다.
- 카드사·VAN 연동으로 승인 내역 자동 수집 — 파일 올리기·손 등록으로 충분하다(2026-08-09 §5 와 같은 판단).
- 옛 입금 기록 일괄 고치기 — 새 기록부터 남기고, 옛 것은 읽을 때 계산해서 보인다.
- 세금계산서 발행 자동화 — 이 설계 밖.

## 8. 검사 · 단계

각 단계는 **함수를 소스에서 떠서 실제로 돌리는** 검사(`vm`)를 쓴다(「되풀이된 실수 ②」). 값을 글자로 박지 않고 규칙(`≥24`, «오래된 달부터», «CMS 는 등록 안 함»)을 박는다. 쓰는 길마다 «짝»을 확인하고, 막는 코드를 일부러 망가뜨려 검사가 잡는지 본다.

## 9. 대표 확인이 필요한 정책 (AI 권장값으로 만들어 둔다)

1. 일괄입금 거슬러 보는 한도 **24개월** — 더 오래 밀린 곳은 미수금관리에서 따로.
2. **다른 사업장 이름**으로 온 돈 — 자동 확정 금지, 사유 선택 필수(권장).
3. 관계 등록은 **사람이 «계속 대납»을 고를 때만**(권장). 한 번 확정으로 자동 학습하지 않는다.
4. 카드 상담료 정산 대사 창 — 승인일이 정산일 앞 **7일** 안(카드사 정산 주기에 맞춰 조정).
