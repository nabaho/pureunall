# 컨설팅정산 앱 설계서

- 작성일: 2026-10-31
- 대상: 포털 «내부관리» 줄의 새 앱 `settle`(`pu-settle.html`) + 대표 PC 에서 도는 카톡 심부름꾼(`scripts/kakao-agent/`) + 재무관리 성과급 겹침 막기
- 대표 요청: 「내부관리에 컨설팅정산 항목을 만들고 프로그램 만들어달라. 사업마다 사업의 종류에 따라 개별정산이 필요하다.
  사업 관련해서는 푸른이알피에 확인하고, 개인입금되는 것들 중 개별정산이 필요한 것은 프로그램에서 정리하게」
  + 「카톡에 들어오는 내역 자동으로 체크하고, 통장에 입금된 것들 총금액을 합하고, 담당노무사에게 인센 배정」
  + 「담당자에게 카톡으로 자동으로 보내는 것까지」
- 경로: 건축급 — 새 앱 + 새 PC 프로그램 + 새 저장 규칙. 이 설계서 → 대표 승인 → 계획서 순.

## 1. 합의된 것

| 항목 | 내용 | 정한 때 |
|---|---|---|
| 목표 | 개인 통장으로 들어오는 정부사업 지급액을 사업장별로 모아, 주관(대표)과 담당노무사 사이의 차액 정산을 계산·기록·안내한다 | 대표 요청 |
| 포털 자리 | **«내부관리» 줄** (경력관리·재무관리·인사관리 옆) | 대표 요청 |
| 사업 범위 | 틀은 «사업 종류별 규칙»으로 범용, 이번에 넣는 규칙은 일터혁신(이알피 사업 종류 `cons-ilteo`) 하나 | 대표 선택 2026-10-31 |

| 정산 단위 | **지급월마다 그 달 입금분만** 따로 정산(1차·2차는 각각의 달) | 설계 — 기존 엑셀 방식과 같은 결과, §5.3 |

| 카톡 약관 위험 | PC 카톡을 프로그램이 조종하는 것은 카카오 약관상 계정 제한 위험이 있다(`docs/카톡수집기-검토.md` ㉮). **알고 진행** — 대화는 읽지 않고, 등록된 방에만, 대표가 누른 것만, 한 달 몇 통 | 대표 선택 2026-10-31 |

| 볼 사람 | 대표·위임관리인·재무권한자만(재무관리와 같은 권한). 담당노무사는 카톡으로 결과만 받는다 | 대표 선택 2026-10-31 |

## 2. 범위

넣는 것
- 비용지급 안내 엑셀 올리기(끌어 놓기) → 지급월·사람·업체·금액 읽기
- 업체·사람을 이알피 원본 ID(`consultings` id · `sid`)에 «사람이 한 번 확정» → 다음 달부터 저절로
- 사업 종류별 정산 규칙·요율(사람별, 사업장별 예외)
- 지급월 정산표(계산 → 확정), 송금 목록(누가 누구에게 얼마, «보냄» 체크), 이월·조정
- 담당노무사별 카톡 문구 만들기 → «카톡 발송» → 심부름꾼이 PC 카톡으로 보냄, 결과 기록
- 심부름꾼이 «카카오톡 받은 파일» 폴더를 지켜보다 새 비용지급 안내가 저장되면 포털에 «새 안내 도착»으로 올림
- 정산표 엑셀 내려받기
- 재무관리: 컨설팅정산 사업 종류의 개인수익 확정 때 성과급을 만들지 않고 까닭을 표시

넣지 않는 것 (v1 제외)
- 일터혁신 밖 사업의 규칙(틀만 둔다 — 대표가 규칙을 알려 주면 «규칙 방식»을 더한다)
- 담당노무사 본인 로그인 화면, 송금 자체(은행 이체), 담당노무사 개인 통장 자동 조회
- 카톡 «대화 내용» 읽기 — 카카오가 길을 주지 않는다(`docs/카톡수집기-검토.md`). 받는 것은 «저장된 파일»뿐
- 알림톡·카카오 API 발송(대표가 PC 방식을 골랐다)

## 3. 전체 구조

```
① 운영기관 담당자 → 대표 카톡으로 「비용지급 안내_…(~N월).xlsx」 (누적 파일: 지급월 열이 달마다 늘어남)
② 대표 PC 카톡에서 «저장/열기» → 카카오톡 받은 파일 폴더
③ 심부름꾼(scripts/kakao-agent)이 새 파일을 보고 읽어 settle/inbox 에 올림   ← 손으로 올려도 같다(앱에서 끌어 놓기)
④ 포털 «컨설팅정산» (pu-settle.html, 재무권한)
     안내 읽기 → 업체·사람 확정 → 지급월 정산표 계산 → 확정 → 송금 목록 → 카톡 문구 → «카톡 발송»
⑤ settle/kakaoQueue 에 보낼 것이 쌓임 → 심부름꾼이 1분마다 가져가 PC 카톡으로 보냄 → 결과를 그 줄에 기록
⑥ 재무관리(pu-erp.html)는 settle/rules 를 읽어, 맡겨진 사업 종류의 개인수익 확정에서 성과급을 뺀다
```

계산은 `js/pu-settle-core.js` 한 곳에서 한다 — 포털 화면과 심부름꾼(Node)이 같은 파일을 싣는다(전광판 `js/pu-signboard-core.js` 선례).

## 4. 포털 앱 `pu-settle.html`

### 4.1 포털에 들어가는 자리
- `enter.html` APPS: `{key:'settle', name:'컨설팅정산', row:'inside', perm:'fin', url:'pu-settle.html'}` — 새 권한 깃발을 만들지 않는다
  (새 깃발은 `portalLoadAppPerm`·`recordUidRole`·`roleGuard` 세 곳을 함께 고쳐야 하고, 이알피 로그인 때마다 지워진다).
- `js/pu-appbar.js` APPS, `js/pu-ontology.js` TERMS·PROGRAMS(`primaryRoots:['settle']`, writeContracts)·READ_ADAPTERS(`strategy:'in_app'`).
- 공통 틀은 전광판(`pu-signboard.html`)을 따른다 — pu-sid-guard·firebase compat·pu-ontology(+write, enforce)·PuGate·PuAppBar·PuWhoami·PuBack.
- 폰 점검 자료 `tools/phone-audit/seeds/settle.js`(지어낸 자료만).

### 4.2 화면 (탭 넷, 한 줄 탭)
1. **정산** — 지급월 목록(☐·№·지급월·사업 종류·사업장 수·상태·송금 남은 건) → 고르면 정산표
   - 정산표: 사업장별 묶음, 줄 = 사람(☐·№·사업장·구분(주관/담당)·이름·세전·원천징수·세후·통장 실입금(입력)·요율·몫·차액·조정·정산액·최종)
   - 위 숫자 상자: 세후 합계 · 담당 몫 합계 · 송금 건수/금액 · 확인 필요 건수
   - 단추: «확정» · «기록만(수기 정산 끝남)» · «엑셀» · «카톡 문구»
   - 송금 목록: 줄 = 보낼 사람 → 받을 사람 · 금액 · 사업장 · ☐ «보냄» (누가·언제 눌렀는지 남김)
2. **안내 파일** — 올린/도착한 안내 목록, 끌어 놓기 자리, 읽은 결과 미리보기, 업체·사람 확정 칸(후보는 이름으로 «보여만» 준다)
3. **규칙·요율** — 사업 종류별 규칙(방식·주관 sid·사람별 요율·사업장별 예외·켜짐/꺼짐), 이월·조정 목록
4. **카톡** — 사람별 채팅방 이름, 보낸 기록(☐·№·받는 사람·지급월·상태·시각·오류), 심부름꾼 마지막 응답(N분 전 경고)

폰에서는 표를 «두 줄 카드»로 편다(CLAUDE.md 폰 화면 절). 표의 한 칸은 한 줄, 맨 왼쪽은 ☐+번호, 입력칸 16px 이상, 27색 팔레트. 사번은 화면에 안 보인다.

### 4.3 상태와 지키는 것
- 정산표 상태: `draft`(계산만) → `confirmed`(확정) 또는 `manual`(기록만, 발송 안 함). 확정 뒤 고치려면 «확정 풀기» — 풀면 그 달 카톡 대기분은 취소된다.
- 확인 필요(요율 없음·업체/사람 미확정·주관 없음·세전 0)가 하나라도 있으면 확정할 수 없다.
- 같은 지급월이 새 안내 파일에서 금액이 달라지면 «바뀜» 딱지 — 확정된 달은 자동으로 덮지 않는다.
- 돈 기록은 지우지 않고 `_deleted` 표식(공용 관문).

## 5. 계산 (`js/pu-settle-core.js`)

### 5.1 안내 파일 읽기
- 머리줄: «컨설턴트»·«기업명» 칸이 있는 줄. «지급월» 병합 칸 아래 칸들이 지급월 열(예: `7월`, `9월 (10/2 지급)`, `10월`).
- 지급월 열쇠: 이름 앞의 «N월» + 연도. 연도는 파일 받은 날 기준, N월이 받은 달보다 크면 전년(화면에서 고칠 수 있다).
- 금액: 원 미만이 든 값 → 원 단위 반올림. 0·빈칸은 «그 달 지급 없음».
- 회차: 같은 줄에서 앞선 지급월에 금액이 있으면 2차, 없으면 1차.
- **사업장 명단**(설계 판단): 안내 파일에서 그 사업장 줄 가운데 «합계(세전)» 또는 어느 지급월이든 금액이 있는 사람. 배정 금액이 아예 없는 줄(합계 0·빈칸)은 뺀다.
  주관(`leadSid`)은 그 달 금액이 0 이어도 늘 그 사업장의 상대방으로 넣는다. 명단의 담당도 그 달 0원이면 0원 줄로 넣는다.
  까닭: `pool` 식은 선형이라 «달마다 따로 정산한 합» = «사업장 전체를 한 번에 정산한 값»(끝수 몇 원 차이)이 된다 — 주관·담당이 다른 달에 입금돼도 결과가 같다.
  그 달 명단 전원이 0원인 사업장은 그 달 정산표에 나오지 않는다.
- 이알피 `managerMain/Subs` 는 명단을 정하지 않는다 — 안내 파일(돈이 실제로 나간 기록)이 기준이고, 이알피는 ID 연결에만 쓴다.
- **2026년만**(대표 지시): 업체 연결 후보는 수행기간이 2026년에 걸친 `cons-ilteo` 컨설팅만 보여 준다.
- 읽는 자리를 못 찾으면 그 파일 전체를 «읽지 못함»으로 두고 아무것도 만들지 않는다.

### 5.2 규칙 방식 `pool`(일터혁신)
```
사람마다  소득세 = FLOOR(세전 × 3%, 10원) · 지방소득세 = FLOOR(소득세 × 10%, 10원) · 세후 = 세전 − 두 세금
          (통장 실입금을 넣으면 그 값이 세후를 대신한다)
사업장    T = 세후 합계
담당마다  몫 = FLOOR(T × 요율)  · 차액 = 몫 − 세후  · 정산액 = 차액 + 이월·조정
주관      정산액 = −(담당 정산액 합)   · 최종 = 세후 + 정산액
검산      사업장 최종 합 = T, 정산액 합 = 0
```
- 정산액 > 0 : 주관 → 담당 송금 · < 0 : 담당 → 주관 송금.
- 요율은 사업장별 예외 → 사람별 순으로 찾는다. 담당인데 요율이 없으면 «확인 필요».
- 주관은 규칙의 `leadSid` 한 사람. 한 사업장에 담당이 둘 이상이어도 같은 식(담당마다 몫, 주관이 나머지).
- 계산은 정수 원 단위로만 한다(소수 요율도 만분율 정수로 바꿔 곱한다).

### 5.3 기존 엑셀과 맞추기
지난 정산 엑셀(사업장 1곳 1차분)과 같은 입력이면 같은 정산액이 나와야 한다 — 검사에 지어낸 숫자로 그 식을 박는다.
연간 원천징수를 반으로 나누던 옛 방식과는 원 단위가 몇 원 다를 수 있다 — 지급월 방식이 «통장에 실제로 들어온 돈» 기준이라 이것을 쓴다.

### 5.4 이월·조정
- 줄 = 사업 종류·사업장·사람·금액(부호는 정산액과 같은 뜻)·내용. 그 사업장·사람이 들어 있는 **다음 확정 정산표**에 한 번 붙고, 붙은 정산표 id 를 남긴다.
- 확정을 풀면 다시 «안 붙음»으로 돌아간다.

### 5.5 카톡 문구
담당노무사마다 한 통: 머리 «[사업 이름 N월 입금분 정산 안내]» → 사업장마다 세전·원천징수·세후, 사업장 세후 합계 × 요율 = 몫, 정산(누구에게 얼마) → 합계 → 맺음말.
머리·맺음말은 규칙에 적어 고칠 수 있다. 계좌번호는 넣지 않는다.

## 6. 저장 자리 (실시간DB 새 최상위 `settle`)

| 자리 | 내용 | 쓰는 쪽 |
|---|---|---|
| `settle/rules/{typeCode}` | 방식·leadSid·요율(`rates{sid:pct}`·`siteRates{consultingId:{sid:pct}}`)·문구·켜짐 | 앱 |
| `settle/links/{company\|person}/{key}` | 안내 파일 이름 → 확정 ID(consultingId·companyId / sid) | 앱(사람이 확정) |
| `settle/notices/{id}` | 읽은 안내(파일 이름·받은 때·지급월·줄) — 파일 자체는 두지 않는다 | 앱·심부름꾼 |
| `settle/runs/{id}` | 지급월 정산표(계산 결과 스냅숏·상태·송금 목록·보냄 기록) | 앱 |
| `settle/adjusts/{id}` | 이월·조정 | 앱 |
| `settle/rooms/{sid}` | 카톡 채팅방 이름 | 앱 |
| `settle/kakaoQueue/{id}` | 보낼 카톡(받는 sid·방 이름·글·상태·시도·오류) | 앱이 만들고 심부름꾼이 상태를 고침 |
| `settle/agent` | 심부름꾼 마지막 응답·모드 | 심부름꾼 |

- 모든 줄은 `id`·`entityType`·`createdAt`·`updatedAt`(공용 관문). 사람은 `sid`, 사업장은 이알피 `consultings` id + `companyId` 로 잇는다 — 이름은 «안내 파일에 적힌 글»로만 둔다.
- 보안 규칙(만들개 `scripts/make-firebase-rules.js`): 읽기·쓰기 `LOGIN && (ADMIN || SUB || FIN)`, 지우기 금지(쓰기는 `newData.exists()`), `settle/agent` 는 서버 CLI 전용(규칙상 쓰기 없음).
  - **`settle/kakaoQueue`·`settle/rooms` 쓰기는 `ADMIN` 만**(설계 판단) — 대표 카톡 이름으로 나가는 글이라 위임관리인·재무권한자는 정산표까지만 다루고 발송 대기열엔 못 넣는다.
    대기열 줄은 새로 만들기만(`!data.exists()`), 상태 칸은 심부름꾼(CLI)만 고친다.
  `tests/perf-rules.test.js` allowTop 에 까닭과 함께 넣는다. **재무관리(fin)보다 넓게 열지 않는다.**
- 재무관리는 `settle/rules` 만 읽는다(같은 권한이라 새로 열리는 사람이 없다).

## 7. 카톡 심부름꾼 `scripts/kakao-agent/`

- Node(전광판 심부름꾼과 같은 뼈대: config·store·run·main·install-task.ps1). 포털 자료는 **이 PC 에 로그인된 firebase CLI** 로 읽고 쓴다 — 서비스 계정 키는 만들지 않는다.
- 설정은 저장소 밖 `%APPDATA%\pureun-kakao-agent\config.json`: 지켜볼 폴더 목록, 파일 이름 꼴(`비용지급 안내*.xlsx`), `liveEnabled`(기본 false).
- **보내기**: 1분마다 `settle/kakaoQueue` 의 `pending` 을 가져와 PowerShell(Win32 호출)로 PC 카톡에 넣는다.
  - 받는 방 창이 열려 있으면 그 창, 없으면 카톡 메인 창의 채팅 검색칸에 방 이름 → 열린 창의 제목이 방 이름과 **똑같을 때만** 보낸다(카톡 창 제목의 특수 공백 `\xa0` 은 보통 공백으로 보고 견준다). 다르면 보내지 않고 `failed`.
  - 보내기 전 확인: 방 이름이 `settle/rooms` 에 등록된 것이고, 줄의 `runId` 가 확정(`confirmed`) 정산표이며, 줄을 만든 사람이 관리자일 것. 하나라도 어긋나면 보내지 않는다.
  - 입력칸에 글을 넣고 Enter → 입력칸이 비었는지로 «나갔다»를 판단.
  - 창 메시지(`WM_SETTEXT`·`PostMessage`)로만 넣는다 — 마우스·키보드를 뺏지 않아 대표가 그 PC 로 일하는 중에도 섞이지 않는다. 화면이 잠긴 때에도 되는지는 첫 시험에서 확인 [확인 필요] — 안 되면 `pending` 으로 두고 «화면 잠김»을 적는다.
  - 도는 PC: 지금 카톡이 로그인된 대표 PC(카톡 PC판은 한 대만 로그인된다). 받은 파일 폴더도 그 PC 것을 지켜본다.
  - 시험 모드(기본)는 카톡을 건드리지 않고 `outbox/` 에 보낼 글만 적는다. 같은 줄은 3번까지 시도.
  - 방을 열면 그 방의 안 읽은 글이 읽음이 된다 — README 에 적는다.
- **받기**: 지켜볼 폴더에 새 안내 파일이 생기면(이름 꼴 + 수정 시각) `vendor/xlsx.full.min.js` 로 읽어 `settle/notices` 에 올린다(같은 파일 해시는 한 번만).
- PC 카톡이 켜져 있고 로그인돼 있어야 한다. 꺼져 있으면 `failed` 가 아니라 `pending` 으로 두고 «카톡이 꺼져 있음»을 `settle/agent` 에 적는다.
- 자동 시작(작업 스케줄러 로그온 시)은 스크립트만 주고, **등록은 대표 확인 뒤**에 한다.
- 이 폴더는 배포본에서 지워진다(공개되지 않는다).

## 8. 재무관리 성과급 겹침 막기 (`pu-erp.html`)
- 이알피가 켜질 때 재무권한자면 `settle/rules` 를 읽어 «켜진 규칙의 사업 종류» 모음을 둔다.
- 개인수익 성과급이 생기는 길은 **둘**이다 — 둘 다 막는다(설계 판단):
  ① 입금확정 저장의 개인수익(`isPersonalRev`) 갈래, ② 개인↔법인 다시 열기 `personalReclassPatch`(일괄 창 포함).
  원본 컨설팅의 사업 종류가 그 모음에 있으면 `perfShares` 를 비우고 «🧾 컨설팅정산에서 개별정산» 표시를 남긴다. 막는 판단은 한 함수로 모아 두 길이 함께 부른다.
- «법인 매출»로 확정하는 길은 그대로 둔다 — 그것은 돈이 법인에 들어온 경우라 보통 성과급이 맞다.
- 이미 만들어진 성과급은 건드리지 않는다(돈 기록 자동 변경 금지) — 화면에 «겹칠 수 있음» 경고만.
