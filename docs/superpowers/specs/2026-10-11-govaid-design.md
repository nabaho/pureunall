# 정부지원금(govaid) — 설계서

- 작성: 2026-10-11 · 상태: **설계 승인됨(대화), 설계서 검토 대기**
- 대표 지시: 「정부지원금 프로그램 만들려고 한다」 → 「고객사 뿐 아니라 신규고객사에게도 검토 후 지원받을 수 있는 것 연계 예정」
- 시안: 대화에서 보낸 `mockup-gov-subsidy*.html` (저장소에는 두지 않는다 — 문지기 규칙)

## 1. 무엇을 하나

정부 지원사업을 **사전**으로 두고, 사업마다 **지원 조건을 구조화**해 두면,
**기존 고객사와 예비(신규) 고객사**마다 «받을 수 있어 보이는 사업» 후보를 자동으로 뽑는다.
후보는 판단 재료일 뿐이고, **해당·보류·비해당은 노무사가 누른다.** 저장되는 것은 그 결정뿐이다.

«연계»(실제 신청·안내·대행)는 이 판의 범위가 아니다 — 자리만 남긴다(9절).

### 결정된 것 (대화에서)

| 물음 | 답 |
|---|---|
| 대상 | 기존 고객사 + 예비(신규) 고객사 |
| 검토 방식 | 조건을 구조화 → 후보 자동 도출 → 사람이 확정 |
| 앱 위치 | 새 프로그램(A안). 정부사업신청(gov.html)은 손대지 않는다 |
| 1판 화면 | ① 회사 중심 · ② 한눈 표 · ④ 사업 중심 + 사업 사전 · 확인할 조건 |
| 미룬 화면 | ③ 상담 즉석(신규 고객 상담 중 실시간 후보) → 2판 |
| 쓰는 사람 | **노무사(직원) 전원** — 조건 확정까지 누구나. 누가 했는지 남긴다 |

## 3. 자료 (RTDB `govaid/`)

모든 레코드는 공용 관문(`js/pu-ontology-write.js`) 규칙을 따른다:
`id`·`entityType`·`schemaVersion`·`contractVersion`·`createdAt`·`updatedAt`·`revision`,
지우기는 `_deleted`·`deletedAt`·`deletedBy`(물리 삭제 없음), 수정은 `revision` 비교 트랜잭션.

### 3-1. 지원사업 `govaid/programs/{id}` — entityType `SupportProgram`(신규)

| 칸 | 뜻 |
|---|---|
| `name` | 사업명(전문) |
| `agency` | 담당기관 — `고용노동부`·`중소벤처기업부`·`특허청`·`과학기술정보통신부`·`기타` 등 |
| `fields[]` | 분야 꼬리표 — `산업·일자리전환`·`사업전환`·`디지털 전환(사업전환)`·`디지털 전환(디지털)` |
| `summary` | 지원내용 한 줄 |
| `cond` | 조건(3-4절) |
| `status` | `draft`(초안) · `confirmed`(확정) |
| `baseYear` | 조건이 맞는 해(예: 2026) |
| `confirmedAt` · `confirmedBy`(sid) | 확정한 때·사람 |
| `source` | `{title, no, url, page}` 공고 근거 — 모르면 비움(지어내지 않는다) |
| `seedRow[]` | 캡처의 원래 번호(예: `[67,31]`) — 출처 추적용 |

### 3-2. 예비 고객 `govaid/prospects/{id}` — entityType `Organization`

`name` · `bizno`(사업자번호, 있으면) · `industry` · `region` · `headcount` · `yearsInBiz` · `memo` ·
`companyId`(계약해 업체관리에 생기면) · `companyLinkStatus`(`TERMS.companyLinkStates` — 처음엔 `pending`).

- 업체관리 원장(`data/companies`)에 **넣지 않는다**(원장 밖 회사는 원장에 안 넣는다는 기존 결정).
- 원장 업체와 잇는 것은 `PuOntology.validateCompanyLink` 로 검증한다. **이름이 같다고 잇지 않는다.**
- 이어진 뒤에도 예비 고객 레코드는 지우지 않는다(검토 기록이 그 id 를 가리킨다). 화면에서는 원장 업체로 합쳐 보인다.

### 3-3. 보충값 `govaid/extras/{subjectKey}` · 검토 `govaid/reviews/{subjectKey}/{programId}`

`subjectKey` = `co_{companyId}`(기존 고객사) 또는 `pr_{prospectId}`(예비 고객).

- **보충값** — 원장·국민연금에 없는 사실만 담는다: 정년 제도 유무, 매출 감소율, 만 60세 이상 인원 등
  (3-4절 `facts`). 값마다 `{v, at, by}`. **원장에 있는 값의 사본을 두지 않는다.**
- **검토** — entityType `EligibilityReview`(신규): `decision`(`yes`·`hold`·`no`) · `reason` · `by`(sid) · `at` ·
  `snapshot`(결정 당시 엔진이 본 조건별 판정 — 나중에 조건이 바뀌어도 «그때 왜 해당이었나»가 남는다).

### 3-4. 조건 모양 `cond`

```js
cond = {
  headcount:  { min: 5, max: null },          // 상시 근로자 수
  yearsInBiz: { min: null, max: 7 },          // 업력(년)
  sizes:      ['sme','priority'],             // 중소·중견·대·우선지원대상 — 비면 제한 없음
  regions:    [],                             // 시·도 — 비면 전국
  industries: { include: [], exclude: [] },   // 업종 대분류 — 비면 전체
  facts:      [{ key:'retireAgePolicy', want:true, label:'정년 제도 있음' }],
  manual:     ['경영상 이유로 고용조정이 불가피할 것']   // 사람만 판단
}
```

- `facts` 의 `key` 는 **정해진 목록**에서만 고른다(엔진 파일에 둔다) — 자유 입력하면 사업마다 이름이 갈라져 보충값과 안 맞는다.
- 숫자는 «이상/이하»만. 「~명 미만」 같은 표현은 확정하는 사람이 정수로 바꾼다.

## 4. 사업장 값은 어디서 오나

| 값 | 기존 고객사 | 예비 고객 |
|---|---|---|
| 이름·사업자번호·주소(→지역) | `data/companies` 원장 | 예비 고객 레코드 |
| 상시 근로자 수 | `pucards/coInfo/{번호}/nps` 의 지금 값(국민연금, 매달 2일 갱신) — 고른 회사만 있음 | 직접 입력 |
| 업종 | 원장 업태·종목은 글이라 대분류로 자동 변환하지 않는다 → **보충값에서 사람이 고름** | 직접 입력 |
| 업력·규모·`facts` | 보충값 | 예비 고객 레코드·보충값 |

- 화면은 값마다 **출처 꼬리표**(원장·국민연금·직접 입력)를 붙인다.
- **값이 없으면 «모름»이다. 0 으로 두지 않는다.**
- `[확인 필요]` 원장 주소 칸 이름과 `coInfo` 의 업체 번호 잇는 법(`data/companies` 의 어느 칸)은 계획 단계에서 코드로 확인한다.

## 5. 엔진 `js/pu-govaid-match.js` (순수 함수)

```
judge(profile, program, today) → { verdict, items:[{key,label,state}] }
  state   : 'ok' | 'no' | 'unknown' | 'manual'
  verdict : 'candidate'(후보) | 'unknown'(정보 부족) | 'no'(안 맞음) | 'unconfirmed'(조건 미확정)
```

규칙:
1. `status !== 'confirmed'` 이거나 `baseYear < 올해` → `unconfirmed`. **해가 바뀌어도 자료를 고쳐 쓰지 않는다** — 계산에서만 초안으로 본다.
2. 조건 하나라도 `no` → `no`.
3. 아니고 하나라도 `unknown` → `unknown`(무엇을 알면 되는지 `items` 로 알려 준다).
4. 나머지 → `candidate`. `manual` 조건은 후보여도 «사람 확인» 표시로 붙는다.
5. 사업장 값이 `null`·`undefined`·빈 글자 → `unknown`. **0 은 값이다**(0명은 «0명»).
6. 엔진 결과는 저장하지 않는다 — 검토 결정의 `snapshot` 에만 그때 결과를 담는다.

## 6. 화면 `pu-govaid.html`

공통: 목록 맨 왼쪽 ☐ + 보이는 순서 번호(저장 안 함) · 표 칸은 한 줄(넘치면 `…` + `title`) ·
색은 5색군 팔레트만(파랑=확정·기존, 호박=확인 필요·예비, 초록=후보·해당, 빨강=안 맞음, 회색=안내) ·
폰 입력칸 16px 이상 · `pu-active.js`(유휴 로그아웃) · 한 앱 한 창.

| 탭 | 내용 |
|---|---|
| ① 회사 중심 | 왼쪽 회사 목록(기존·예비 함께, 찾기, + 예비 고객) → 오른쪽: 사업장 값(출처 꼬리표) / ✅ 후보 / ❓ 정보 부족(입력 단추) / ▸ 안 맞음(접힘) / 각 줄 해당·보류·비해당 + 사유 |
| ② 한눈 표 | 줄=회사, 칸=사업. ● 후보 ◐ 정보 부족 · 안 맞음, 초록 바탕 = «해당» 확정. 후보 없는 사업 열 숨김. 칸을 누르면 조건 비교 작은 창에서 검토 |
| ④ 사업 중심 | 왼쪽 사업 목록(후보 회사 수) → 오른쪽 그 사업의 후보 회사 / 정보 부족 회사 + 검토 |
| 📚 사업 사전 | 사업명·분야·기관·조건 요약·상태·기준연도·확인일. 찾기·기관·분야·상태 거르기. + 사업 더하기 |
| ⏳ 확인할 조건 | 초안(및 지난해 확정) 사업을 한 건씩: 조건 칸 입력 + 근거 + «확정(올해 기준)» |

## 9. 1판에서 하지 않는 것

③ 상담 즉석 화면 · AI 조건 초안 단추(공고 원문 → 조건) · 안내문·메일 보내기 · 정부사업신청 공고와 잇기 ·
신청 대행 진행 관리(단계·서류·수수료) · 업종 글 → 대분류 자동 변환 · 「연계」 기록.

## 10. 위험과 막이

| 위험 | 막이 |
|---|---|
| 지난해 조건으로 «해당»을 안내 | 해가 바뀌면 계산에서 초안 취급(5절-1) + 검토 `snapshot` |
| 모르는 인원을 0으로 보고 «안 맞음» | 엔진 규칙 5 + 검사 |
| 이름이 같은 다른 회사를 이음 | 예비 고객 → 원장 연결은 `validateCompanyLink` 만, 이름 맞추기 금지 |
| 지원 요건을 지어냄 | 씨앗은 조건 없이 draft, `source` 모르면 비움, 확정은 사람 |
| 다른 사업을 합침 | 씨앗 합치기는 분야만 다른 «같은 이름» 20쌍만(그중 기관이 다른 #54↔#10 은 기관을 비우고 `[확인 필요]`), 이름이 잘린 클라우드 두 줄은 합치지 않음 |
