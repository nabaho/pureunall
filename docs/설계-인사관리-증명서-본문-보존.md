# 설계안 — 인사관리 증명서를 발급할 때 «본문 사본»을 남기기

> **상태: 설계안(초안) — 대표 결정 대기.** 이 문서는 구현도, 보안규칙 배포도 아니다. 승인 전에는 `pu-erp.html`·`scripts/make-firebase-rules.js` 를 고치지 않는다.
> 작성: 2026-11-14 · 발단: PR #3025(경력관리 «푸른인사관리에서 재직증명서 당겨오기»)가 «본문이 없어서» 기록만 가져온다는 한계를 남겼다.
> 읽은 곳(모두 이 저장소 코드): `pu-erp.html` 증명서 모듈(`saveLog`·`printCert`·`downloadHTML`·`sendCertMail`·`renderCertContent`·`CertLog`), `dbSet`/`DIFF_KEYS`, `scripts/make-firebase-rules.js`, `functions/index.js`(`sendPayslip`), `functions/staff-claim.js`, `docs/firebase-storage-전체(붙여넣기용).txt`, `js/pu-ontology.js`, `tests/hr-stage0.test.js`, `kcareer.html`·`js/kcareer-hrcert.js`.

## 0. 대표님께 한 장 요약

- **지금**: 인사관리는 증명서를 발급(인쇄/PDF·HTML 저장·메일)할 때 «누구에게·언제·무슨 용도로»만 발급대장에 남깁니다. **발급된 문서 그 자체(본문)는 어디에도 남지 않습니다.** 그래서 경력관리가 가져올 수 있는 것은 «발급 기록»뿐이고, 파일은 사람이 다시 붙여야 합니다.
- **추천**: 발급하는 순간의 본문을 **발급대장과 같은 사람(재무 권한자·관리자·위임관리인)만 읽는 새 칸**에 «새로 쓰기만»(고칠 수 없게) 남기고, 경력관리는 대표 본인 줄의 본문을 읽어 **PDF 를 자동으로 만들어 줄에 붙입니다.**
- **여쭐 것(§8)**: ① 본문을 남길지 ② 보관 기간 ③ 직인 그림을 사본에 넣을지 ④ 옛 발급분 처리 ⑤ 읽을 수 있는 사람의 범위.
- **하지 않은 것**: 규칙 변경·배포, 인사관리 코드 변경, 증명서 발급(인쇄/PDF)·저장·삭제.

## 1. 지금 어떻게 되어 있나 (읽은 사실)

| 무엇 | 사실 | 근거 |
|---|---|---|
| 발급 때 남는 것 | `saveLog(method, recipient)` 가 `data/cert_log` 에 한 줄: `id`·`certNo`·`submitTo`·`recipient`(받는 메일)·`issuedAt`·`kind`·`targetSid`·`targetName`·`targetTitle`·`purpose`·`issuedBy`·`contactName`·`method`. 취소는 `canceled`·`canceledAt`·`canceledBy` 표시만(줄은 안 지움). | `pu-erp.html` `saveLog`·`CertLog` |
| 부르는 길 셋 | 인쇄(`printCert`, 본문 = `#cert-preview` 의 `innerHTML`) · HTML 저장(`downloadHTML`, `outerHTML`) · 메일(`sendCertMail`, `html2canvas`+`jsPDF` 로 PDF 를 만들어 `sendPayslip` 으로 보냄). 셋 다 끝에 `saveLog` 만 부른다. | 같은 모듈 |
| 본문은? | **남지 않는다.** 줄에 본문·변수 칸이 없다. 발급 화면에서 고른 «발급일»(`issueDate`)·«담당업무»(`dutyInput`)·«생년월일»(`birthInput`)·주소/퇴직사유 포함 여부(`incAddr`·`incReason`)도 안 남는다. | `saveLog` 필드 목록 |
| 메일 서버에는? | 메일 함수(`sendPayslip`)는 보낸 뒤 `id`·`to`·`by`·`from`·`replyTo` 만 돌려주고 **PDF 사본을 저장하지 않는다.** 보낸 메일 서비스(Resend) 쪽에 사본이 남는지는 **확인하지 못했다.** | `functions/index.js` `sendPayslip` |
| 저장 방식 | `cert_log` 는 `DIFF_KEYS`(건별 저장 표)가 **아니다** → `dbSet('cert_log', 배열)` 로 **배열 통째** 저장(`data/cert_log = {v:[…], u}` 봉투). 줄마다 본문을 넣으면 발급할 때마다 전체가 다시 쓰인다. | `pu-erp.html` `DIFF_KEYS`·`dbSet` |
| 읽기·쓰기 권한 | `cert_log: { '.read': HRW, '.write': HRW }` — HRW = 재무 권한자·관리자·위임관리인. 이름 없는 `data/<열쇠>` 는 `$other` 로 떨어져 «재직 직원 누구나 읽고 쓰기»다 → **새 열쇠는 규칙을 먼저 달지 않으면 직원 전체에게 열린다.** | `make-firebase-rules.js`, `tests/hr-stage0.test.js` ⑤ |
| 크기(측정) | 가짜 환경(지어낸 자료·기본 직인)에서 재직증명서 미리보기 `#cert-preview` `outerHTML` = **7,560자(UTF-8 7,830바이트)**, 그중 직인 그림(data URL) 3,754자 → 직인을 빼면 약 3.7KB. **실제 법인 직인(`company_info.stampDataUrl`, 올린 그림)의 크기는 측정하지 못했다**(실제 자료는 대표 화면에서만 읽을 수 있다) — 직인이 크면 사본이 수십 KB 로 커질 수 있다. | 임시 미리보기 서버 실측(저장소 밖, 발급·저장 없음) |
| 창고(Storage) | 로그인 증표에 새겨진 구분은 `staff:true` 하나뿐 → **창고 규칙은 «직원이냐»까지만 가린다. «발급대장을 읽는 사람(HRW)»을 가릴 수 없다.** | `functions/staff-claim.js` 머리글 |
| 경력관리 | 대표 전용 앱. 로그인한 직원(`sid`)의 `cert_log` 줄만 읽어(읽기 전용) 보관함 기록을 만든다 — 파일이 없다. | `js/kcareer-hrcert.js` |

**관찰(고칠 일은 아님)**: 미리보기의 «제 PU-…호»(`renderCertContent`)와 발급대장의 `certNo`(`saveLog`)는 «그해 줄 수 + 1» 을 각자 그때 센다. 보통 같지만, 그 사이 다른 기기가 발급하면 종이의 번호와 장부의 번호가 어긋날 수 있다. **본문 사본은 «종이에 찍힌 번호»를 그대로 남기므로** 어긋나면 드러난다 — 사본을 남기는 부수 이득이다.

## 4. 추천안 상세

### 4-1. 자리·모양
- 경로: **`cert_docs/{logId}`**(최상위 — `data/` 밑이 아니다. `data/<열쇠>` 는 `{v,u}` 봉투·통째 저장·로컬 캐시 길이라 건별 노드와 안 맞는다). `logId` = `cert_log` 줄의 `id`(`cl-…`) — 발급 이력과 1:1.
- 모양(초안):
  `{ v:1, certNo, kind, sid, html, vars:{…}, stampKey, templateVer, at, by }`
  - `html`: 발급 순간 `#cert-preview` 본문. **직인 `<img src="data:…">` 는 `data-stamp` 표시로 바꿔 뺀다**(§4-4).
  - `stampKey`: 그때 쓴 직인의 짧은 해시(어느 직인이었는지만).
  - `sid`: 대상 근로자의 사번(사람은 `sid` 로 잇는다 — 온톨로지 규칙).
- 크기 한도: `.validate` 로 `html` ≤ 약 60KB 같은 한도를 둔다(숫자는 실제 직인·서식 측정 뒤에 정한다).

### 4-2. 쓰는 때
`saveLog` 가 부르는 «세 길 모두»에서, 발급 순간 한 번(같은 함수에서) 사본을 만든다 — 길마다 따로 만들면 한 길이 빠진다. 사본을 못 남겼다고 발급을 막지는 않되, 발급대장 줄에 `docSaved:false` 를 남겨 «사본 없음»을 숨기지 않는다.

### 4-3. 규칙(초안 — 승인 전에는 파일에 넣지 않는다)
```js
/* ══ 증명서 발급본(cert_docs) — 읽기는 발급대장(cert_log)과 «같은 사람» ══ */
rules.cert_docs = {
  '.read': HRW,
  $id: {
    // 새로 쓰기만(고칠 수 없다) · 지우기는 관리자만(보유기간 뒤 파기)
    '.write': `(${HRW} && !data.exists() && newData.exists()) || (${ADMIN} && data.exists() && !newData.exists())`,
    '.validate': "$id.matches(/^cl-[A-Za-z0-9_-]{1,40}$/) && newData.hasChildren(['v','certNo','kind','sid','html','at','by'])",
    html:  { '.validate': "newData.isString() && newData.val().length <= 60000" },
    certNo:{ '.validate': "newData.isString() && newData.val().length <= 24" },
    $other: { '.validate': false }   // 이름 없는 칸은 막는다
  }
};
```
(위는 모양 설명용 초안이다 — 한도 숫자·칸 목록은 실제 직인·서식을 측정한 뒤 정한다. 구현할 때는 `tests/hr-stage0.test.js` ⑤ 처럼 «새 칸도 이름이 있고 직원 누구나 쓰기(`$other`)로 떨어지지 않는다»를 지키는 검사를 같이 만든다.)

**어느 칸이 누구에게 보이게 되나(CLAUDE.md 가 요구하는 보고)**
- **새로 «생기는» 자료**: 발급한 증명서 본문(성명·생년월일·직위·입사일·담당업무·용도·제출처·법인 정보). 지금은 어디에도 없다.
- **읽는 사람**: `cert_log` 와 같은 HRW(재무 권한자·관리자·위임관리인) — **넓어지지 않는다.** 대표만으로 좁히려면 `SS_OWNER`(= `staff_secret` 방식)를 쓴다(§8-5).
- **쓰는 사람**: HRW, 새로 쓰기만. **지우는 사람**: 관리자만.
- 기존 칸(`cert_log` 등) 규칙은 **바꾸지 않는다.**

### 4-4. 직인
직인은 `company_info.stampDataUrl`(올린 그림)이고 `company_info` 는 직원 전체가 읽는 칸이다. 사본 본문에 그림을 넣으면 발급마다 같은 그림이 복사되어 커진다. **그림은 빼고 `stampKey`(해시)만 남기며**, PDF 를 만들 때는 그 시점의 직인을 입히되 해시가 다르면 «발급 당시 직인과 다름»을 화면에 알린다(§8-3 에서 대표 확인).

### 4-5. 소급 불가
이미 발급된 줄은 본문을 되살릴 수 없다(그때 화면이 사라졌다). 경력관리 창은 이런 줄을 «본문 없음 — 인사관리에서 다시 발급하거나 PDF 를 붙이세요»로 계속 구분한다.

### 4-6. 보관·파기·접근 기록
- 본문에는 성명·생년월일이 있다 → **보유 기간을 정하고(§8-2) 지날 때 관리자가 지우는 길**이 필요하다. 주민등록번호는 현행처럼 **절대 넣지 않는다**(생년월일만).
- 열람 기록이 필요한지: 주민번호 금고(`staff_secret`)는 고시상 접속기록 때문에 `_log` 를 두었다. 생년월일만 있는 사본에도 같은 수준이 필요한지는 **확인이 필요하다**(§8, §9).

### 4-7. 경력관리 쪽 바뀜(승인 뒤)
- `kcareer-hrcert` 가 `cert_docs/{logId}` 를 같이 읽어 줄에 «본문 있음/없음»을 보여 준다.
- «넣기» 때 본문이 있으면 HTML → PDF(이미 쓰는 `jsPDF` + 화면 그리기 도구)로 파일을 만들어 줄에 붙인다(이 PC 보관함 + 창고, 지금 «📎 붙이기»와 같은 길). 해시가 다르면 직인 안내.
- 읽기 전용·sid 매칭·중복 방지·개인정보 최소 원칙은 그대로.

### 4-8. 등록·백업
- 온톨로지: 최상위 새 칸이라 `PuOntology.PROGRAMS.hr` 의 소유 뿌리에 올려야 한다(`staff_secret` 이 `erp` 에 올라 있는 방식). `tests/ontology-registry.test.js`·`ontology-contract.test.js` 가 코드가 쓰는 뿌리와 맞춘다. 새 레코드는 `id`·`entityType`·`createdAt`·`updatedAt` 을 갖춘다.
- 서버 백업 목차에 새 칸이 들어가는지는 **확인하지 못했다**(`functions/nas-backup-export.js` 가 `HR_DATA_KEYS`/`data/…` 뿌리만 보는지 따로 봐야 한다) [확인 필요].

## 5. 실행 순서(승인 뒤)
1. **규칙 먼저**: `make-firebase-rules.js` 에 `cert_docs` → 규칙 검사(에뮬레이터) → `rules-deploy.js`(사라지는 규칙이 있으면 스스로 멈춤) → 무엇이 누구에게 보이게 됐는지 보고. 클라이언트보다 규칙이 먼저 올라가야 «새 칸이 직원 전체에게 열리는» 순간이 없다.
2. 인사관리 `saveLog` 에서 사본 쓰기(세 길 공통) + 발급대장 `docSaved`.
3. 경력관리 읽기·PDF 붙이기.
4. 검사: 규칙 모양(HRW·새로 쓰기만·`$other` 금지), 세 길 모두 사본이 남는지, 사본이 실패해도 발급대장은 남는지, 경력관리가 sid 가 다른 사본을 안 읽는지, 직인이 사본에 안 들어가는지.
5. 실제 발급 시험은 «사람이» 한다 — 이 작업은 로그인된 인사관리에서 발급·저장을 하지 않는다.

## 6. 하지 않기로 한 것·미룬 것
- `cert_log` 줄 안에 본문 넣기(배열 통째 저장 — 성능·충돌).
- 창고(Storage) 파일(읽기 범위를 발급대장 수준으로 좁힐 수 없음 — 새 증표 구분이 먼저).
- 옛 발급분의 본문 복원(불가능).
- 연봉증명서(임금 정보)·발급 취소 기능 변경.

## 7. 위험·열린 문제
- **직인 실제 크기 미측정** — 한도 숫자는 측정 뒤.
- **서식이 바뀌면** 변수만으로는 옛 문서를 못 만든다 → 본문 HTML 을 남기는 이유. `templateVer` 를 함께.
- **HRW 범위**: 재무 권한자도 본문(성명·생년월일)을 읽게 된다. 지금 발급대장도 같은 범위라 «넓어지지는 않는다»지만, 본문은 생년월일이 있다는 점이 다르다 → §8-5.
- **법적 근거·보존 기간 [확인 필요]**: 근로기준법의 사용증명서 조항(제39조로 알고 있다)과 서류 보존 조항(제42조·같은 법 시행령 제22조로 알고 있다), 개인정보 보호법의 보유기간·파기 조항을 **법제처 원문으로 확인하지 못했다**(이 환경의 법령 조회 도구에는 인증 키가 없고, 법제처 사이트가 점검 중이었다). 담당 노무사가 원문과 사실관계(발급 사본이 보존 대상 서류에 드는지)를 확인하기 전에는 보유 기간을 정하지 않는다.
- 보낸 메일 서비스(Resend)에 사본이 남는지 **확인 못 함** — 남아 있어도 우리 쪽 «기록»이 아니다.

## 8. 대표님께 여쭐 것
1. **본문 사본을 남길까요?** (예 → 이 설계 / 아니오 → 현행 유지: 발급할 때 PDF 를 직접 저장해 «📎 붙이기»)
2. **얼마나 보관할까요?** (퇴직 후 몇 년 — 법적 근거 확인 뒤 정함)
3. **직인 그림은 사본에 넣지 않고 «어느 직인이었는지(해시)»만 남겨도 될까요?** (PDF 를 다시 만들 때는 그때의 직인으로 입히고, 달라졌으면 알려 줍니다)
4. **지금까지 발급한 증명서는 어떻게 할까요?** (본문은 되살릴 수 없습니다 — 필요한 건 다시 발급해 새 방식으로 남길 수 있습니다)
5. **누가 읽을 수 있게 할까요?** (발급대장과 같은 «재무 권한자·관리자·위임관리인» / 대표만)
