# 정부사업신청 → 공고별 지원 작업함

## 사용 흐름
1. 정부사업신청의 ‘지원할 만한 것’ 또는 컨설턴트 모집 글에서 **☑ 지원**을 누른다. 공고 모아보기의 서류 버튼도 같은 입구다.
2. 경력관리에서 해당 공고의 지원 작업함을 연다. 같은 공고는 기존 작성본을 이어 연다.
3. 지원자 본인 계정의 경력·학력·자격·실적을 근거로 신청서·이력서·자기소개서·수행계획서 초안을 만든다. 관련 경력 선택과 문장을 수정할 수 있다.
4. 공개 공고 본문·붙임 목록을 읽고, 지원하는 한글·PDF·워드 붙임(최대 5개, 파일마다 8MB)을 자동으로 가져온다. 한글 양식은 기존 칸 지도 엔진으로 알려진 칸과 선택 경력을 채워 사본으로 보관한다.
5. 자동 읽기에 실패하거나 그림·ZIP·기관 로그인 등이 필요하면 공고문·양식을 직접 추가하거나 본문을 붙인다. 필요서류의 빠진 항목은 수동으로 추가한다.
6. 보완 목록에서 누락된 정보·서류·확인 사항을 본다. 보유 증빙은 원본과 기간을 대조해 ‘파일 연결’에서 고른다.
7. 초안과 생성된 한글 양식은 담당자가 수정·검토한다. 기관 양식 편집기는 기존 편집기를 그대로 사용한다. AI 자기소개·계획 초안 정리는 별도 버튼으로 실행한다.
8. ‘서류 묶음 내려받기’로 초안, 채운 양식, 선택 증빙, 공고정보, 보완 목록을 ZIP으로 받는다. 읽지 못한 원본 파일은 첨부확인 목록에 남긴다.

## 완료 판단
- 초안 생성·파일 연결만으로 준비 완료를 표시하지 않는다.
- 지원자격, 공고·붙임의 필수서류 전체 목록, 증빙 유효기간·서명·동의, 최종 검토는 담당자가 확인한다.
- 증명서 발급·서명·동의 체크·기관 제출은 자동 실행하지 않는다.
- 한글 자동 채움이 모르는 칸, 서술형 문항의 기관 지정 양식 반영, PDF·워드 양식은 편집기에서 확인한다. 주민번호·계좌·도장을 자동으로 넣지 않는다.
- 현재 경력관리의 **기존 본인 계정 권한**을 따른다. 담당자가 다른 계정으로 대표의 개인 자료를 열도록 권한을 확대하지 않았다. 수정 가능한 초안·ZIP으로 검토를 이어갈 수 있다.

## 저장과 개인정보
- `kcareer/{uid}/applicationPacks/{id}`: 본인 전용 지원 준비. 공용 저장 관문의 revision 트랜잭션 사용.
- 원본 경력·실적에는 쓰지 않는다. 공고의 sourceKind/sourceId와 선택 경력의 원본 ID를 유지한다.
- 빈 배열을 생략하는 실제 RTDB 응답을 읽을 때 목록을 복원한다.
- 파일은 기존 IndexedDB 및 본인 전용 `kcareer_forms/{uid}` 창고를 재사용한다. 창고 업로드 실패 시 이 기기에서만 사용할 수 있으며 다른 기기에서는 파일 추가가 필요하다.
- 자문·고문 고객사명은 기존 `KcareerAdvSummary`로 가린 뒤 초안·양식·AI 재료로 사용한다. AI에는 선택한 경력과 최소 프로필만 전달하고 주민번호 가림 도구를 거친다.
- 공고 안의 명령은 분석 자료로만 취급한다. 서버는 기존 공고 수집 호스트의 HTTPS GET만 허용하고 사설 IP·인증정보·비표준 포트·무제한 이동·대용량 응답을 차단한다. 기관 쿠키·로그인정보를 보내지 않는다.
- 원문·초안·첨부 경로는 통합 색인으로 내보내지 않는다(`in_app`).

## 검증
- 지원 작업함 단위 검사: 사실 근거, 미확인 정보, 고객사 가림, 빈 DB 응답, 동시수정, 공용 한글 엔진, 공개 URL 경계.
- 기존 정부사업신청 전달 검사: 제목만 URL로 넘기던 고정값 검사를 ID·제목·원문·계정의 전달 동작 검사로 확장.
- 가짜 Firebase 화면: 정부사업신청→경력관리, 자동 공고·붙임 읽기, 복수 한글 양식 채움, 저장·재열기, ZIP 안의 생성 파일·보완 목록 검증. 진짜 서버에는 쓰지 않는다.
- 서버 함수 `govApplicationRead`는 프런트와 별도로 지정 배포해야 한다. 배포 전에도 자동 읽기 실패 안내와 파일 추가 경로는 사용할 수 있다.
