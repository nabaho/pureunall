### P박스 — 이미 수파베이스를 쓰도록 짜인 곳 (2026-11-16 점검)

앞 글들은 «수파베이스를 쓰는 곳이 아직 없다»는 전제였고, 위 규모 재기도 파이어베이스만 셌다. 그런데 P박스(`pu-pbox.html`, 11-14~16 병합)는
수파베이스 무료 요금제를 «공유 DB»로 쓰도록 이미 짜여 있다(표 설계 `docs/pbox-supabase-schema.sql` · 서버 중계 `functions/pbox-sync.js` ·
화면 `js/pu-pbox-store.js`). 위치는 서울이다(대표 확인 2026-11-16, 수파베이스 대시보드 값은 못 봄).
안티그래비티(`antigravity:gemini-4-argon-high`)의 검증과 직접 확인을 합친 결과다.

**지금 상태: 켜져 있지 않다**

- 배포된 서버 함수(`pboxApi` · `pboxDailySync`)에 수파베이스 주소·서버용 열쇠 환경변수가 없다(이름만 확인, 값은 보지 않았다).
  화면에도 «공유DB · 보관 N편» 대신 «무료 무제한»이 보인다.
- 수파베이스 프로젝트·표를 만들었는지는 [확인 필요 — 수파베이스 대시보드]. 켜려면 표를 만든 뒤 주소·열쇠를 서버 함수에 넣고 다시 배포해야 한다.

**구조**

- 실제로 쓰는 길: 서버 함수가 서버용 열쇠로 `pbox_documents` 표 한 개만 읽고 쓴다. 브라우저는 수파베이스에 직접 붙지 않는다 —
  5절 후보 «Cloud SQL + 우리 서버 함수»와 같은 틀이다(DB 만 수파베이스).
- 표 5개 중 `pbox_documents` 만 코드가 쓴다. 나머지(`pbox_laws` · `pbox_projects` · `pbox_sync_state` · `pbox_active_staff`)와 검색 함수는 쓰지 않는다.
  들어가는 자료는 공개 법률 자료와, 직원이 비식별 확인 뒤 공유한 문서뿐이고 고객 자료 표(`pbox_projects`)는 쓰지 않는다.

**고칠 곳**

1. 브라우저 직접 연결(설정 창에 직원 증표 입력)은 이어지지 않는다. 표 규칙이 `app_metadata.staff` 와 `pbox_active_staff` 명부를 요구하는데
   파이어베이스 증표에는 없고 명부를 채우는 코드도 없다. 요청 머리글(`apikey`)에도 프로젝트 공개 키가 아니라 직원 증표를 넣는다 —
   수파베이스는 이 칸에 프로젝트 키를 기대하므로 막힐 가능성이 크다 [시험 필요]. 서버 중계만 실제 길이다.
2. 서버가 수파베이스 연결 값을 못 찾아도 «성공»(`ok: true`, `skipped: true`)으로 돌려준다. 공유가 안 됐는데 된 것으로 보일 수 있다 [화면 표시는 시험 필요].
3. 무료 요금제 한계: DB 500MB 권장(판결 전문과 본문 글자 색인이 크다) · 거의 안 쓰고 7일이 지나면 자동 일시정지 ·
   매일 백업은 Pro 부터 · 내려받기 월 5GB · 한도를 넘으면 읽기 전용·정지(공식 공정 사용 정책).
   공유 문서를 여기에만 두면 잃었을 때 되살릴 길이 없다.
4. 표 바꾸기는 대시보드에 SQL 을 붙여 넣는 방식(올리개 없음)이고, 온톨로지에는 `localOnly:true` 로만 등록돼 있다 —
   앞 글(11-07) 7절의 조건(올리개 · 온톨로지 계약 먼저 · 백업)과 어긋난다.
5. (작은 것) 서버 함수 주석은 «실시간DB에 아무것도 쓰지 않는다»고 하지만 요청 간격 확인에 실시간DB 쓰기가 있다.

**이 글과의 비교**

- 앞 글들의 «수파베이스는 새 회사가 하나 늘어난다»는 P박스가 켜지는 순간 이미 사실이 된다. P박스는 공개 자료가 중심이라 부담이 작지만,
  직원이 공유하는 «비식별 내부 문서»가 들어갈 수 있어 0은 아니다 [담당 노무사 확인].
- P박스는 «본문 검색이 많은 큰 공개 문서»라서 실시간DB 보다 PostgreSQL 이 맞는 사례다. 급여 아웃소싱은 반대로 민감 자료이므로
  무료 요금제로는 안 된다 — Pro 이상 + 백업(앞 글 7절 6번).
- 이 점검은 앞 글 5절의 «SQL Connect CDN 시험»을 대신하지 않는다(P박스는 브라우저 직접 연결을 쓰지 않는다).

## 2. 옮기면 무엇이 어떻게 바뀌나

| 지금(파이어베이스) | 수파베이스에서는 | 어려움 |
|---|---|---|
| 실시간DB(JSON 나무) | PostgreSQL 표. 약 100묶음 이상을 표로 다시 설계 | **큼** — 공식 이전 도구가 **없다**(수파베이스 커뮤니티 도구는 로그인·Firestore·창고·함수만 다룬다) |
| 한 번 받기 `.once` | 표 조회(PostgREST) 또는 서버 함수(RPC) | 중간 |
| 계속 듣기 `.on` | Realtime — 변경 알림(Postgres Changes) 또는 방송(Broadcast) | 중간~큼 |
| 동시 수정 `.transaction` | DB 안의 함수(`plpgsql`)에서 잠그고 고치기 | 중간 |
| 보안규칙 2,286줄 | 행 단위 권한(RLS) + 열 권한 | **큼** |
| 로그인: 비밀번호 | 이전 도구가 있다(Firebase scrypt 해시 가져오기) | 작음~중간 |
| 로그인: 카카오 | 수파베이스 기본 카카오 로그인, 또는 자체 서명 증표 | 중간 |
| 로그인: 지문 | passkey 는 **«실험 기능»**(공식 표기). 기존에 등록한 지문을 가져오는 길이 문서에 없어 **모두 다시 등록**으로 본다 | 중간~큼 |
| 로그인: 익명 | 익명 로그인 있음(권한에서 «익명»을 따로 가려야 한다) | 작음 |
| 재직자 표시 `staff` | 증표 만들 때 표시를 붙이는 훅(Custom Access Token Hook) | 중간 |
| 사용자 번호(uid) | **전부 새로 생긴다** → `uid_roles` · `sid` 연결표를 다시 맞춘다 | 중간 |
| 서버 함수 140 | Edge Functions(Deno). 일부는 파이어베이스에 남기는 혼합도 가능 | **큼** |
| 예약 39 | pg_cron(공식 문서 있음) | 중간 |
| 자료 변경 때 도는 함수 10 | 표 트리거 + 필요하면 웹훅 | 중간 |
| 창고 3곳 | Supabase Storage (이전 도구 있음). **저장된 주소가 모두 바뀐다** | 중간 |
| 푸시(FCM) · 앱 확인(App Check) | **대응 없음** → 파이어베이스 프로젝트가 남는다 | — |
| 규칙 올리개 `rules-deploy.js`(사라질 규칙이면 멈춤) | 표 바꾸기 비교 도구를 새로 짓는다 | 중간 |
| 온톨로지 계약(`PuOntology`) | `writeContracts` 를 표 쓰기에 맞게 다시 | 중간 |

## 5. 어떤 문제가 생기나 (무거운 순)

1. **움직이는 표적.** 11-07 이후 9일 동안 main 에 합쳐진 커밋이 454개(병합 제외 283개)이고 열린 PR 이 15건이다.
   옮기는 동안 «옛 길 구현»과 «새 길 구현»을 둘 다 고치거나, 기능을 멈춰야 한다. 이것이 기간을 가장 크게 늘린다.
2. **자료 모양을 바꾼다.** JSON 나무를 표로 풀 때 `data/<표>` 를 «통째 덮어쓰는» 자리 · 안쪽 경로가 변수인 자리 약 50곳 ·
   종료·이관·취소·마감·휴지통 상태를 되살리지 않는다는 규칙(2026-11-11)을 DB 가 지키게 다시 짜야 한다.
3. **보안이 «기본 닫힘»에서 «표마다 켜야 열림/닫힘»으로 바뀐다.** RLS 를 표마다 켜야 하고, **한 번만 빠뜨려도 공개 키로 읽힌다.**
   이 저장소는 공개이고 여러 방(AI)이 표를 만든다. 주민번호·계좌 같은 «칸 단위 비밀»은 RLS(행 단위)로는 못 가려서 별도 표나 열 권한이 필요하다.
4. **실시간이 다르게 움직인다.**
   - 지금 `.on('value')` 는 «현재 전체 + 이후 변화»를 준다. 수파베이스 Realtime 은 «변경 알림»만 주므로 «처음 읽기 + 구독» 두 단계가 된다.
   - 삭제 알림에는 **권한(RLS)이 적용되지 않고**(공식 문서), 삭제 알림에 옛 값을 받으려면 표 설정(`replica identity full`)이 필요하다.
   - 변경 알림은 한 줄 처리(단일 스레드)이고 구독자마다 권한을 검사한다 — 같은 변경을 3,000명 넘게 구독하면 방송(Broadcast)으로 바꿔야 한다.
5. **동시 수정 120곳.** 파이어베이스 `transaction` 은 «읽고-고치고-쓰기를 한 번에»를 해 준다. 표에서는 DB 안의 함수(잠금) 또는 «판 번호가 같을 때만 고치기»로 다시 짠다.
6. **로그인.**
   - 카카오·지문은 지금 서버가 파이어베이스 증표를 직접 만든다. 같은 이름의 «증표 직접 발급» 기능은 수파베이스 문서에서 찾지 못했다 —
     기본 카카오 로그인으로 바꾸거나, 자체 서명(프로젝트 비밀키 관리 부담)을 한다.
   - **지문 로그인은 수파베이스에서 아직 «실험 기능»**이고, 기존 등록 지문을 가져오는 길이 문서에 없어 근로자·직원이 모두 다시 등록해야 할 것으로 본다.
   - 사용자 번호가 모두 새로 생겨 `uid`·`sid` 연결을 다시 맞춰야 한다 — «사람 이름으로 맞추지 않는다» 규칙 때문에 연결표를 만들어야 한다.
   - 서버에 보내는 증표 약 100자리가 파이어베이스 증표에서 수파베이스 증표로 바뀐다.
7. **서버 함수(Deno 제한).** 요청당 CPU 2초 · 메모리 256MB · 함수 크기 20MB · 바깥으로 나가는 포트 25·587 막힘 · `sharp` 같은 다중 스레드 부품 불가(공식 문서).
   우리 메일은 465·993·995 를 써서 포트는 괜찮으나, 메일(IMAP·SMTP)·PDF·지문 검증 부품이 Deno 에서 도는지는 [시험 필요].
8. **창고 주소가 깨진다.** 문서·서명본·사진에 저장된 창고 주소가 모두 바뀐다. 옛 주소를 읽는 자리를 한동안 남겨야 한다.
9. **파이어베이스를 완전히 떠나지 못한다.** 푸시(FCM)와 앱 확인(App Check, 약 100곳 언급)은 수파베이스에 없다. 두 벤더를 계속 관리한다.
10. **병행 운영 중 자료가 어긋날 위험.** «어디서든 데이터가 지워지면 안 된다»(2026-10-07)를 지키기 가장 어려운 기간이다.
11. **개인정보·청구.** 수탁자인 우리가 처리를 다시 맡기는 회사가 늘어 고객사 재위탁 동의가 필요하다(개인정보 보호법 제26조 제6항, 원문 [확인 필요]).
    국외이전 해당 여부는 [확인 필요 — 담당 노무사]. 청구는 달러 카드 결제이고 한국 세금계산서가 안 나온다 [세무 확인].
12. **안전장치를 다시 짓는다.** 규칙 올리기 전 비교 · 칸막이 · 재직자 확인 · 온톨로지 관문 · 검사 644개.

## 6. 장기적으로 — 이점과 위험

**이점**
- **표 구조가 업무에 맞는다.** 급여·연차·퇴직금처럼 «여러 표를 엮어 합치는 일»을 DB 가 한다(앞선 글 4절).
- **가격이 예측된다.** 월 정액 + 서버 단계. 실시간DB 는 읽은 양에 비례해 «부팅 폭풍» 같은 사고 달(8월 ₩12만)이 생긴다.
- **떠나기 쉽다.** 속은 표준 PostgreSQL 이고 수파베이스는 오픈소스라 통째 내보내거나 직접 운영할 수 있다. 파이어베이스는 닫힌 서비스라 떠나는 비용이 크다.
- **기금 4단계 «PostgreSQL 전환»**(`fund-erp/README.md`)과 같은 DB 를 쓸 길이 열린다(칸막이를 먼저 정할 때).

**위험**
- **운영 책임이 늘어난다.** 백업·복구·서버 크기·표 바꾸기를 우리가 챙긴다(파이어베이스는 알아서 관리).
- **서버 크기가 계단식으로 오른다.** Micro → Small → Medium 은 월 $15~60 씩 오른다. 동시 접속·실시간이 늘면 먼저 닿는 한도다.
- **새 기술을 익혀야 한다.** SQL · RLS · 표 바꾸기 — 잘못 쓰면 파이어베이스보다 위험하다(3번).
- **수파베이스 회사 · 가격 정책 변화.** 문을 닫아도 자료는 표준 형식이라 옮길 수 있지만, 그 일도 이전 비용이다.
- **두 벤더.** 푸시용 파이어베이스가 남는다.

## 7. 코딩할 때 어떻게 푸나

### 원칙

1. **옮기기 전에 «한 겹»을 먼저 씌운다.** 화면이 `.ref()` 를 직접 부르는 약 1,900자리를 공용 자료층(예: `PuDb` — 읽기 · 쓰기 · 구독 · 동시 수정)을 지나게 한다.
   **파이어베이스 위에서 먼저** 돌려 같은 결과가 나오는 것을 증명하고, 뒤에서 구현만 갈아끼운다. 이 일은 이전을 안 해도 쓸모가 있다(시험·교체가 쉬워진다).
   새 코드는 공용층만 쓰게 하고, 검사는 «직접 `.ref(` 자리가 늘지 않는다»를 본다(개수를 박지 않고 줄기만 본다 — `test-pin-guard` 규칙).
2. **앱 단위로 옮기고, 원본은 읽기 전용으로 남긴다.** 새 앱(급여 아웃소싱)을 첫 시범으로, 그다음 작은 앱, 마지막에 큰 앱(기금·명함첩). 앱마다 켜고 끄는 스위치를 둔다.
3. **자료 이관은 항상 같은 순서.** 백업 → 변환 → 대조(건수·합계·해시) → **읽기만 전환** → 쓰기 전환 → 일정 기간 이중 쓰기 → 원본 읽기 전용 → 해지.
   원본은 물리 삭제하지 않는다. 앞뒤가 어긋나면 멈춘다(`--force` 길을 만들지 않는다).
4. **가짜 자료로만 시험한다.** 지금 `tools/phone-audit` 의 가짜 파이어베이스처럼 «가짜 수파베이스 시드»를 만들고, 실제 고객 자료·살아 있는 서버는 시험에 쓰지 않는다.

### 문제별 해법

| 문제 | 코딩 해법 |
|---|---|
| 자료 모양(JSON → 표) | 표마다 `id` · `entityType` · `createdAt` · `updatedAt` · `company_id` · `sid` 를 갖게 한다. 금액은 «원» 정수(`bigint`). 물리 삭제 대신 상태 열. **종료·취소·마감 건이 되살아나지 못하게 DB 트리거로 거절**(종료·삭제·되돌림 불변 규칙을 DB 가 지킨다). 안쪽이 변수인 경로는 표 설계 전에 «실제 키 목록»을 읽기 전용으로 뽑아 본다 |
| 보안(RLS) | 표를 만드는 표 바꾸기(migration) 파일 한 곳에서 **`enable row level security` + 기본 거부 + 정책**을 함께 쓴다. 검사 하나가 «RLS 가 꺼진 표가 있으면 실패»를 본다(`pg_tables`). 공개 키(anon)로 읽기를 시도해 **막히는지** 보는 «막힘 시험»을 표마다 둔다. 주민번호·계좌는 **별도 표 + 열 권한** |
| 실시간 | `subscribe(경로)` 헬퍼 한 곳에서 «처음 읽기 → 구독»을 묶는다. 처음엔 «변경 알림이 오면 해당 부분만 다시 읽기»의 단순형으로 시작한다(통째 다시 받기는 부팅 폭풍의 원인이었다). 삭제는 `replica identity full` 을 켠 표만 쓴다. 구독자가 많은 화면은 방송(Broadcast) |
| 동시 수정 | 유형을 나눈다 — 번호·카운터는 DB 순번 / 읽고-고치고-쓰기는 DB 함수 하나(`FOR UPDATE`) / 단순 덮어쓰기는 «판 번호가 같을 때만 고치기». 화면에서는 `rpc('이름', 인자)` 한 줄 |
| 로그인 | 비밀번호는 해시 가져오기 도구로 · 카카오는 기본 제공자 · 익명은 기본 기능 + 권한에서 «익명이면 거절»을 명시 · `staff` 는 Custom Access Token Hook · 지문은 **다시 등록하는 날**을 정해 안내(근로자·직원 모두). `uid` 연결표는 사람 이름이 아니라 «옛 uid → 새 uid» 로만 만든다 |
| 서버 함수 | 함수 한 개 = Deno 폴더 한 개의 표준 틀. 공통 `requireStaff` 는 공용 모듈. 시크릿은 수파베이스 시크릿으로. 메일·PDF 처럼 큰 부품은 **파이어베이스에 남기는 혼합**을 허용하고(수파베이스 DB 는 서버 키로 부른다), 예약은 pg_cron, 트리거 함수는 표 트리거로 |
| 창고 주소 | 옛 주소 → 새 주소 대응표를 만들고, 읽는 자리에서 옛 주소도 한동안 받아 준다. 서명본·증빙은 해시로 대조 |
| 올리개 | 표 바꾸기 파일을 올리기 전 **«사라지는 표·열·정책이 있으면 멈춘다»** 비교 도구를 먼저 짓는다(`rules-deploy.js` 의 짝). 우회로 없음 |
| 로컬 시험 | `supabase start`(도커 필요, 이 PC 에서 가능한지 [확인 필요]) + 표 시험(pgTAP 또는 노드 검사). 요금 상한(spend cap)을 켜고 요금 화면(`pu-billing`)에 칸을 더한다 |

### 옮긴다면 이 순서로

0. (이전과 상관없이 지금) 급여 아웃소싱의 PostgreSQL 시범 — 구글 Cloud SQL 반나절 시험(앞선 글 5절 · 8절).
1. «한 겹» 공용층 + 파이어베이스 구현으로 증명(이 단계만으로도 이득).
2. 가장 작은 앱 하나를 공용층으로 옮겨 본다.
3. 수파베이스 구현을 공용층 뒤에 붙이고, 가짜 자료 시범으로 막힘 시험 · 속도 · 용량 · 한 달 요금을 잰다.
4. 앱 단위 이관(작은 것 → 큰 것). 각 앱은 위 3번 순서.
5. 로그인 · 창고 · 함수를 앱 이관과 겹쳐 옮긴다.
6. 원본을 읽기 전용으로 몇 달 두고, 문제가 없을 때만 해지한다.

## 9. 확인 못 한 것

- P박스용 수파베이스 프로젝트가 실제로 있는지 · 서울인지 · 표 설계 SQL 을 적용했는지 — 수파베이스 대시보드로(1절 «P박스» 소절)
- 실시간DB 현재 용량 · 창고 3곳 용량 · 월 함수 호출 수 · 동시 접속자 수 · 로그인 계정 수 — 구글 콘솔 사용량으로(살아 있는 서버는 이 검토에서 건드리지 않았다)
- 구글 요금에서 실시간DB·함수·창고별 몫(10월)
- 환율($1 = ₩1,400 어림) · 외주 개발 단가 · AI 사용료
- 메일(IMAP·SMTP)·PDF·지문 검증 부품이 Deno(Edge Functions)에서 도는지
- 지문(passkey) 실험 기능의 안정도 · 카카오 로그인을 기본 제공자로 바꿀 때 사용자 번호(`uid_kakao`) 연결
- 이 PC 에서 로컬 수파베이스(도커)를 쓸 수 있는지
- 개인정보 보호법 제26조 제6항 원문 · 국외이전 해당 여부 · 수파베이스 결제 증빙(세무)
- 기간·인건비는 «굵은 어림» — 실제 견적이나 작은 시범 결과로 고친다
