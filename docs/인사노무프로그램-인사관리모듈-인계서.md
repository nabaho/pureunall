# 인사관리 모듈 인계서 — 「인사노무프로그램」 모듈설계용

> 작성 2026-10-31 · 푸른이알피 `pu-erp.html?app=hr` (인사관리) 를 **하나의 모듈**로 보고, 다른 챗팅방에서 이어서 설계·개발할 수 있게 정리한 문서.
> 줄 번호는 이 날짜 기준이다 — 파일이 매일 바뀌므로 **함수 이름으로 찾을 것**(`grep -n "^function 이름(" pu-erp.html`).
> ⚠ 사람 이름·주민번호·계좌·금액은 이 문서에 적지 않는다(저장소 `docs/` 는 배포에서 지워지지만 그래도 지킨다).

## 0. 한 줄 요약

- 인사관리는 **푸른노무법인 «자기 직원»** 의 명부·급여·성과·근태·휴가·퇴직·증명서를 다룬다. 한 파일(`pu-erp.html`, 9.1만 줄) 안에 **약 1만 줄**로 들어 있다.
- 같은 법 계산(급여·연차·퇴직)을 **고객사 110곳 급여 아웃소싱**(`payroll-os.html`)도 쓴다 → 계산을 **하나의 엔진(`js/pu-labor-core.js`)** 으로 모으는 것이 모듈화의 핵심이다. 지금은 **반쯤만** 모여 있다(§4).
- 모듈로 떼어낼 때 가장 큰 일은 ① 계산을 엔진으로 옮기기 ② 자료 칸의 모양을 «계약»으로 적기 ③ 다른 프로그램이 읽는 자리(명부·근태)를 깨지 않기 — 이 셋이다(§8).

## 1. 이 문서를 읽는 순서 (새 방이 시작할 때)

1. 이 문서 §0~§3 (10분) — 무엇이 어디 있는지.
2. `CLAUDE.md` 의 **«되풀이된 실수» 절을 가리키는 `STATUS.md`** 와 `status/` 최근 기록 — 같은 PR 규칙·검사 규칙.
3. §6 «정해진 것»을 읽고 **되돌리지 않는다**.
4. 일을 고르면 §9 «일하는 법» 순서대로(작업 폴더 → 시안 → 코딩 → 검사 → 합치기).

## 4. 계산 지도

### 4-1. 급여 한 달(`calcPayroll`)
`기본급(일할: 입퇴사·무급휴직 일수 반영) + 수당(pay_items) + 법정수당(연장·야간·휴일·주휴) + 성과금(finance_income 에서 자동) + 상여 − 4대보험·소득세·지방세 = 실지급`
- 통상시급 = 월 통상임금 ÷ 소정근로시간(기본 209, **단시간 직원은 209×시간÷8**).
- 법정수당 시간은 근태관리의 초과근로 기록이 `payroll_monthly.legalAllowances` 로 내려간다(자리·열쇠 통일, 2026-09-02).
- **실비(비과세 업무비용)**: 엑셀 급여대장의 «업무비용»은 `businessExpense` 로 보관되지만 **화면·명세서는 `reimbursements` 만 읽는다** → 지금 2026-06 한 달 말고는 0 으로 보임. 관리자 확인 방식 시안(`https://claude.ai/artifact/6G88whsZMXUM5x883gCBVT`)까지 나왔고 **대표 결정 대기**(§7).

### 4-2. 연차
- 정책 카드 `policy_leave` + 부여 수기 조정 `leave_grants` + 사용량 `PuWork.leaveUsed`(시간연차는 **그 직원 소정근로시간**으로 환산).
- 기산: **입사일 기준**(회계연도 아님, 대표 2026-10-10). 2021-06-01 전 입사 4명은 **대법원 2023도5476 판결식**으로 전환(상수 `LEAVE_RULING_FROM=2026-10-10` 한 줄이 되돌리는 스위치).
- 사용촉진 1·2차 통보 날짜는 `PuLaborCore.promotionSchedule`.

### 4-3. 성과급
- 원천: 입금(`finance_income`) 한 건의 `perfShares`. 급여는 **명세서를 열 때마다** 그 달 입금을 훑어 다시 센다(얼려 두지 않음).
- 기준 금액은 **세후**(기타소득 8.8%·사업소득 3.3% 뗀 뒤) — `perfBaseAmount`. ÷0.912 같은 «세전 되짚기» 금지.
- 마감된 달의 성과는 막지 않고 **다음 열린 달**로 넘긴다(`perfYM`·`perfSettled`).
- 지난 실적(2019~2025 인센티브 엑셀에서 가져온 자료)은 `perfHistorical:true` — **실적으로는 세고 급여에는 안 붙인다**. 거르개는 `erpPerfCounts(item, forPay)` 하나.

### 4-4. 퇴직
- 퇴직금 = 30일분 평균임금 × 재직일수/365 (`PuLaborCore.severancePay`). 퇴직소득세는 엔진으로 어림.
- **직원 전원 DC형**(대표 2026-10-10): 법정 퇴직금을 그대로 잡으면 이중 지급 위험 → DC 가입자는 «부담금 적립 부족분»만 본다. 퇴직일 = **마지막 근무일**(대표 2026-10-11). 앞날짜 퇴사 = «퇴직 예정».

### 4-5. 마감
월말 마감(재무관리 ▸ 월말 마감)은 **근태·휴가 → 급여 → 비정규직 → 계약 → 입금 → 출금** 여섯 단계를 한 줄로 잠근다. 순서는 계산의 근거를 따른 것이다(근태가 급여의 근거, 급여 확정이 출금에 기록).
**잠금 순서는 화면 버튼에서 경고 후 앞지를 수 있지만(`force`), 해제 순서는 못 뚫는다** — 이미 확정된 금액의 근거가 사라지기 때문(`monthCloseUnlock` 의 `heldBy` 검사를 느슨하게 하지 말 것). 근태 잠금은 화면마다 막지 않고 `dbUpsert/dbPatch/dbRemove/dbUpsertMany/dbRemoveMany` 다섯 자리의 `ATTEND_LOCK_TABLES` 관문에서 막는다(근태 수정 자리가 20곳 넘어 한 곳씩 막으면 빠뜨린다).

### 4-6. 엔진 연결 현황 (중요)
`PuLaborCore` 는 `pu-erp.html` 에서 **두 곳만** 쓴다 — 4대보험 요율표(`insuranceRatesOf`), 퇴직소득세(`retirementIncomeTax`). 나머지(연차 부여, 평균임금, 법정수당, 촉진 일정 …)는 **화면 안 함수가 따로 계산**한다.
2026-10-10 전수검토의 결론: «연차 네 벌·퇴직금 세 벌» — 화면마다 계산이 달랐고, 0~6단계로 큰 구멍은 막았지만 **«엔진 하나로 모으기»는 끝나지 않았다.**

## 6. 이미 정해진 것 (대표 확정 — 되돌리지 말 것)

1. **연차는 입사일 기준**, 직원 **전원 DC형**, 7~9월 급여 자료는 카카오톡 저장 파일(최종본: `2026년 푸른노무법인 급여대장_수정 26.09.30.xlsx`, 인센티브·급여 1~9월).
2. 퇴직일 = **마지막 근무일**. 퇴사 처리 시 열려 있는 휴직은 닫는다.
3. 성과 기준은 **세후**. 마감 달 성과는 **다음 열린 달 조정**. 지난 실적은 급여에 안 붙인다.
4. **사번·로그인 이메일은 화면에 안 적는다 — 이름만**(2026-10-25).
5. **금액은 관리자(재무 권한자)만 본다**(성과 이력·실비 등).
6. 과거 입금에 맞춰 **가짜 사건·컨설팅 카드를 만들지 않는다**. 이름으로 사건에 잇지 않는다(사업장은 companyId, 사람은 sid).
7. **2026년 incentive 줄을 새로 만들지 않는다** — 재무 입금이 그 일을 한다(매출 이중). 이미 넣은 2019~2025 는 «지난 실적».
8. **푸른 DC 실납입 자료는 지어 넣지 않는다**(받으면 `dc_contributions` 에).
9. 폰 화면: 칩·탭·단추 줄은 줄바꿈(인사관리만), 입력칸 16px, 한 칸은 한 줄, 폰 격자는 `minmax(0,1fr) …` 꼴로 쓴다(전체 규칙이 `1fr 1fr`·`repeat(` 를 한 칸으로 접는다).
10. 새 UI 는 **시안(목업)을 먼저 보여 드리고 승인받은 뒤** 코딩한다. 시안엔 지어낸 이름·금액만.

## 8. 모듈 설계안 (제안 — 승인 전)

### 8-1. 목표
인사관리를 «이알피 한 파일 안의 화면 묶음»에서 **「인사노무 모듈」** 로 바꾼다: 같은 법 계산을 **푸른 직원 인사**와 **고객사 급여 아웃소싱**이 함께 쓰고, 다른 프로그램은 **정해진 입구**로만 인사 자료를 읽는다.

### 8-2. 층 (아래가 위를 모른다)

```
┌ 화면층   pu-erp.html 의 hr/* 컴포넌트 (+ 폰 규칙 css/pu-erp.css)         ← 읽기·그리기·사람 입력만
├ 응용층   «유스케이스» 함수: 한 달 급여 확정 · 입퇴사 처리 · 연차 부여 · 퇴직정산 · 증명서 발급
│          (지금은 화면 안에 섞여 있음 — 여기를 꺼내는 것이 2단계)
├ 계산층   js/pu-labor-core.js (PuLaborCore) · pu-simpletax.js · pu-work-core.js (PuWork)   ← 순수 함수, 노트북 검산
├ 자료층   dbGet/dbUpsert/dbPatch + 자료 «계약»(§3 표를 코드로) + 마감 길목(_attendLockDenied)
└ 규칙층   scripts/make-firebase-rules.js (HRW·FIN·LOGIN)  +  js/pu-ontology.js (hr 프로그램·writeContracts)
```

### 8-3. 모듈의 «공개 입구» (다른 프로그램은 이것만 쓴다)
- **읽기 어댑터**: `user_dir`(사람 목록) · `attendance_records`(근태) · `leave_of_absence`(휴직) — 지금도 다른 앱이 읽는 3곳. **칸 이름 바꾸지 않기**가 약속.
- **쓰기 입구**: `attendance_records`(캘린더 연동) · `perf_confirm`(성과 확인). 나머지 자료는 인사관리 안에서만 쓴다.
- **계산 입구**: `PuLaborCore` 의 함수들(고객사 급여도 같은 함수).
- **이벤트(앞으로)**: 퇴사 확정 → 업무 이관 알림 · 급여 확정 → 재무 출금 «제안» (자동으로 넣지 않고 제안만).

### 8-4. 단계 (한 단계 = 한 PR, 앞 단계가 끝나야 다음)

| 단계 | 일 | 끝났다는 증거 |
|---|---|---|
| **M0 계약 적기** | §3 표를 `docs/` 의 «자료 계약»으로 + 칸 이름·열쇠(`empSid`)·`{u,v}` 봉투를 **검사로 고정** | 계약 검사가 실제 서버 모양과 일치(`tests/`) |
| **M1 계산 엔진 합치기** | 연차 부여(`calcGrantDays`)·법정수당·평균임금·촉진 일정을 `PuLaborCore` 로 옮기고 화면은 호출만. **옛 함수와 새 함수가 같은 답**을 내는 비교 검사를 먼저 | 같은 입력 100건에서 옛/새 일치, 화면 결과 불변 |
| **M2 응용층 꺼내기** | «한 달 급여 확정»·«입퇴사 처리»·«퇴직정산»을 컴포넌트 밖 함수로(자료를 받아 «쓸 것 목록»을 돌려줌 — 실제 쓰기는 한 곳) | 화면 코드에서 `dbSet` 직접 호출이 줄어듦(수 세기) |
| **M3 파일 나누기** | `hr/*` 컴포넌트를 `js/hr/*.js` 로 옮김(전역 함수는 `PuHr.` 이름표). 한 번에 한 화면씩, **옮긴 화면은 검사로 «같은 DOM»** 확인 | 해당 화면 검사 통과 + 폰 점검 도구 수치 불변 |
| **M4 개인정보 분리** | 주민번호·계좌를 `user_accounts` 에서 `worker_secret` 식으로 분리(담당자+대표만) | 규칙 만들개 + 규칙 검사, 읽기 어댑터는 영향 없음 |
| **M5 고객사 급여와 합치기** | `payroll-os.html` 이 쓰는 이식본을 `PuLaborCore` 하나로 | 두 곳 같은 검산표 통과 |

> **하지 말 것**: 한 번에 파일 전체를 옮기기(검사가 «문자열 위치»를 읽는 것이 많아 한꺼번에 깨짐 — `tests/` 중 `pu-erp.html` 을 읽는 것이 500개 넘음) · 계산을 바꾸면서 동시에 화면을 바꾸기 · 급여 자료를 지우고 다시 만들기.

### 8-5. 위험
1. **`pu-erp.html` 한 파일**: 검사 524개 파일이 이 파일을 «문자열»로 읽는다 → 옮길 때 `fnSrc(...)` 로 함수를 찾는 검사가 같이 이사해야 한다.
2. **전역 상태**(`dbGet` 캐시·`CURRENT_USER`): 모듈이 이 전역에 기대는 곳을 세어 두고 «주입»으로 바꿔 나간다.
3. **법 해석이 코드에 박힘**(2021-06-01 연차 기산 등): 상수 하나로 스위치가 되게 유지.
4. **실데이터**: 급여·근태는 법적 책임 자료다 — 백업 → 쓰기 → 서버에서 다시 읽어 확인 순서 고정(`Documents/pu-erp-backups/`).

## 9. 새 방에서 일하는 법 (이 저장소의 규칙)

1. **시작**: `STATUS.md` 읽기 + `gh pr list --state open` + `git log --oneline -20`.
2. **작업 폴더**: 공유 폴더에서 일하지 말고 `../pu-wt-이름` 새 작업 폴더(워크트리). 파일 줄바꿈은 LF 로 맞춘다(`pu-erp.html` 은 `sed -i 's/\r$//'`).
3. **시안 먼저**: UI 가 바뀌면 지어낸 자료로 시안을 보여 드리고 승인받는다. 폰 화면은 `tools/phone-audit` 로 실제 폭에 그려 잰다(§부록).
4. **코딩**: 최소 변경·한국어 주석·팔레트 27색(5색군) 안·한 칸은 한 줄·폰 입력칸 16px.
5. **검사**: 새 검사는 «지금 값»이 아니라 «규칙»을 본다(`CLAUDE.md` 표). 끝나면 `pu-erp.html`/`css/pu-erp.css` 를 읽는 검사 **전부**를 묶음(40개씩)으로 돌린다.
6. **자료를 고칠 때**: ① 백업 파일 ② 서버를 다시 읽어 «본 것과 같은지» 확인 ③ 쓰기 ④ `data/<자리>/u` 에 시각 찍기 ⑤ 서버에서 다시 읽어 검산. 마감된 달·재무 자료는 대표 결정 없이 건드리지 않는다.
7. **규칙 올리기**(보안규칙): 만들개 한 곳만 고치고 `node scripts/rules-deploy.js --deploy`. 사라질 규칙이 있으면 멈춘다 — `--force` 만들지 말 것.
8. **끝**: `status/날짜-가지이름.md` 에 «한 것·남은 일» 새 파일 하나(표에 덧붙이지 않음) → 같은 PR. 합치기 후 사이트 배포가 끝나면 실제 화면 확인.
9. **개인정보**: 화면·문서·예시에 실명·주민번호·계좌·금액을 쓰지 않는다. 사번도 화면엔 안 적는다.
10. 큰 일은 시작할 때 `status/` 쪽지(`상태: 이어하기 대기`)를 남겨 한도에 걸려도 이어진다.
