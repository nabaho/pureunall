# 전체 점검 — 충돌·깜빡임·느림 (대표 지시 2026-09-22)

> 「자꾸 충돌나고 깜빡이거나 시간이 늦거나 … 열 몇 개 앱에서 한 번씩 발생한다.
>  두 군데, 세 군데가 동시에 돌아가면서 생기는 문제들을 전체 검토해 달라」

앱 22개 · 공용 파일 30여 개를 훑었다. **확인된 것**과 **의심되는 것**을 갈라 적는다.
값을 짐작으로 적지 않는다 — 못 잰 것은 못 쟀다고 적는다.

---

## 0. 왜 하필 「열 몇 개 앱」인가 — 이것이 실마리였다

대표님 말씀이 진단의 핵심이었다. 한 앱의 문제가 아니라 **열 몇 개**라는 것.
공용 파일이 실리는 앱 수를 세어 보니 정확히 겹친다.

| 공용 파일 | 실리는 앱 | 하는 일 |
|---|---|---|
| `js/pu-version.js` | **20개** | 새 판이 나오면 새로고침 |
| `js/pu-ontology.js`·`-write.js` | **19개** | 저장 관문 |
| `js/pu-resilience.js` | **17개** | 멎으면 띠를 띄우고 새로고침 |
| `js/pu-health.js` | 17개 | 상태 알림 |
| `js/pu-gate.js` | 16개 | 들어가기 문 |
| `js/pu-whoami.js` | 12개 | 누구인지 |
| `js/pu-authsync.js` | **10개** | 다른 탭에서 로그아웃하면 여기도 끊는다 |

**「열 몇 개 앱에서 한 번씩」은 «한 앱씩 고장 난 것»이 아니라
«한 파일이 열 몇 군데에서 한 번씩 드러난 것»일 가능성이 높다.**
앱을 하나씩 고치면 영영 안 끝난다 — 고칠 자리는 이 일곱 개다.

## 1. 충돌 — 「내가 넣은 게 없어졌다」

### ①★★ 직원 명부를 «통째로» 덮어쓴다 — 로그인이 막힐 수 있다

`pu-erp.html:87151` (`_syncUserDir`)

```js
fbDb.ref('data/user_dir').set({ v: dir, u: Date.now() }).catch(function(){});
```

- `user_dir` 은 **로그인할 때 읽는 명부**다.
- 이 한 줄은 «내 PC 에 있는 `user_accounts`»로 명부를 **통째로 갈아 끼운다.**
- 푸른ERP 의 다른 모든 저장은 `dbSet` 이라는 두꺼운 보호장치를 지난다 —
  서버를 먼저 읽고, 합치고, 트랜잭션으로 쓰고, 0건·급감을 막는다.
  **이 줄만 그 문을 지나지 않는다.**

**무슨 일이 나나:** 관리자 A 의 화면이 새 직원을 아직 못 받은 채 이 함수가 돌면,
그 직원이 명부에서 **사라진다.** 사라진 직원은 **로그인이 안 된다.**
`.catch(function(){})` 라 실패해도 아무 말이 없다.

> 확인 방법: 새 직원을 넣은 직후 다른 관리자 PC 에서 로그인해 보기.

### ②★ 같은 칸을 «두 군데»에서 통째로 쓴다

대표님이 말씀하신 「두 군데, 세 군데가 동시에」가 코드에 그대로 있다.

| 앱 | 같은 칸 | 쓰는 곳 둘 |
|---|---|---|
| `pu-home.html` | `homepage/check` | `:2485` · `:2862` |
| `rules.html` | `chwieop/bank/meta` | `:5698` · `:5734` |

둘 다 **표 전체를 `.set()`** 한다. 한쪽이 쓰는 사이 다른 쪽이 쓰면 **먼저 것이 사라진다.**

### ③ 통째 덮어쓰기가 남아 있는 자리 (합쳐 20곳 남짓)

`pu-cards.html:3668`(명함 색인 전체) · `:9248`(갈래 전체) · `:17464`
`pu-home.html:1846`(홈페이지 쪽 설정 전체) · `:6362`(협력사 로고 전체)
`rules.html:1939`(교정 기억 전체) · `payroll-os.html:579,582` · `kcareer.html:13620`
`pu-erp.html:67680`(`ieum_public` 전체)

혼자 쓸 때는 멀쩡하다. **둘이 동시에 열면 나중 사람이 이긴다.**

### ④ 앱마다 보호 두께가 다르다 — 이것이 「어떤 앱만 그런다」의 정체

| 보호 | 앱 |

**그 교훈이 다른 앱에는 안 옮겨졌다.**

## 2. 깜빡임 — 「화면이 자꾸 다시 그려진다」

### ⑤★★ 거래내역 화면이 «그릴 때마다» 모든 줄을 다시 훑는다

`pu-erp.html:47581` 과 `47601` — **둘 다 의존목록(`[...]`)이 없다.**

```js
useEffect(function(){
  ...expAll.forEach(...)...       // 줄 전체를 훑는다
});                               // ← 여기 [] 가 없다 = 그릴 때마다 돈다
```

의존목록이 없으면 **무엇 때문에 다시 그리든** 이 일이 또 돈다 —
검색창에 한 글자를 쳐도, 1초 시계가 돌아도, 서버 자료가 도착해도.

**`47601` 은 그 길에서 «서버에 쓴다»** (`saveExpense` → `dbUpsert('finance_expense', …)`).
쓸 때마다 새 `id` 를 만든다(`'fe-'+Date.now()+Math.random()`) —
**같은 줄이 두 번 통과하면 지출이 두 건 생긴다.**
(지금은 `removeRow` 가 같은 묶음에서 줄을 치워 막고 있다. 막는 것이 «한 겹뿐»이다.)

322줄짜리 표에서 이것이 대표님이 보신 깜빡임·느림의 유력한 자리다.

### ⑥ 표 높이를 «그릴 때마다» 다시 잰다

`pu-erp.html:9027` (`useFillHeight`)

```js
useEffect(function(){ fit(); });   // 의존목록 없음 — 그릴 때마다 잰다
```

`fit()` 은 `getBoundingClientRect()` 를 부른다 — 브라우저가 **그 자리에서 레이아웃을 다시 계산**한다.
8px 이력현상으로 무한고리는 막아 두었다(잘 되어 있다).
다만 잣대가 `getBoundingClientRect().top`(화면 기준)이라 **스크롤 위치에 따라 값이 달라진다.**

### ⑦ 이미 달아 둔 «이름표»가 있다 — 그 말을 믿어야 한다

`pu-erp.html:9702` 에 2026-09-17 대표 제보 「깜빡임이 계속된다」로 달아 둔 것이 있다:

```
🐌 화면 멈춤 ○○ms — 서버 자료 «○○» 를 받아 적용하는 중  ← 이것이 깜빡임의 정체입니다
```

**깜빡일 때 F12 콘솔을 열어 이 줄을 한 장 찍어 주시면 어느 표인지 바로 나옵니다.**
지금은 그 줄이 무엇을 찍었는지 아무도 모른다 — 달아만 두고 안 읽었다.

## 4. 잘 되어 있는 것 — 되돌리지 말 것

점검하며 확인한 것이니 함께 적는다. **이것들을 건드리면 손해다.**

- 푸른ERP 의 저장 길(`dbSet`)은 **원자적 트랜잭션으로 합친다.**
  「다른 노무사가 입력한 자료가 사라지던 경로」를 이미 막았다(`:4995` 주석).
- 0건·급감 가드가 트랜잭션 **안에서** 다시 검사된다 — 읽고 쓰는 사이를 막는다.
- `fb_data_changed` 는 150ms 로 묶는다(`:990`) — 다시 그리기 폭증을 막는다.
- 서버 자료가 늦게 오는 것을 **이름표로 찍는다**(`:9702`).
- 로그인 동기화(`pu-authsync.js`)는 두 번 끊지 않게 막아 두었다(`kicked`).
- 새 판 새로고침은 **팝업이 열려 있으면 기다린다** — 입력하던 것을 안 날린다.

## 7. 고친 것 (2026-09-22)

### ① `user_dir` — 두꺼운 문을 지나게 했다

세 겹을 달았다. `tests/userdir-and-effect-deps.test.js` 가 **진짜 함수를 떠서 돌려** 지킨다.

1. **빈 명부는 아예 안 올린다.** 사본이 없는 기기에서 관리자가 로그인하면
   `accs` 가 `[]` 가 되어 명부를 통째로 비웠다 — 그러면 아무도 못 들어온다.
2. **통째 `set` → 트랜잭션.** 읽고 쓰는 사이에 남이 넣은 직원이 사라지지 않는다.
3. **사람이 사라지면 멈춘다.** 잣대는 수가 아니라 **이름표(`sid`)** 다 —
   수가 같아도 «다른 사람»일 수 있다(검사가 그 경우를 따로 본다).
   한 명 줄이는 것은 사람이 한 일일 수 있으니 통과시킨다(`USERDIR_MAX_DROP`).
4. **조용히 실패하지 않는다.** `.catch(function(){})` 를 걷고 막힌 까닭을 화면에 띄운다.

### ② 거래내역 효과 둘 — 의존목록을 달았다

⚠ **`expAll`·`expGuess` 는 목록에 넣으면 «안 된다».** 둘 다 그릴 때마다 새로 만드는
값이라(`var expAll = rows ? …filter(…)`) 넣어도 매번 달라 보여 **목록이 헛것이 된다.**
고친 것처럼 보이면서 그대로 매번 도는 것이 가장 나쁘다 — 검사 ⑥ 이 그것을 막는다.

기댄 것은 그 값들을 «만들어 내는» 쪽이다: `rows`·`ldTabEff`·`_ldSrc`·`expCat`(·`expAutoReg`).

### 돌연변이 확인 5회 — 다섯 다 걸린다

빈 명부 막이 빼기 · 트랜잭션을 도로 `set` 으로 · 사람사라짐 막이 빼기 ·
의존목록 떼기 · **목록에 `expAll` 넣기(겉만 고친 꼴)**

⚠ 그리고 검사가 **내 주석에 한 번 걸렸다** — 「`.catch(function(){})` 가 남아 있다」를
글자로 찾았더니 그 까닭을 적어 둔 주석이 걸렸다. 이 저장소 「되풀이된 실수 ②」 그대로다.
주석을 먼저 걷게 고쳤다.

   선언되지 않은 이름이라 **그 자리에서 터진다.** 이 앱은 `alert` 만 쓴다.
   검사 ⑥ 이 이제 그것을 막는다.
2. **검사를 쓰며 「첫 번째 것」에 걸렸다.** 트랜잭션 몸통을 `return next;` 라는
   글자로 잘랐는데 그 글자가 함수 안에 **둘** 있어 반쪽만 떴다.
   중괄호를 세어 뜨도록 고쳤다(이 저장소 「되풀이된 실수 ⑦」과 같은 결).

### 남의 검사 둘이 깨졌다 — 대역이 방법을 못 박고 있었다

`tests/pu-home-screen.test.js` 의 db 대역이 `set` 만 주고 있어, `update` 로 바꾸자 깨졌다.
그 검사가 보는 것은 「실패를 삼키지 않는가」이지 「어느 방법으로 쓰는가」가 아니다 —
대역에 `set`·`update` 를 **둘 다** 주어 뜻은 지키고 브레이크만 풀었다.
경로와 방법을 보는 것은 새 검사 ①의 일이다.
