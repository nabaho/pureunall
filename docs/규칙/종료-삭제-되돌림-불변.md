## 1. 왜 자꾸 되살아나거나 중복됐는가 (되풀이된 5가지 사고 경로)

1. **확정 되돌림(`undoneDate`) 거르개 누락**
   거래내역에서 입금 확정을 되돌리면 레코드를 지우지 않고 `undoneDate`를 찍는다. 그런데 일부 화면(`IncomeListTab`, `IncomeKindTab`, `IncomeUnmatchedTab`, `PerfTab` 등)이 `dbGet('finance_income')`를 날것으로 읽어, 이미 되돌린 입금이 입금 리스트와 성과 분배에 유령처럼 남았다.
2. **옛 캐시·통째 덮어쓰기(`data/<표>`)로 인한 부활**
   한 기기에서 삭제(`_deleted: true`)·되돌림(`undoneDate`)·종결(`closed`) 처리했는데, 다른 탭·기기의 오래된 사본이나 콘솔 강제 동기화(`erpSyncNow`)가 표 전체를 덮어써 죽은 레코드를 되살렸다.
3. **무덤 표식(`_deleted` / `tombstone`) 없는 물리 삭제**
   데이터 정리 스크립트가 레코드를 물리 삭제(`remove`)하면, 다른 PC의 로컬 저장소(`IndexedDB`/`localStorage`)에 남아 있던 사본이 동기화 때「서버에 아직 안 올라간 새 줄」로 오인되어 다시 올라온다.
4. **자동 번호 재정렬이 종결·휴지통 건까지 건드림**
   `reorderConsultingNos`·`renumberContracts2026`가 휴지통(`_deleted`) 건까지 번호 계산에 넣거나, 이미 종결·이관(`closed`/`transferred`/`cancelled`)되어 보고서·계산서에 나간 관리번호까지 뒤에서 밀어 바꿨다.
5. **원본 표 이름 불일치·종결 이력 미확인으로 인한 중복 생성**
   기타사업 입금 되돌림이 `'other' + 's'`(`others`라는 없는 표)에 패치해 `other_projects`가 완납으로 남거나, 자동 계약 등록이 `closed`·`cancelled` 계약을「이미 처리된 계약」으로 보지 않아 중복 카드를 다시 만들었다.

## 2. 절대 어기면 안 되는 5대 불변 원칙

### 원칙 ① 종결·이관·마감 불변 (`Terminal Immutability`)
- 아래 상태에 들어간 레코드는 **이미 끝난 역사 기록**이다:
  - `status`가 `'closed'` · `'cancelled'` · `'transferred'` · `'done'` · `'end'`인 건
  - `closedAt` · `closedDate` · `closeDate` · `permanentArchived` 값이 찍힌 건
  - 마감 잠금(`locked_income_months`, `locked_payroll_months`)된 달에 속한 입금·임금·성과 기록
- **금지**:
  - 자동 번호 재정렬·일괄 데이터 정리·마이그레이션이 위 레코드의 **관리번호(`no`, `contractNo`, `caseNo`)·상태(`status`)·금액·담당자·종결일**을 바꾸는 것.
  - 마감된 달의 입금·성과를 뒤에서 직접 고치거나 지우는 것(마감월 정정은 반드시 다음 열린 달 차액 조정 `perf-adjust` 경로를 탄다).
- **허용**: 사용자가 화면에서 명시적으로 `[재진행]` / `[종결 취소]` / `[마감 해제]`를 누른 단건 작업만 허용한다.

### 원칙 ② 휴지통·무덤 표식 보존 (`Tombstone Preservation`)
- 모든 업무·재무·업체 레코드의 삭제는 물리 제거가 아니라 **`_deleted: true` + `_deletedAt` + `_deletedReason` (`TrashBin.remove`)** 및 무덤 표식(`co_tombstones`, `trash_bin`, `trash_fin`)으로 기록한다.
- **금지**:
  - 데이터 중복 정리 때 Firebase 경로에서 키를 그냥 `null`로 지워 무덤 표식을 없애는 것(다른 기기 캐시에서 되살아난다).
  - 동기화 병합(`_fbUnknownBaseUpserts`, `dbSet` 트랜잭션)이 서버에 이미 찍힌 `_deleted: true`를 옛 사본으로 덮어써 지우는 것.
- **복원 유일 경로**: `TrashBin.restore`가 명시적 복원 시각(`_restoredAt`)과 복원 의도(`_erpRestoreIntent`)를 찍었을 때만 `_deleted` 해제를 인정한다.

### 원칙 ③ 입금·성과 단일 거르개 (`Single Live/Perf Gate`)
- `finance_income`은 감사를 위해 되돌린 줄(`undoneDate`)과 휴지통 줄(`_deleted`)을 같은 표에 남긴다. 따라서 읽는 모든 자리는 예외 없이 공용 거르개를 써야 한다:
  - **입금 목록·매출·미수/계산서 대조·통장 집계·카드수수료 파생·전역 검색**: `erpIncomeLive(fi)` (매출 집계는 `erpIncomeIsRevenue(fi)`).
  - **임금 성과급·성과관리(`PerfTab`)·퇴사자 미정산 성과**: `erpPerfCounts(fi, forPay)` 또는 `!fi._deleted && !(fi.undoneDate && !fi.perfSettled)`.
  - **원본 완납 롤백**: 반드시 `erpIncomeSourceStore(fi.sourceKind)`를 거쳐 `'other' → 'other_projects'`, `'company' → 'companies'` 매핑이 어긋나지 않게 한다.

### 원칙 ④ 통째 덮어쓰기 금지 (`No Whole-Table Blind Write`)
- 핵심 공유 표(`DIFF_KEYS`: `contracts`, `cases`, `consultings`, `funds`, `other_projects`, `companies`, `finance_income`, `payroll_monthly`, `ledger_batches`)는 서버에서 **레코드 ID 열쇠 객체(`data/<표>/v/<id>`)**로 관리한다.
- **금지**:
  - 앱 코드·콘솔 함수(`erpSyncNow`)·외부 Node/REST 스크립트에서 `data/<표>` 전체를 배열이나 로컬 스냅샷으로 통째 `set` / `PUT` 하는 것.
  - 숫자 배열 인덱스(`0, 1, 2...`)를 `v/` 아래에 섞어 쓰는 것(배열·객체 분열로 중복이 생긴다).
- **필수**: 언제나 `dbUpsert` · `dbPatch` 또는 `data/<표>/v/<id>/<field>` 단위의 최소 경로 패치만 사용한다.

### 원칙 ⑤ 데이터 검토·정리 5단계 안전 절차 (`Live Data Review Protocol`)
AI나 개발자가 중복·오류 데이터를 검토하거나 정리할 때는 아래 5단계를 순서대로 밟는다:
1. **백업 및 사전 진단(읽기 전용)**: 작업 전 백업 본을 확보하고 `node scripts/erp-integrity-audit.js --snapshot <전.json>`으로 현재 상태를 수치로 먼저 확인한다.
2. **불변 레코드 격리**: `closed` · `cancelled` · `transferred` · `_deleted` · `undoneDate` · 마감월 레코드는 자동 정리 대상에서 제외한다. 종료된 건 자체가 중복이라 정리해야 할 때는 **목록(ID·관리번호·사유)을 먼저 표로 보여주고 대표 승인을 받은 뒤** 소프트 삭제(`_deleted: true`)만 수행한다.
3. **파급 사슬(Cascade) 전수 확인**: 아래 §3 파급 대조표에 따라 연결된 하위·상위 레코드(`finance_income`, `sourceContractId`, `transferredTo`, `work_erp`, `pucards`)에 고아 참조나 유령 성과가 남지 않는지 함께 확인한다.
4. **최소 경로 패치(`dry-run` 먼저)**: 바뀔 레코드 `id`와 필드 전후 값을 먼저 출력(`dry-run`)해 검증한 뒤 해당 `id` 경로만 패치한다.
5. **사후 불변 검증**: 작업 후 스냅샷으로 `node scripts/erp-integrity-audit.js --before <전.json> --after <후.json>`을 돌려 **불변 위반 0건(`violationCount: 0`)**을 확인하고 보고한다.

## 3. 표 간 연결·파급 대조표 (한 표만 고치면 어긋나는 자리)

| 손대는 표 | 연결된 표·필드 | 함께 확인·처리할 일 |
|---|---|---|
| `contracts` (계약관리) | `cases`·`consultings`·`funds`·`other_projects` (`sourceContractId`, `sourceContractNo`), `contract_requests` (`srcMails`, `srcPhoto.id`) | `transferred` 계약의 번호·상태 변경 금지. 취소·삭제 시 이미 이관된 업무가 살아 있는지 먼저 확인 |
| `consultings` · `cases` · `funds` · `other_projects` | `finance_income` (`sourceKind`, `sourceId`), `work_erp`, 정부사업일정(`scal_*`) | 삭제(`_deleted: true`) 전 연동된 살아 있는 `finance_income` 유무 확인. `closed` 건의 관리번호(`no`, `caseNo`) 변경 금지 |
| `finance_income` (입금·성과) | 원본 업무 완납 플래그(`contractPaid`, `balancePaid`, `retainerPaid`, `successPaid`, `paid`), `perfShares`, 마감월(`locked_income_months`, `locked_payroll_months`) | 확정을 무를 때는 물리 삭제 대신 `erpUndoIncome`(→ `undoneDate` + 마감월이면 `perf-adjust` 차액 이월 + `erpIncomeSourceStore` 원본 롤백) 단일 경로 사용 |
| `companies` (업체관리) | 모든 업무 표의 `companyId`, 기업정보함(`pucards`), 무덤 표식(`co_tombstones`) | 사업자번호(`bizNo`)가 유일 기준(이름 병합 금지). 삭제·통합 시 `co_tombstones`를 남겨 옛 사본 부활 차단 |
