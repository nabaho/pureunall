# NAS 에 AI 를 넣어 «찾기»를 고친다 — 설계 (2026-09-10, 검토 ③)

대표 물음: 「허깅페이스에서 AI 를 받아 NAS 에 넣어 기존 자료를 관리하고 싶다 — 어떻게 하는 게 좋은가」

> 한 줄 결론 — **NAS 는 「찾기」에 좋고 「이해하기」에는 약하다.**
> 판독·요약은 지금처럼 Gemini 에 두고, **찾기(색인)** 를 NAS 로 가져온다.
> NAS 는 «만드는 곳», 밖(폰)에서는 «색인만» 본다 — 원본은 사무실을 안 나간다.

## 0. 지금 있는 것 (실측)

| 자리 | 무엇 | 어디 |
|---|---|---|
| 시놀로지 NAS | `192.168.0.21`, FileStation API 로 이미 붙어 있다 | `pu-erp.html` NasBackupSettings |
| 계약서 보관함 | 서명 계약서 스캔본 — 파일은 NAS, ERP 엔 **링크만** | `contract_docs` |
| 자료 보관소 | 컨설팅·급여대장·4대보험 파일 — 파일은 NAS, ERP 엔 **메타·링크만** | `nas_archive {fileName, category, yearMonth, companyName}` |
| 취업규칙 서고 | 본문은 Firebase(`rules_mgmt/casebook/text`), 검색은 **낱말 색인**(회차당 2회 이상 나온 상위 60 낱말) | `js/pu-rules-casebook.js` |
| 판독 사다리 | Gemini 3모델 → Vision(월 1,000장) → tesseract.js(기기 안·무제한) | `functions/doc-read.js`·`vision-read.js`·`pu-doc-read.js` |

**진짜 아픔은 「어디 있는지 못 찾는 것」이다.** 서고 검색 코드가 스스로 적는다 —
「한 번만 나온 말은 색인에 없어 찾지 못합니다」. 「휴가 며칠 쓸 수 있나」로는 안 나온다.
NAS 의 계약서·자료보관소는 검색 자체가 없다(이름·업체·연월 칸으로 거르기만).

## 1. NAS 에서 실제로 돌아가는 것 — 사양이 정한다

시놀로지는 대부분 CPU 만 있고 GPU 가 없다. 그 조건에서:

| AI 종류 | NAS(CPU) 에서 | 판정 |
|---|---|---|
| **임베딩**(글 → 숫자, 의미 검색) | 가볍다. 모델 0.5~2GB, 한 문단에 0.1~1초 | ✅ **가장 잘 맞음** |
| **OCR**(스캔 → 글자) | 한 쪽에 몇 초. 밤에 돌리면 된다 | ✅ 됨 |
| 작은 LLM(3B 이하) | 1초에 몇 글자 — 사람이 못 기다린다 | △ 밤 배치 요약 정도 |
| 쓸 만한 LLM(30B+) | GPU 없이는 안 된다 | ✗ |

⚠ **모델 판 번호는 자주 바뀐다.** 아래 이름은 «갈래»로 읽고, 실제 받는 날 최신을 다시 본다.
- 한국어 임베딩: `BAAI/bge-m3`(다국어·무난한 첫 선택) · `nlpai-lab/KURE-v1` 계열(한국어 특화) · `intfloat/multilingual-e5-large`
- OCR: PaddleOCR(한국어) · Surya — 지금 tesseract 보다 표·도장에 강하다
- 띄우기: 시놀로지 **Container Manager(도커)** — DSM 7 이상

## 2. 가장 큰 걸림돌은 하드웨어가 아니다 — «밖에서 어떻게 보나»

`192.168.0.21` 은 사무실 안에서만 보인다. 대표는 **폰으로 밖에서** 쓴다.
- NAS 를 인터넷에 열면 → 계약서·주민번호가 든 상자를 인터넷에 여는 것이다. **하지 않는다.**
- ERP 는 HTTPS(GitHub Pages)인데 NAS 가 HTTP 면 브라우저가 막는다(코드에 `isMixedContent` 가 이미 있다).

그래서 구조를 이렇게 둔다:

```
NAS (사무실 안 · 인터넷에 안 엶)
 ├ 계약서·자료 스캔본 원본                    ← 지금 그대로
 ├ 밤마다: OCR → 조각내기 → 임베딩(숫자)        ← AI 가 여기서 돈다 (도커)
 └ «색인»만 Firebase 로 올린다                 ← 숫자·짧은 미리보기·파일 링크. 원본은 안 나감
                    ↓
폰/PC(밖) → Firebase 색인으로 검색 → 「㈜가야 2024 자문계약서 3쪽 — "…연차는 근속…"」
                    ↓
        열어야 할 때만 NAS 링크 (사무실 안·VPN 에서만 열린다 — 지금 계약서 보관함과 같다)
```

이것은 이 집이 이미 쓰는 설계(「ERP 엔 링크만, 파일은 NAS」)와 **같은 철학**이다. 새 원칙이 안 늘어난다.

⚠ 색인에 담는 것과 안 담는 것을 못 박는다:
- 담는다: 임베딩 벡터, **짧은 미리보기(문장 한둘, 200자 안)**, 파일 링크·쪽수, 업체 `companyId`, 자료 종류, 날짜
- **안 담는다**: 원본 본문 전체, 주민번호·계좌·도장 그림, 사람 이름을 열쇠로 쓰는 것(온톨로지 규칙 — 사람은 `sid`, 업체는 `companyId`)
- 미리보기는 만들 때 주민번호 꼴(`\d{6}-\d{7}`)·계좌 꼴을 **가린 뒤** 담는다(`js/pu-rrn-mask.js` 의 규칙 재사용)

## 3. 검색은 어디서 하나 — 두 길

**㉠ 브라우저가 벡터를 내려받아 견준다** (첫 시험)
- 색인이 몇 천 조각이면 벡터(1024차원 × float16 ≈ 2KB)를 다 받아도 몇 MB — 폰도 된다
- 물음을 벡터로 바꾸는 일이 필요하다 → 브라우저에서 작은 임베딩 모델(transformers.js, 100~300MB)을 돌리거나, **Gemini 임베딩 API**(지금 열쇠·무료 몫 안)를 부른다. **첫 시험은 Gemini 임베딩** — 붙일 것이 없다.
- ⚠ 색인 벡터와 물음 벡터는 **같은 모델**이어야 한다. NAS 가 bge-m3 로 색인했으면 물음도 bge-m3 여야 한다. → 첫 시험은 «양쪽 다 Gemini 임베딩»으로 맞추는 것이 가장 단순하다(NAS 도 Gemini API 를 부른다 — 그러면 NAS 의 몫은 OCR·조각내기·가리기·올리기다).
- 그 다음 단계에서 NAS 임베딩(bge-m3)으로 바꾸면 물음도 브라우저 transformers.js 로 — 그때 원본도 물음도 밖에 안 나간다.

**㉡ Cloud Function 이 벡터를 견준다**
- 색인이 커지면(수만 조각) 브라우저가 못 받는다 → 함수가 견준다. 이때는 Firestore 벡터 검색이나 작은 벡터 DB 가 필요하다. **지금은 아니다.**

## 4. 단계 — 작게, 숫자로 보고 늘린다

| 단계 | 무엇 | 되는지 보는 숫자 |
|---|---|---|
| 0 | **NAS 모델명·RAM·DSM 판·도커 여부** 확인 (대표) | — |
| 1 | 계약서 100장 → NAS 에서 OCR(PaddleOCR) → 글자 파일 | 한 장 몇 초 · 글자 정확도(표본 10장 눈으로) |
| 2 | 조각내기(문단 300자) → 가리기 → Gemini 임베딩 → Firebase `nas_index/v1/{chunkId}` | 조각 수 · 올린 크기(MB) |
| 3 | 서고·자료보관소 화면에 「🔎 뜻으로 찾기」 한 칸 — ㉠ 길 | 「휴가 며칠」로 찾아지는가(정답 표본 20문항) |
| 4 | 밤마다 도는 일로(NAS 작업 스케줄러 · 새 파일만) | 하루 처리 장수 · 실패 수(조용히 넘기지 않는다) |
| 5 | 임베딩을 NAS 모델로 바꿔 «밖으로 아무것도 안 나가게» | 검색 품질이 3단계와 같은가 |

⚠ 3단계 전까지 화면에 아무것도 안 붙인다. 2단계까지는 «되는지»만 본다.

## 5. Firebase 쪽 — 규칙·온톨로지

- 새 자리 `nas_index/v1/{chunkId}`: `{ v:[…], preview, src:{kind:'nas_archive'|'contract_doc'|'casebook', id, page}, companyId?, yearMonth?, model:'gemini-embedding-…', createdAt }`
- 읽기: 재직 직원(STAFF). 쓰기: NAS 가 쓰는 **전용 계정**(서비스용 `uid_roles` 한 줄, `isAdmin:false`, 쓰기는 이 자리만). 규칙은 `scripts/make-firebase-rules.js` 에서만 고치고 `rules-deploy.js` 로 올린다(CLAUDE.md).
- 온톨로지: `PuOntology.TERMS` 에 개체 `nasIndexChunk`, 관계 `indexes`(→ 원본 `sourceKind`·`sourceId`) 먼저 정의. 파생 색인이므로 `sourceMutation:'never'` — 색인이 원본을 고치거나 지우지 않는다. 이름으로 회사를 맞추지 않는다(`companyId` 만).
- 비용: Gemini 임베딩은 무료 몫이 넉넉하나 **밤 배치가 몫을 다 쓰면 낮의 판독이 굶는다** → 배치는 하루 한도(예 2,000조각)를 두고 남은 것은 다음 날로.

## 6. 하지 않는 것 (지금은)

- NAS 에 LLM 을 두어 질문에 «답하게» 하는 것 — CPU 로는 사람이 못 기다린다. 찾아 주고, 읽는 것은 사람이 한다.
- 허깅페이스 «클라우드 추론»(Inference Providers·Endpoints) — 무료 몫이 작고 GPU 임대는 월 수십만 원. 지금 사다리보다 약한 층이다.
- NAS 를 인터넷에 여는 것.

## 7. 대표께 물을 것 (0단계)

DSM → 제어판 → 정보센터: **모델명 · RAM · DSM 판**, 패키지센터에 **Container Manager** 가 있는지.
- RAM 8GB↑ + 도커 → 1~5단계 다 간다
- RAM 4GB → 임베딩만(OCR 은 느리다) — 그래도 3단계까지는 된다
- 도커 없음(구형 J/value) → NAS 는 보관만, 색인 만들기는 사무실 PC 한 대가 밤에 한다(같은 설계, 도는 자리만 다르다)
