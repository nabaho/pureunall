# 푸른업무 보관함 — LLM 위키 규칙

이 보관함은 «AI 와 한 일»을 쌓아 두고, 그것을 **위키로 정리**해 다음 일에 다시 쓰려는 곳이다.
(Karpathy 의 LLM 위키 방식: 원자료 → 위키 → 규칙, 세 층.) 이 파일은 클로드 코드·코덱스가 이 폴더에서 시작하면 읽는다.

## 세 층 — 고치는 곳이 정해져 있다
| 층 | 자리 | 누가 쓰나 |
|---|---|---|
| 원자료 | `raw/` | **자동 수집만.** 사람도 AI 도 고치지 않는다(`tools/obsidian-sync`가 만든 대화 기록) |
| 위키 | `wiki/` | **AI 가 쓴다.** 사람이 읽고 바로잡는다 |
| 규칙 | 이 파일 | 사람이 고친다 |
| 하루 목록 | `daily/` | 표시(`obsidian-sync:begin~end`) 사이는 자동, 바깥은 사람 손글씨 |

## 「정리해줘」라고 하면 — 정리 절차
1. `wiki/_pending.md` 를 읽는다(아직 정리 안 된 원자료). 많으면 오래된 것부터 한 번에 10건 안팎.
2. 원자료를 읽고 **남길 것만** 뽑는다: 결정·이유 · 새로 안 사실 · 되풀이된 실수 · 다음 할 일.
   잡담·시행착오·도구 출력은 버린다.
3. `wiki/` 의 알맞은 쪽을 **고치거나 새로 만든다.**
   - `wiki/projects/<이름>.md` — 프로젝트(저장소·사업) 하나당 한 장. 지금 상태 · 결정 · 남은 일.
   - `wiki/clients/<고객사>.md` — 고객사 하나당 한 장. **다른 고객사 내용을 섞지 않는다.**
   - `wiki/concepts/<주제>.md` — 법령·계산 방식·절차처럼 여러 일에 걸친 지식.
   같은 주제의 장이 이미 있으면 새로 만들지 말고 거기에 보탠다(두 벌 금지).
4. 쓴 모든 문장 끝에 **근거 링크**를 단다: `[[raw/sessions/…/파일이름]]`. 근거 없는 말은 쓰지 않는다.
5. `wiki/index.md` 에 새 장·바뀐 장의 한 줄 요약을 올린다.
6. `wiki/log.md` 맨 아래에 한 줄씩 남긴다 — 이것이 «정리 끝» 표시다(`_pending` 에서 빠진다):
   `## [YYYY-MM-DD] ingest | raw/sessions/…/파일이름 → [[고친 장]]`

## 법인 업무 규칙 (어기지 않는다)
- 법령·판례·행정해석은 **원자료에 적힌 것만** 옮긴다. 조문·사건번호를 기억으로 채우지 않는다.
  확인 안 된 것은 `[확인 필요]` 로 표시한다.
- 사실 · 가정 · 해석 · 의견을 섞지 않는다. 날짜는 «사건일»과 «검토일»을 구분한다.
- 개인정보(주민번호·계좌·연락처)는 위키에 **절대 옮기지 않는다.** 원자료에서 `[주민번호]` 처럼 가려져 있는 것은
  그대로 둔다. 원본에서 복원하려 하지 않는다.
- 고객사별로 장을 나누고 서로 링크하지 않는다(고객 비공개 정보가 섞이지 않게).
- 원자료와 위키가 어긋나면 위키를 고친다. 원자료는 그대로 둔다.

## 위키 장의 모양
```
---
type: project | client | concept
updated: YYYY-MM-DD
sources: 근거 원자료 수
---
# 이름
한 줄 요약.
## 지금 상태
## 결정과 이유        ← 각 줄 끝에 [[근거]]
## 남은 일
## 되풀이된 실수
```

## 점검 («점검해줘» 라고 하면)
- 근거 링크가 없는 문장 · 서로 모순되는 장 · 오래 안 고친 장(`updated`) · 링크가 끊긴 장을 목록으로 보고한다.
- 고치기 전에 목록을 먼저 보여 준다.
