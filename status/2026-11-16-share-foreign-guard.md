# 2026-11-16 · 다른 웹사이트가 보낸 «공유»는 담지 않는다 (대표 「여기서 막아줘」)

앞 작업(`status/2026-11-15-sw-erp-into-pu-sw.md`, PR #3098)의 자동 보안 검토에서 이어진 일.

## 무엇을 막았나
- 폰의 «공유 → 푸른○○»를 받는 일꾼(서비스워커)이, 다른 웹사이트의 페이지가 보낸 전송은 담지 않는다.
  담지 않고 «공유를 받지 않았습니다» 화면(403, 앱으로 가기 고리)을 보인다.
- 보낸 곳이 우리 앱(일꾼과 같은 폴더) 밖의 웹 주소인 전송은 거절한다 — 같은 깃허브 주소의 다른 저장소 페이지도 거절.
  폰의 공유는 그대로 받는다(잣대의 자세한 설명은 `pu-sw.js` 의 `fromOtherSite` 머리말).
- 사진첩은 받은 것을 확인 없이 담는다(대표 지시 2026-10-02) — 그 방식은 그대로 두었다.

## 고친 것
- `pu-sw.js` — `fromOtherSite`(거르개)·`refuseOtherSite`(거절 화면)를 더하고, 받는 함수 다섯(기업정보함·사진첩·이알피·급여데이터함·문서뷰어)의 첫 줄에서 거른다.
  가로채는 줄(`e.respondWith(take…)`)의 모양은 그대로다(`tests/photos-share-target-path.test.js` 가 «가로채는 곳 = 공유 길 수»를 본다).
- `pu-cal-share-sw.js` — 같은 두 함수를 옮겨 두고 POST 에서 거른다(이 일꾼은 scope 를 좁혀 따로 살아 불러 쓰지 않는다).
- 옛 껍데기 `pu-photos-sw.js`·`pu-cards-sw.js` — 옛 갈래를 들고 있던 것을 `importScripts('pu-sw.js?from=…')` 한 줄로 바꿨다
  (`pu-erp-sw.js` 와 같은 방법). 이 일꾼이 남은 폰도 다음 갱신 때 통합 일꾼과 똑같이(거르개 포함)움직인다.
- `pu-cal.html` 머리말에 한 줄(사람이 누르는 길은 그대로 둔다).
- 거절 화면은 보낸 곳 주소나 받은 내용을 싣지 않는다. 화면(html)은 일꾼이 직접 만들어 각 앱 화면은 손대지 않았다.

## 검사
- 새 `tests/share-target-other-site.test.js` — 규칙 «다른 웹사이트가 보낸 공유는 어느 일꾼도 담지 않는다 — 폰의 공유는 그대로 받는다».
  - 저장소의 일꾼 파일을 «내용으로» 빠짐없이 찾는다(fetch 를 듣거나 importScripts 를 쓰는 js — 등록 안 하는 옛 껍데기 포함). 켜지지 않는 것은 공유를 받는 꼴이 아니어야 한다.
  - POST 공유 앱(manifest share_target)마다 일꾼을 vm 으로 켜 «폰처럼» 보내 담는 짝을 찾고, 짝마다 보낸 곳을 바꿔 본다(깃허브 주소·localhost 둘 다).
    받음: 보낸 곳 없음 · android-app:// · 우리 앱 화면 · Origin null · 같은 Origin / 거절: 남의 사이트(https·http) · 남의 Origin · 같은 주소 다른 폴더.
  - 거절은 403·html·보낸 곳 주소를 싣지 않음·고리는 앱 안.
- `tests/lib-sw-boot.js` — 가짜 공유 요청에 «보낸 곳·Origin» 을 줄 수 있게 했다.
- `tests/phone-security-hardening.test.js` — 기업정보함 옛 껍데기를 글자로 박던 줄을 규칙으로(통합 일꾼을 부르면 비우기는 pu-sw.js 몫, 자기 갈래를 들면 먼저 비운다).
- 고장 16가지를 일부러 넣어 모두 잡힘: 갈래별 거르개 뺌(사진첩·기업정보함·이알피) · Origin 안 봄 · android-app 까지 막음 · 폴더 안 봄 · 거절 화면에 보낸 곳 실음 · 거절 대신 앱으로 303 · 거르개 늘 «아니다»/늘 «남» · 캘린더 거르개 뺌 · 캘린더 Origin 안 봄 · 옛 껍데기 둘을 옛 코드로 · 새 공유 앱을 더하며 거르개 빠뜨림 · 새 일꾼 파일이 거르개 없이 받음.
- 전체 `node --test 'tests/*.test.js' 'functions/*.test.js'`(윈도우) — 30,630개 실패 0 · 건너뜀 66.
- 크로미움 원본(`chrome/browser/android/webapk/webapk_post_share_target_navigator.cc`)을 보니 폰의 공유 POST 는
  브라우저가 «보낸 곳 없이» 시작하고, 시작한 곳(initiator)은 앱 자기 주소다 — 이 거르개가 폰 공유를 막지 않는다는 근거.
  그래도 진짜 폰 확인은 아래 «사람이 할 일»로 남긴다.

## 사람이 할 일 (배포 뒤, 안드로이드 폰)
1. 갤러리·카톡에서 평소처럼 «공유 → 푸른사진첩 / 푸른이알피 / 푸른기업정보함 / 푸른캘린더» — 그대로 담기는지.
2. **«공유를 받지 않았습니다» 화면이 뜨면 바로 알린다** — 폰 공유가 막힌 것이다(폰이 «보낸 곳»을 예상과 다르게 붙인 경우). 그때는 거르개를 풀고 다시 본다.
- 배포 직후 첫 공유 한 번은 폰에 남은 옛 일꾼이 받을 수 있다 — 그 뒤에 새것으로 바뀐다.
- 내장 브라우저는 서비스워커 등록을 막아 두어 일꾼의 실제 POST 받기는 vm 검사로만 확인했다.
