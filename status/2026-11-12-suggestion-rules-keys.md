# 2026-11-12 · 건의함 보안규칙 — 번호 모양 · 알려진 칸 · 길이 한도

요청: 「건의함 보안규칙: 키 모양·크기 검사 추가」 — PR #3008 의 외부 보안 검토가 «근본 구멍은 규칙» 이라고 남긴 일.

## 무엇이 구멍이었나
건의함 세 자리는 직원이 쓸 수 있는 자리인데 규칙이 키 모양·칸·크기를 안 봤다.
- 번호(키)에 `& | ^ %` 따옴표를 넣을 수 있었다 → 대표 PC 의 감시 도구가 윈도우에서 firebase 를 cmd.exe 로 부르므로 명령으로 읽힐 수 있었다(도구 쪽은 #3008 에서 막음 — 이것은 두 번째 겹).
- 아무 이름의 칸에 큰 글을 숨기면 대표가 건의함 목록을 열 때마다 내려받았다(진행함 전체를 읽는다).
- 새 건의에 서버 전용 칸(assist·감시 알림 칸)을 함께 담을 수 있었다.

## 한 것 (`scripts/make-firebase-rules.js` 건의함 절 → 적용본·붙여넣기 사본 다시 만듦)
- 번호: 건의·메타·진행함 `^[A-Za-z0-9_-]{1,64}$`, 진행함 uid `{1,128}`. (운영 번호 37개·uid 5개·직원 uid 10개 전부 통과하는 모양. 카카오·지문 로그인도 기존 uid 를 쓴다.)
- 알려진 칸만(`$other:false`): 건의 원문 14칸 · 메타 7칸 · 진행함 13칸 — 화면(enter.html)이 실제로 쓰는 칸을 하나씩 확인해 적었다(새 건의·재요청·길잡이 채팅 접수·관리자 답변·건의자 확인).
- 칸마다 종류·길이: 그림 한 장 100만 자·3장, 답변 2만 자, 피드백 2천 자, 제목 200자, relatedId·source 모양, resolvedOk·seen 은 참/거짓.
- **객체가 아닌 값**: 컨테이너 자리(images·replyImages·진행함 `$uid`·`$id`)는 `newData.hasChildren()` — RTDB 는 통짜 값(글자·숫자)을 쓰면 자식 규칙을 «평가하지 않는다».
- **그림은 0번부터 빈틈 없이**(1번은 0번이, 2번은 1번이 있을 때만) — 빈틈이 있으면 배열이 아닌 객체로 돌아와 대표 화면의 `images.map` 이 죽는다. ★ 연속성은 «컨테이너» 에서 본다 — 자식에서만 보면 지울 때 평가되지 않아 3장 중 0·1번만 지우는 부분 삭제로 빈틈이 생겼다.
- 서버가 쓰는 칸은 규칙에 «없다» — 서버(함수·감시 도구)는 관리자 권한이라 규칙을 안 탄다.
- 읽기·쓰기 권한은 안 바꿨다. 지우기는 번호가 이상해도 된다.

## 검증
- **진짜 엔진(Firebase 에뮬레이터 4.11.2, 이 PC 안에서만)**: `tests/suggestion-rules.emulator.mjs` **111개** 전부 통과 — 정상 쓰기(직원·관리자·서버 칸이 붙은 옛 자료 위 갱신 포함) + 나쁜 쓰기마다 «한 군데만 다른 통과하는 짝».
  같은 시험을 **옛 규칙**으로 돌리면 나쁜 쓰기 36개, 객체 아닌 값·빈틈 10개, 부분 삭제 5개가 그대로 통과 — 구멍이 실제였고 시험이 그것을 잡는다는 증거.
  ★ 확인한 «뜻»: `$other:false` 가 서버 칸이 붙은 기존 건의에 대한 관리자 답변(부분 갱신)을 막지 않는다.
- 저장소 검사 `tests/suggestion-rules.test.js` 13개(모의 평가기, `.validate` 만 — 삭제는 흉내 못 내서 규칙 «모양» 도 직접 지킨다). 규칙을 하나씩 약하게 만든 돌연변이 15종이 모두 빨갛게 변하는 것 확인.
- 전체 검사 29,857개 통과(실패 0). 올리기 도구 «보기만»: 새로 생기는 규칙 18 · 값이 바뀌는 규칙 2 · 읽기·쓰기 조건 변경 0.
- 외부 검토(Antigravity 기능 검증 · Codex/Antigravity 보안): 1차 «중간 2·낮음 1»(통짜 값 우회·칸 수 표기) → 고침 → 재검증 1차 기능 **통과 0건**, 보안 «중간 1»(부분 삭제 우회)·낮음 1(시험이 uid_roles 전체를 덮어씀) → 고침.
- 기존 검사 `tests/suggestion-push.test.js` 의 «규칙에 watchNotice 낱말이 없다» 는 글자 검사라 설명 주석의 표현만 바꿨다(그 칸의 «새 규칙» 은 여전히 없다).

## 남은 일 / 모르는 것
- ⚠ **규칙을 아직 콘솔에 올리지 않았다.** 올리기 도구(`node scripts/rules-deploy.js`)가 «멈췄다»: 콘솔에는 있고 생성기에는 없는 규칙 2개(`harass_invest`·`harass_secret`)가 사라질 판이다 — 열린 PR #3014(괴롭힘·성희롱 조사 프로그램)가 규칙을 콘솔에 먼저 올리고 생성기 변경은 아직 안 합쳤다.
  안전장치가 정확히 이 사고를 막았다(`--force` 를 만들지 않는다). **#3014 가 합쳐진 뒤** 이 가지를 main 위로 옮기고(생성기에 그 규칙이 들어온다) 올리면 사라질 규칙이 0 이 된다. 올린 뒤: 콘솔 원문을 새 판으로 갈아 끼우고 `tests/photos-staff-share.test.js` 의 게시 전 목록(PENDING) 스무 줄을 비운다.
- 규칙을 올리기 전까지는 옛 규칙 그대로라 구멍이 열려 있다 — 정상 건의 접수·답변·확인은 영향 없다. 감시 도구 쪽 방어(#3008)가 먼저 합쳐지면 그 사이에도 명령 삽입은 막힌다.
- 실제 로그인 화면에서 건의 접수·답변·확인을 눌러 본 것은 아니다(에뮬레이터에서 화면이 보내는 모양 그대로 시험).
- 화면에 새 칸을 더하면 규칙도 같이 고쳐야 한다(안 그러면 접수가 막힌다) — CLAUDE.md·AGENTS.md·docs/규칙/건의함.md 에 적었다.
- 기존 자료에 그림이 객체(빈틈) 모양인 건은 없다(운영 37건 모두 배열). 대표 화면의 `images.map` 은 `Array.isArray` 방어가 없지만, 규칙이 새 빈틈을 막으므로 이번 PR 에서는 화면을 건드리지 않았다.
