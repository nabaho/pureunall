# 2026-11-12 · 건의함 보안규칙 — 번호 모양 · 알려진 칸 · 길이 한도

요청: 「건의함 보안규칙: 키 모양·크기 검사 추가」 — PR #3008 의 외부 보안 검토가 «근본 구멍은 규칙» 이라고 남긴 일.

## 무엇이 구멍이었나
건의함 세 자리는 직원이 쓸 수 있는 자리인데 규칙이 키 모양·칸·크기를 안 봤다.
- 번호(키)에 `& | ^ %` 따옴표를 넣을 수 있었다 → 대표 PC 의 감시 도구가 윈도우에서 firebase 를 cmd.exe 로 부르므로 명령으로 읽힐 수 있었다(도구 쪽은 #3008 에서 막음 — 이것은 두 번째 겹).
- 아무 이름의 칸에 큰 글을 숨기면 대표가 건의함 목록을 열 때마다 내려받았다(진행함 전체를 읽는다).
- 새 건의에 서버 전용 칸(assist·감시 알림 칸)을 함께 담을 수 있었다.

## 한 것 (`scripts/make-firebase-rules.js` 건의함 절 → 적용본·붙여넣기 사본 다시 만듦)
- 번호: 건의·메타·진행함 `^[A-Za-z0-9_-]{1,64}$`, 진행함 uid `{1,128}`. (운영 번호 37개·uid 5개·직원 uid 10개 전부 통과하는 모양. 카카오·지문 로그인도 기존 uid 를 쓴다.)
- 알려진 칸만(`$other:false`): 건의 원문 14칸 · 메타 7칸 · 진행함 13칸 — 화면(enter.html)이 실제로 쓰는 칸을 하나씩 확인해 적었다(새 건의·재요청·길잡이 채팅 접수·관리자 답변·건의자 확인).
- 칸마다 종류·길이: 그림 한 장 100만 자·3장, 답변 2만 자, 피드백 2천 자, 제목 200자, relatedId·source 모양, resolvedOk·seen 은 참/거짓.
- 서버가 쓰는 칸은 규칙에 «없다» — 서버(함수·감시 도구)는 관리자 권한이라 규칙을 안 탄다.
- 읽기·쓰기 권한은 안 바꿨다. 지우기는 번호가 이상해도 된다.

## 검증
- **진짜 엔진(Firebase 에뮬레이터 4.11.2, 이 PC 안에서만)**: `tests/suggestion-rules.emulator.mjs` 84개 전부 통과 — 정상 쓰기 18(직원·관리자·서버 칸이 붙은 옛 자료 위 갱신 포함) + 나쁜 쓰기 마다 «한 군데만 다른 통과하는 짝».
  같은 시험을 **예전 규칙**으로 돌리면 나쁜 쓰기 36개가 그대로 통과(실패 36) — 구멍이 실제였고 시험이 그것을 잡는다는 증거.
  ★ 확인한 «뜻»: `$other:false` 가 서버 칸이 붙은 기존 건의에 대한 관리자 답변(부분 갱신)을 막지 않는다.
- 저장소 검사 `tests/suggestion-rules.test.js` 10개(모의 평가기, `.validate` 만) — 번호 모양이 화면(`_chatImpValidId`)·규칙에서 같은 모양인지도 묶는다. 규칙을 하나씩 약하게 만든 돌연변이 10종이 모두 빨갛게 변하는 것 확인.
- 규칙 관련 기존 검사 133개 통과. 올리기 도구 «보기만»: 새로 생기는 규칙 18 · 값이 바뀌는 규칙 2 · **사라지는 규칙 0** · 지금 콘솔 규칙과 저장소 규칙이 일치.
- 기존 검사 `tests/suggestion-push.test.js` 의 «규칙에 watchNotice 낱말이 없다» 는 글자 검사라 설명 주석의 표현만 바꿨다(그 칸의 «새 규칙» 은 여전히 없다).

## 남은 일 / 모르는 것
- ⚠ **규칙을 아직 콘솔에 올리지 않았다.** CLAUDE.md 절차(`node scripts/rules-deploy.js --deploy`)는 올리는 도구가 «지금 콘솔» 과 견주어 사라질 규칙이 없을 때만 올린다 — PR 이 합쳐진 뒤 올려야 다음 «Firebase 배포» 가 옛 규칙을 되돌려 놓지 않는다.
- 실제 로그인 화면에서 건의 접수·답변·확인을 눌러 본 것은 아니다(에뮬레이터에서 화면이 보내는 모양 그대로 시험).
- 화면에 새 칸을 더하면 규칙도 같이 고쳐야 한다(안 그러면 접수가 막힌다) — CLAUDE.md·AGENTS.md·docs/규칙/건의함.md 에 적었다.
