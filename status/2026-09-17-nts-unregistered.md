# 2026-09-17 · 국세청에 «없는» 사업자번호를 사진첩이 막는다

- PR: (아래에 채움)

  처리하는게 좋은가?」 (2026-09-15)

## 무엇이 있었나

대표께서 기업정보함의 한 회사를 짚으셨다. 그 회사의 사업자번호는 **`123-45-67891`** —
**국세청에 없는 번호**다. 그런데도 사진첩이 등록증을 읽고 **자동으로** 기업정보함에 넣었다.

## ★★★ 왜 체크섬이 못 막았나

`123-45-67891` 은 검산을 **통과한다.**
앞 아홉 자리 가중합이 169 라 검사자리가 1 이고, 적힌 것도 1 이다. 자릿수도 맞다.
**기계적으로는 흠이 없는 번호**다. 이런 번호는 오직 국세청만 가려낼 수 있다.

## ★★★ 그런데 그 답을 우리가 «안 읽고 있었다»

국세청은 없는 번호에 이렇게 답한다.

```
{ "b_no": "1234567891", "b_stt": "", "tax_type": "국세청에 등록되지 않은 사업자등록번호입니다." }
```

**상태(`b_stt`)를 비우고 안내문을 `tax_type` 에 담아 준다.**
그런데 `js/pu-doc-read.js` 는 이렇게 한 줄이었다.

```js
out.ntsState = row.b_stt || null;     // ← b_stt «하나만» 봤다
```

그래서 없는 번호가 「물어봤는데 아무 말도 없더라」가 되고,
바로 아래 자동 입력 문(`autoOk`)이 **그냥 열렸다.**

> ⚠ 기업정보함은 이미 제대로 읽고 있었다(`coNtsWord` — PR #1239).
> **한 응답을 두 곳이 다르게 읽고 있었던 것**이 이 구멍의 정체다.

## 고친 것

### ① 한 줄을 읽는 규칙을 기업정보함과 «같게» 맞췄다
`ntsWord(row)` — `b_stt` 가 있으면 그것, 없으면 `tax_type`.
검사가 **두 곳을 나란히 돌려** 같은 답이 나오는지 본다. 갈리면 한쪽만 막는 구멍이 다시 생긴다.

### ② 「없다」를 «값으로» 남긴다 — `ntsFound`
| | |
|---|---|
| `true` | 국세청에 있다(상태말이 왔다) |
| `false` | **국세청에 없다**(안내문이 왔다) |
| `null` | 국세청이 안 가려 줬다 — **모른다** |

⚠ `null` 을 `false` 로 뭉개지 **않는다.** 모르는 것을 「없다」로 단정하면 멀쩡한 등록증이
죄다 「확인 필요」로 쌓여, 치울 수 없는 할 일이 목록을 못 믿게 만든다
(2026-08-04 「확인 필요 오류가 계속 나온다」와 같은 종류의 사고).

### ③ 자동 입력 문에서 막는다
```
국세청에 없는 사업자등록번호입니다 — 번호를 다시 확인해 주세요
```
사진첩 한 줄도 이 글을 그대로 쓴다 — 「번호 확인됨」이라고 **거짓말하지 않는다.**

### ④⚠ 옛 결과를 깨뜨리지 않는다
`ntsFound` 는 오늘 생긴 칸이라 **이미 읽어 둔 결과에는 없다.**
없다고 「모른다」로 두면 지난주에 읽어 둔 **「폐업자」가 오늘 갑자기 자동으로 통과한다** —
고치려던 것보다 더 나쁜 구멍이다. 그래서 칸이 없으면 상태말 자체를 보고 가린다.
(이 자리를 처음에 틀리게 짰고, 저장소의 옛 검사가 그것을 잡았다.)

## ⚠ 이미 들어와 있는 것은 이 고침이 안 지운다

`READ_VERSION` 을 **안 올렸다.** 올리면 읽어 둔 사진 전부가 다시 읽을 차례에 들어가고,
그것은 AI 몫을 통째로 한 번 더 쓰는 일이다. 물음이 하나도 안 바뀌었으므로 값이 없다.

이미 기업정보함에 앉은 가짜 번호는 **기업정보함의 「🏛 국세청 훑기」**(PR #1244)가
AI 없이 전부 훑어 준다 — 거기서 「국세청에 등록되지 않은 사업자등록번호입니다」로 뜬다.
이 고침이 막는 것은 **앞으로 들어올 것**이다.
