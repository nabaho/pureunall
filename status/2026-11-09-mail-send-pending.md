## 1. 속도 — 확인한 것 (서버 로그, 읽기 전용)
`firebase functions:log --only sendMaterialMail` 에서 실제 실행 시간:

| 때 | 서버 실행 시간 |
|---|---|
| 2026-11-09 18:53(KST) — 첨부 있는 강의자료 메일 | **6,095 ms** |
| 2026-11-02 16:18(KST) | **4,246 ms** |

- 두 번 다 바로 앞에 «OPTIONS 36~85 ms»(깨어 있는 서버)가 붙어 있었다 → **서버가 처음 켜지는 느림(콜드 스타트)이 아니라 «일 자체»가 4~6초**다.
- 로그에는 단계별 시간이 없다 — **어느 단계가 몇 초인지는 재지 못했다.** 아래는 코드를 읽고 짚은 후보다(추정).
- 진짜 메일은 한 통도 보내지 않았다(로그만 읽음).

서버가 답하기 «전»에 차례로 하는 일(`functions/index.js sendMaterialMail` → `mail-deliver.js deliverOnce`):
1. 로그인 확인(`verifyIdToken(…, true)` — 폐기 여부까지 서버에 물음) · 직원 확인(캐시)
2. 첨부 모으기(창고에서 내려받기) · 서명 그림·열람 확인 준비(DB 읽기·쓰기 여러 번)
3. **SMTP 발송**(접속·인증·전송)
4. **다음메일 «보낸메일함» 사본 넣기(IMAP)** — 새로 접속 → 로그인 → 폴더 목록 → 올리기(APPEND) → 끊기. **첨부가 있으면 편지를 한 번 더 통째로 올린다.** 20초 한도까지 기다림. 이게 가장 긴 후보다.
5. 기록 쓰기(`sendLog`·`sentBox`, DB 리전은 싱가포르·함수는 서울) · 임시 파일 정리(창고 목록 조회 포함)

## 2. 화면 — 고친 것 (`pu-cards.html`, 서버 변경 없음)
- 메일함에서 「지금 보내기」를 누르면 **서버 답을 기다리기 전에** 「📤 보낸 메일」 창으로 간다. 맨 위에 `⏳ 보내는 중… N초` 줄이 서서 기다린다.
- 나가면 목록을 다시 읽어 실제 기록으로 바뀌고(「보냈습니다」 알림), 실패하면 `❌ 보내지 못함` 붉은 줄 + 오류 문구 + 「다시 쓰기」(쓴 글 그대로 되살림)·「지우기」. 알림(alert)도 그대로 띄운다.
- **예약**과 **메일함이 아닌 곳(자료함 보내기 창)** 은 예전 그대로(서버가 곧바로 답하거나, 범위 밖).
- 안전장치: 보내는 동안 다른 메일은 못 보낸다(`_sending`, 같은 메일 두 번 방지) · 쓰던 글은 줄이 들고 있다 · 임시저장은 «나간 뒤에만» 지운다 · 보내는 중에는 «쓰다 만 글 이어 쓸래요?»를 묻지 않는다(같은 글이 또 열리지 않게) · 기다리는 사이 새로 쓰기 시작한 글은 건드리지 않는다.
- 줄에 찍히는 값은 가려서(esc) 찍고 id 는 `data-*` 속성으로만 싣는다(묶음 줄 보안 검토와 같은 약속).

## 2-1. 자동 검증(Orca) 1회차 지적 → 고침 (기능·보안 둘 다 같은 «중간» 2건)
- ① **나간 글의 임시저장이 남는다** — 보내는 중 보낸 창에서 「새 메일」을 누르면(비어 있어도) 나간 뒤 `if(!direct || !_compose) clearDraft()` 가 건너뛰어져, 이미 나간 메일의 임시저장이 남고 다음에 「이어서 쓸까요?」로 또 떠 **같은 메일을 다시 보낼 길**이 된다. 반대로 새로 쓴 글이 자동저장으로 저장본을 덮은 경우엔 지우면 안 된다.
- ② **마지막 수정이 사라진다** — 마지막 자동저장(30초) 뒤에 고치고 곧바로 보내면, 쓰기 화면을 비우면서 저장하지 않아 보내는 중 창이 닫히거나 새로고침되면 최신 글이 없다(주석의 «창이 닫혀도 글이 남는다»가 거짓).
- 고침: 비우기 «전에» `saveDraft(true, pend.id)` 로 지금 글을 저장하되 저장본에 **보내는 줄 번호(`pid`)** 를 적는다. 나간 뒤 `clearDraftIf(pend.id)` — **그 번호가 붙은 저장본만** 지운다(새 글이 덮은 저장본은 남고, 새 메일이 비어 있든 말든 나간 글의 저장본은 지워진다).
  못 보낸 줄 「지우기」도 같은 번호의 저장본을 지우고, 그 저장본을 이어 쓰면 붉은 줄을 거둔다(줄과 편집기가 같은 글을 두 벌로 안 들게). 낮음 반영: 단추 `type="button"` · 오류 칸 `role="alert"` · 긴 오류 줄바꿈.
- 반영 안 함(낮음, 원래 있던 모양): 보조 글자 명암비 · 단추 크기 · 단추별 aria-label.

## 4. 남은 일 · 한계 (숨기지 말 것)
- **서버 속도는 그대로다.** 기다리는 «자리»만 옮겼다. 실제로 줄이려면 서버(`mail-deliver.js`)를 고치고 `sendMaterialMail` 함수를 다시 올려야 한다 — 운영 발송 길이라 대표 승인 없이 올리지 않는다. 후보(추정 효과):
  - ⓐ IMAP 접속·로그인·폴더 목록을 **SMTP 발송과 동시에** 미리 해 두고 발송이 끝나면 올리기만 한다(수 초 중 일부).
  - ⓑ 사본 올리기·`sentBox`/`sendLog` 기록·임시 파일 정리를 **동시에** 한다(순서대로 하던 것).
  - ⓒ 첨부 모으기와 서명·열람 준비를 동시에 한다 · 묵은 임시 파일 훑기는 매번 안 하고 가끔만.
  - ⓓ 먼저 단계별 시간을 로그에 남기는 줄만 올려 «어디가 느린지» 재 본다.
  - ⚠ 답을 먼저 주고 뒤에서 사본을 넣는 방식은 쓰지 않는다 — 함수는 답한 뒤 멈출 수 있어 «보낸함에 안 보인다»(2026-08-23)가 되돌아온다.
- 진짜 로그인한 화면에서 실제 발송으로는 못 봤다(가짜 자료·가짜 응답으로만 확인).
- 자료함 보내기 창(기업정보함)에서 보내는 길은 예전 그대로 쓰기 화면에서 기다린다.
