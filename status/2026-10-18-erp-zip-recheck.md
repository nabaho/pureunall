# 이알피 — 이미 적힌 우편번호 전수 검산·고침 (2026-10-18)

- 까닭: 어제(10/17) 빈 우편번호를 채울 때(status/2026-10-17-erp-zip-backfill.md) 표본 80건 중 4건이 행안부 값과 달랐다. 그래서 «이미 적힌 것» 전부를 같은 잣대로 다시 봤다.
- 대상: 실시간DB `data/companies` · `data/contracts`(사업장 `company.zipcode`) · `data/consultings` · `data/funds` · `data/other_projects` 에서 우편번호가 적힌 것 전부(휴지통 건 뺌).
- 잣대: 서버 `zipLookup` 과 «같은 코드»(`functions/zip-lookup.js` lookupZip·pickZip + `js/pu-addr.js` query·key·clean)로 카카오 주소검색. **한 곳으로 딱 떨어질 때만** 바른 값 후보로 봄.
- 확인: 카카오와 다른 것은 표본이 아니라 **전부** 행안부 주소정보누리집(juso.go.kr)에서 직접 찾아 봄 → 9곳 모두 카카오와 같음. «같음» 표본 2건도 행안부와 같음.

- 570건 중 99건은 어제 채운 것 — 모두 그대로 있고 모두 같음(업무관리 동기화에 덮이지 않았다는 확인도 됨).
  그 전부터 있던 471건 기준으로 틀림 15건(3.2%), 같은 주소로 묶으면 9곳.
- 틀린 모양: 아예 다른 지역 번호(서울·대전·경남 번호, 다른 시 번호, 「00200」) 5곳 몫 10건 · 같은 시 다른 구역 번호 4곳 몫 5건.
  한 회사의 틀린 값이 업체·기금·계약으로 복사되어 퍼진 경우가 있었다(한 곳이 5건).
- 대표 승인(2026-10-18 「승인한다. 틀린 우편번호 15건을 행안부로 확인한 바른 값으로 고쳐라」) 뒤 씀.
- 쓰는 법: 어제와 같다. 쓰기 직전 서버를 다시 읽어 15건의 레코드 지문(sha256)이 미리보기 때와 같은지 확인(달랐으면 하나도 안 쓰고 멈춤) →
  `firebase database:update` 로 **우편번호 칸 하나씩만** → 바뀐 표마다 `data/<표>/u` 에 시각.
  쓴 뒤 다시 읽음 — 맞음 15 · 틀림 0 · 바뀐 다른 칸 0.
- 일부러 안 건드린 것: 주소 칸, `updatedAt`·`updatedBy`, `revision` (어제 기록과 같은 까닭 — 업무관리 동기화가 «최근 이김»으로 덮는다).
- 되돌리기: 되돌릴 자리 파일(19자리)을 세션 공용 쪽지 폴더에 남겼다(저장소 밖).
  `firebase database:update / zipfix-undo-1792308223006.json -f --project pureun-erp`
- 판단 못한 3건은 그대로 둠:
  - 도로명 안에 띄어쓰기(「먹거리 8길」)가 있어 잣대가 도로명을 잘못 읽은 1건 — 행안부로 보니 적힌 값이 맞음.
  - 지번 본번만 있는(「○○동 161번지」) 1건 — 그 본번의 건물이 모두 같은 우편번호라 적힌 값이 맞아 보임.
  - 주소 번지가 행안부에 없는 1건 — 같은 길의 다른 건물 우편번호와는 같다. ⚠ 남은 일: **주소 자체**를 사람이 확인할 일(업체관리).
