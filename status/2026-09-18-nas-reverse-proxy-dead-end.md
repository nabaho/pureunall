# 2026-09-18 저녁 · 역방향 프록시로 CORS 는 못 뚫는다 — 이 DSM 판의 한계

가지 `claude/login-start-screen-386qu2` (코드 변경 없음, 다음 세션을 위한 기록)

## 결론

**대표님 나스(DSM, 로그인 포털 UI 판)의 역방향 프록시로는 브라우저 CORS 응답 머리글을
넣을 자리가 없다.** 셋 다 확인했다 —

| 탭 | 있는 것 | CORS 응답 머리글용인가 |
|---|---|---|
| 일반 | 소스/대상 프로토콜·호스트·포트 | 아니다 |
| 사용자 지정 머리글 | 이름/값 두 줄 넣을 수 있음, 「WebSocket」 미리설정 있음 | **아니다 — 대상(뒤쪽 DSM)으로 보내는 요청 머리글이다.** WebSocket 미리설정이 `Upgrade`·`Connection` 을 넣는 것이 그 증거 |
| 고급 설정 | 시간제한(연결/보내기/읽기) · 프록시 HTTP 버전 · 오류 페이지 재발송 | 아니다 |

`Access-Control-Allow-Origin` 두 줄을 「사용자 지정 머리글」에 넣고 저장까지 했는데도
연결 테스트는 그대로 「DSM 이 이 화면의 주소를 안 받아들입니다」로 실패했다 —
이 가설과 맞는다.

## 여기까지 밟은 길 (다음 세션이 되풀이하지 않게)

1. DSM 자체 헤더 칸(`제어판 → 로그인 포털 → DSM/응용 프로그램/고급`) — **이 판에는 없다.**
   (앞서 두 번 짐작으로 잘못 안내함 — 「응용 프로그램 포털」이름이 이 판에서 「로그인 포털」로
   바뀌었고, DSM 항목은 설치 패키지 목록에 없다)
2. 역방향 프록시 「사용자 지정 머리글」 — **응답이 아니라 요청 쪽으로 간다. 못 쓴다.**
3. 역방향 프록시 「고급 설정」 — 시간제한·HTTP 버전만. **CORS 와 무관.**

## 남은 길 (다음에 시도할 것, 오늘은 안 함)

- ⭐ **나스 「작업 스케줄러」로 밤에 스스로 받아 오게 하기** — 브라우저를 안 거치므로
  CORS 자체가 없다. 이알피가 아니라 나스가 능동적으로 도는 방식(설계 전환 필요,
  `docs/2026-09-10-NAS-AI-색인-설계.md` 의 구조와 통한다).
- 시놀로지 SSL 인증서를 실제 도메인 인증서로 바꾸고 `Origin` 검사를 완전히 딴 방식으로
  (예: 나스 앞에 별도 경량 프록시 컨테이너, Container Manager 여부 확인 필요 —
  아직 「🔌 연결 테스트」의 🖥 모델·RAM·도커 줄을 못 받았다).
- **당장은 「💾 백업 파일 다운로드」→ File Station 수동 백업으로 충분하다.** 위험 없음.

## 대표님께 드린 말

「이 나스 판으로는 브라우저 CORS 를 통과시킬 방법이 없습니다. 제가 짐작으로 일을
늘렸습니다. 오늘은 여기서 접겠습니다.」 — 자동화는 다음에 «나스가 스스로 받아 오는»
설계로 다시 시도한다. 오늘 더 이상 나스 화면을 만지시게 하지 않는다.
