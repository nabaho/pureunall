# 메일도 «좌우로 넓게» — 700 → 980

대표 지시 2026-09-26
「몇번째 요청했는데 캡쳐3의 화면과 같이 좌우로 넓게 정리해서 보내는 방식으로 몇번요청했다」

## 왜 여러 번 말씀하시게 됐나

2026-09-17 에 「한화면에 나오게 좌우로 넓게 만들어봐라」를 듣고 **웹 전문 보기만** 넓혔다.
메일은 700 그대로였다. 게다가 그 결정이 검사에까지 「메일은 700 이라야 한다」로 굳어 있어,
누가 넓히려 해도 검사가 막았다.

⚠ **「700 이 메일의 한계」는 사실이 아니었다.** 실측(2026-09-26): 대표님 다음메일의
읽는 칸은 **1,600px 남짓**인데 편지만 700 이라 오른쪽이 통째로 비어 있었다.

## 잰 것

같은 회차(기사 5 · 자료 7 · 판례 3 · 한마디)를 두 폭으로 지어 브라우저에서 쟀다.

| | 예전(700) | 지금(980) |
|---|---|---|
| 편지 폭 | 700px | **980px** |
| 편지 길이 | 2,541px | **2,002px** (−539px, 21% 짧다) |
| 자료 카드 | 두 칸 | **세 칸** |
| 기사 | 한 줄로 죽 | **두 칸** |

웹 전문 보기는 2,003px — **메일과 거의 같은 모습**이 됐다.

## 넓히기만 하면 안 되는 까닭 (함께 바꾼 것 셋)

메일에는 «웹에서만 되는 것»을 못 쓴다. 폭만 올리면 오히려 읽기 나빠진다.

1. **자료 카드** — 웹은 칸틀(grid)인데 **아웃룩은 grid 를 모른다** → 넓은 메일은 «표로 셋씩».
   ⚠ 표라서 내려받기 단추의 바닥줄은 못 맞춘다(2026-09-18 실측 1015/932/973).
   그건 지금 메일(둘씩 표)도 마찬가지라 나빠진 것은 없다.
2. **기사 목록** — 웹은 단(column-count)인데 **발송기가 통째로 지운다**(STYLE_OK 에 없다)
   → 넓은 메일은 «두 칸 표». 가르는 잣대는 «건»이다 — 문단을 가운데서 자르지 않는다.
3. **이번 주 한마디** — 한 덩이 문단이라 가를 수가 없다 → **읽기 폭(760px)으로 모은다.**
   안 그러면 980px 한 줄이 되어 눈이 줄을 놓친다.

## ⚠ 다음 사람이 알아야 할 것

- **폭으로 «웹인지»를 가르지 말 것.** 이제 메일도 웹도 980 이다. 가르는 것은 `옵션.웹` 이다.
  `전문담기` 만 `웹:true` 를 준다. 지금편지(메일)는 안 준다.
- **메일에 새면 안 되는 것**: `display:grid` · `grid-template-columns` · `column-count` ·
  `break-inside` · `display:flex`. 검사가 다섯을 다 본다.
- **아웃룩 전용 조건부 태그(`<!--[if mso]>`)는 못 쓴다** — 발송기가 주석을 통째로 지운다
  (`mail-send.js`). 그래서 «표»가 아웃룩에서 자리를 잡는 유일한 길이다.
- 지난 회차를 좁게(700) 다시 그리면 예전 그대로 둘씩이다 — 그 길은 살려 두었다.

## 아직 모르는 것 — 솔직히

- **폰에서 어떻게 보이는지는 못 쟀다.** 980px 고정 표라 폰은 스스로 줄여 보여 준다
  (지금 700 도 줄여 보여 준다 — 더 작아지는 것은 사실이다).
  ⚠ 폰으로 받아 보시고 글자가 너무 작으면 말씀해 주십시오. 그때는 폭을 880 쯤으로
  내리거나, 폰에서 카드가 한 줄씩 쌓이게 하는 길을 따로 재 봐야 한다
  (지금은 `<style>` 을 발송기가 지워서 화면 크기별 규칙을 못 쓴다).
- 아웃룩 데스크톱의 읽는 칸이 980 보다 좁으면 옆으로 밀어 봐야 한다.
