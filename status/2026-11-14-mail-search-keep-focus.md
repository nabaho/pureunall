# 2026-11-14 · 메일 검색칸 — 한 글자 치면 커서가 풀리던 것 (mail-search-keep-focus)

상태: 완료(검사 통과 · 실제 브라우저에서 PC 1366·폰 360 재현·확인) · 실제 로그인 화면·진짜 한글 입력기로는 못 봄
가지: claude/mail-search-fix
작업폴더: .claude/worktrees/mail-star-60bc62

대표 지시(2026-11-14, 캡처): 「검색기능 셀(칸)이 이상하다 제대로 작동 잘 안한다 확인하고 고쳐달라」 — 캡처는 검색칸에 「s」 한 글자만 들어가 있다.

## 원인 (실제 브라우저에서 재현)
- 검색칸에 한 글자 칠 때마다 `oninput` → `renderMailPage()` 가 메일 화면 «전체»를 다시 그린다(`el.innerHTML = …`). **검색칸 자신도 새로 만들어져 커서가 풀린다.**
- 미리보기 서버(지어낸 자료)에서 실제 키 입력으로 「a」를 친 뒤: 글자는 들어가 있지만 `document.activeElement` 는 `BODY` — 다음 글자는 어디에도 안 들어간다. 사용자는 칸을 «다시 눌러야» 한 글자 더 칠 수 있다.
- 같은 모양의 검색칸이 다섯이다(메일함 PC `#mbQ`·폰 `#dmmQ`, 수신기록 `#ibQ`, 사업장별 `#ctQ`, 보낸 메일). 자료함 `#matQ` 만 따로 다시 포커스를 주는 코드가 있었다.
- 한글은 더 나쁘다 — 글자를 «조합하는 중»에 칸이 바뀌면 입력기가 깨진다(코드는 조합 중에 안 그리고 조합이 끝나면 그리지만, 그때도 칸이 새로 만들어졌다). **진짜 한글 입력기로는 확인하지 못했다.**

## 고친 것 (`pu-cards.html`, 서버 변경 없음)
- `mailPaint(el, html)` — **커서가 `data-keep` 표가 붙은 칸에 있으면 그 칸(같은 객체)과 조상 줄기는 그대로 두고, 줄기의 «옆 가지»(목록·단추·쪽수)만 새 그림으로 갈아 끼운다.** 칸이 그대로라 커서·글자 조합·Ctrl+Z 가 산다.
  - 커서가 그 칸에 없거나, 새 그림에 같은 칸이 없거나, 줄기 모양(깊이·꼬리표)이 다르면 «예전처럼 통째로» 그린다.
  - 칸의 글자(value)는 안 건드린다. 코드가 값을 바꿨을 때(지우기 등)만 새 값을 따른다.
- `renderMailPage`(PC)·`renderMailMobile`(폰)이 `mailPaint` 를 지난다. 폰은 띠와 몸통을 따로 그리던 것을 «한 번에» 그리도록 바꿨다(몸통 안 검색칸을 지키려고).
- 다섯 검색칸에 `data-keep` 표.
- 입력 처리(조합 중엔 안 그리고, 조합이 끝나면 그림)는 그대로.

## 확인 (지어낸 자료 · 내장 브라우저 · 실제 키 입력)
- 고치기 전: 「a」 친 뒤 `focused:false`, 활성 요소 `BODY`.
- 고친 뒤 PC: 「abc」 이어 침 → 값 `abc`, `focused:true`. 「점검가」 → 6통으로 걸러지고 「🔎 본문까지 찾기」 단추가 나타나도 칸 유지.
- 보낸 메일 검색 · 폰(360px) 메일함 검색 · 폰의 보낸 메일·쓰기·수신기록·사업장별 화면 모두 정상(옆넘침 없음).

## 검사
- 새 `tests/mail-keep-focus.test.js`(19개) — 외부 도구(jsdom: 이 PC 엔 없고 CI 에서만 깔림)에 기대지 않는 «직접 만든 가짜 DOM» 위에서: 칸이 **같은 객체로 남음** · 옆 가지 교체와 차례 · 글자 안 건드림/코드가 바꾼 값은 따름 · 커서가 칸에 없음/표 없음/표 이름 다름/깊이·꼬리표 다름/다른 조각의 칸/같은 표 둘이면 통째로 · 속성 맞춤 · 검색어가 바뀔 때만 스크롤 맨 위 · 연달아 11번 갈아 끼워도 같은 칸 · 다섯 칸의 표와 한글 조합 처리·그리는 길 소스 지킴.
- 망가뜨려 보기 24가지 모두 걸림(처음 3개 살아남아 검사를 더했다: 깊이만 다른 줄기 · 다른 조각의 칸 · 칸마다 한글 조합 처리 — 같은 문장이 두 군데라 한 곳만 바뀌어도 통과했었다).

## 검토
- **자동 검증(Orca)**: 처음엔 Orca 에 연결되지 않아(「Orca 를 열어 두었는지 확인」 오류) 건너뛸 뻔했으나, 검사 결과를 기다리는 사이 다시 연결되어 «실제로 돌렸다».
  - 기능 검증(Antigravity·Gemini) **통과**(높음·중간 0, 낮음 2). 보안 검토(Codex) **발견 사항 없음**. 역할이 다른 AI 로 바뀐 것은 없다(코딩 Claude · 검증 antigravity:gemini-4-argon-high · 보안 codex).
  - 낮음 2건은 반영 안 함(이번 변경이 아니라 원래 있던 것): 검색칸 `outline:none`(키보드 포커스 테두리 없음) · 다섯 검색칸에 `aria-label` 없음(placeholder 만 있음). 원하면 따로 고칠 수 있다.
  - 두 검토 모두 «실제 브라우저 렌더링·진짜 한글 입력기»는 확인 못 함이라고 밝혔다(저는 브라우저로 PC·폰 확인은 했다).
- 이와 별도로 «내 생각에 기대지 않는» 독립 검토를 Claude 하위 에이전트(읽기 전용)에도 맡겼다. 결과: **높음·중간 없음**, 낮음 3 · 참고 2.
  진짜 DOM(헤드리스 Edge)에서 사본 함수를 돌려 «통째로 넣은 것과 글자 하나까지 같은 결과·칸은 같은 객체·포커스 유지»를 확인했다고 보고함. 한글 입력기로는 못 봤다고 함.
- 반영: ⓐ 같은 표의 칸이 한 화면에 둘이면 어느 칸인지 못 정해 커서가 옮겨 갈 수 있음 → 새 그림·지금 화면에 같은 표가 «정확히 하나씩»일 때만 칸을 남기고, 아니면 통째로(지금은 그런 화면이 없어 예방). ⓑ 나눠 보기 목록 스크롤이 내려간 채 남음(예전엔 맨 위로 갔다) → 검색어가 «바뀐» 다시 그리기에서만 줄기의 스크롤을 맨 위로. 새 메일 도착 같은 다시 그리기는 스크롤을 건드리지 않음.
- 반영 안 함: 폰 서랍 클래스 전환 애니메이션 가능성(추측·드묾) · 안 쓰이는 폰 `box` 가지(원래 있던 코드).

## 한계 (숨기지 말 것)
- 진짜 한글 입력기(IME)로 친 것은 못 봤다 — 이 환경은 글자를 직접 넣는다. 칸을 안 바꾸므로 입력기 문제는 없을 것으로 «추정»한다.
- 자료함 검색(`#matQ`)·명함 목록 검색 등 다른 화면의 검색칸은 이번 범위가 아니다(자료함은 이미 다시 포커스를 준다).
- 검색이 «받아 둔 것» 안에서만 걸리는 한계(본문까지 찾기 단추가 서버에 직접 물음)는 원래 있던 동작이다.
