## 승인받은 화면 (사진첩 · 판독 결과 아래)

```
┌ 📋 이 신청서로 계약 등록 ───────────────────┐
│ 회사 11칸이 읽혔습니다.                      │
│ 담당자를 고르면 계약관리에 바로 등록됩니다 — │
│ 기간·금액은 신청서에 없어 빈 칸으로 만듭니다.│
│                                              │
│ 주담당 — 누가 맡습니까?                      │
│ [ — 주담당을 고르세요 —            ▾ ]      │
│ [      이 담당자로 계약 만들기 →      ]      │

```

담당자를 고르기 «전»에는 단추가 안 눌린다 — 계약관리가 주담당 없는 계약을 애초에 안 받는다.
명부를 아직 못 받았으면 빈 고르개 대신 「직원 명부를 아직 못 받았습니다」라고 적는다.

## 이미 절반은 있었다

9월 18일에 만든 것 — 신청서 캡처를 OCR 로 읽고, 누르면 회사 11칸이 채워진 채 계약 창이 열리고,
컨설팅 유형도 서류 이름으로 짐작해 미리 골라 둔다. **빠진 것은 담당자 고르기와 「사람이 누르는 일」**이었다.

## ★★ 저장 길에 사람이 답해야 하는 문이 다섯이다

「사람 확인 없이」를 만들려면 이 다섯에 기계가 대신 답해야 한다. **그 답을 정하는 것이 이 일의 전부다.**

| | 문 | 자동일 때의 답 |
|---|---|---|
| 1 | 계약유형 | 서류 이름으로 짐작(이미 있던 `erpConsTypeByDocName`) |
| 2 | 주담당 | **사진첩에서 미리 고른다** — 이번에 넣은 칸 |
| 3 | 업체가 업체관리에 없다 | **연결 보류** — 업체 ID 를 «안 채우는» 쪽이라 안전하다 |
| 4 | 같은 사업자번호가 다른 업체에 | **안 만든다** (코드가 스스로 「취소 권장」이라 적은 자리) |
| 5 | 같은 회사에 유형이 겹치는 계약 | **안 만든다** |

**「무조건 만든다」가 아니다 — 깨끗한 것만 만들고 걸리는 것은 안 만들고 알린다.**
4·5 에서 기계가 「예」로 답하면 같은 계약이 둘 생기거나 엉뚱한 업체에 붙는다.
자동이라 **그 자리에서 아무도 안 보고 있다** — 사람이 가장 늦게 알아채는 종류의 사고다.

## 얼개 — 사진첩은 «요청»만 남긴다

```
사진첩  담당자 고르고 누름 → PuDocFile.requestContract()
                             → data/contract_requests/{id}  「요청 한 줄」
   ↓ (곧바로 계약관리로 건너간다)
계약관리 열릴 때  runContractRequests()
   · 깨끗하면 → persistOne() 으로 계약을 만든다 (사람은 아무것도 안 누른다)
   · 걸리면   → 안 만들고 state:'blocked' + 왜 걸렸는지를 적어 남긴다
```

**왜 계약관리가 만드나** — 검사 다섯이 전부 거기 있다(업체 목록·계약 목록을 읽어야 한다).
사진첩이 흉내 내면 같은 규칙이 두 곳으로 갈려 **한쪽만 고쳐지는 날이 온다.**

## ★★★ 내가 어겼다가 검사에 걸린 것

처음에 이 일을 **사진첩 화면에 직접** 짰다. `db.ref('data/contract_requests/…').set()`.
검사 셋이 그 자리에서 걸렸다:

- 「포털 공용 루트(data)를 경로로 쓰지 않는다」
- 「화면은 실시간DB에 직접 쓰지 않는다 — 쓰기는 저장 층·대기열만」
- 「사진첩 전용 자리에 담는다」

**2026-07 실데이터 사고 뒤에 세운 울타리였다.** 남의 앱 자리 이름을 아는 일은
`js/pu-doc-file.js`(PuDocFile) 의 몫이다 — 그 파일 머리에 이미
「화면이 남의 앱 속을 알기 시작하면 그쪽이 바뀔 때 조용히 깨진다」고 적혀 있었다.
옮기고 나니 화면은 `PuDocFile.requestContract()` · `PuDocFile.erpStaff()` 만 부른다.

★ **검사가 설계를 바로잡아 주었다.** 그래서 그 갈래를 새 검사로도 못 박아 두었다.

## 한 규칙, 두 부르는 곳

모달과 자동 등록이 **같은 함수**를 본다 — 따로 세면 「화면은 묻는데 자동은 안 막는」 어긋남이 생긴다.

- `erpBiznoClash(form, cos)` — 사업자번호가 다른 업체에 있나
- `erpContractDupBlock(form, contracts)` — 유형이 겹치는 진행 중 계약이 있나
- `erpBlankContractForm()` — 새 계약의 빈 서식(모달·자동 등록이 같은 모양을 쓴다)

## 지킨 것

- ⚠⚠ **업체·계약 목록이 다 내려오기 전에는 안 돈다.** 빈 목록으로 판단하면 전부
  「연결 보류」가 되고 중복을 못 찾아 같은 계약을 또 만든다.
- ⚠ **두 번 겹쳐 돌지 않는다**(`_erpCtReqBusy`) — 요청을 지우기 «전»에 둘째가 읽으면 계약이 둘 생긴다.
- ⚠ **사람이 누른 것과 같은 문으로 저장한다**(`persistOne`) — 월 잠금·업체 연결·관계 검증을 지난다.
- ⚠ **기간·금액을 지어내지 않는다.** 신청서에 없는 숫자다. 빈 칸으로 만들고 상태는 「상담」이다.
- ⚠ **유형을 못 골랐으면 못 골랐다고 적는다** — 말없이 첫 유형을 찍으면 사람이 고른 줄 안다.
- ⚠ **만든 요청은 지우고 걸린 요청은 남긴다** — 지우면 사람이 볼 것이 사라진다.
- ⚠ 창을 닫으면 고른 담당자를 잊는다 — 안 그러면 다음 서류가 앞 서류의 담당자 앞으로 등록된다.

## ⚠ 한계 — 숨기지 않는다

**계약관리를 아무도 안 열면 계약이 안 만들어진다.** 진짜 「찍는 순간 즉시」가 되려면
서버(Cloud Function)가 해야 하는데, 그러면 검사 다섯을 **서버에 한 벌 더** 만들어야 한다
(규칙이 두 곳으로 갈린다). 사진첩이 누른 뒤 곧바로 계약관리로 건너가므로 사람에게는
「바로 등록되는」 것으로 보인다 — 먼저 이렇게 두고, 불편이 실제로 생기면 그때 서버로 옮긴다.

## 자리와 권한

- 새 자리 `data/contract_requests` — **계약과 같은 권한**(`.read`/`.write`: 재직 직원).
  담기는 것이 계약에 들어갈 회사 정보 그대로라, 여기만 더 열면 계약보다 넓게 새는 구멍이 된다.
- 규칙을 올렸다: `node scripts/rules-deploy.js --deploy` → **새로 생긴 규칙 1개 · 사라진 것 0개**,
  되받아 확인까지 마쳤다. 새 기준은 `docs/firebase-rules-콘솔원문-2026-09-19.json`.
- 온톨로지에 `contract_requests:'Task'` 로 등록했다 — **계약이 아니다**(계약관리의 검사를
  지나야 계약이 된다). `Contract` 로 적으면 관계 색인이 「아직 없는 계약」을 센다.

## ★★★ 실제 자료로 검증하고 구멍 둘을 막았다 (대표 지시 「니가 검증해라 기존에 있던 자료 넣어서」)

만들어 놓고 **실제 신청서 49장**(`kind='form'`)을 그대로 넣어 돌렸다. 그랬더니 구멍이 둘 있었다.
**둘 다 「자동이라 아무도 안 보고 있다」는 점 때문에 생긴 것이다.**

### 구멍 ① — 유형을 못 고르면 「현장클리닉」으로 찍혔다 (47장 중 25장)

`ctReqForm` 이 짐작에 실패하면 `types[0].code`(첫 유형 = 현장클리닉)로 두었다.
모달의 `fixTypeCodes` 를 따라 한 것인데, **모달은 사람이 드롭다운을 «보고» 있고
자동 등록은 아무도 안 보고 있다.** 그래서 「2026년 충남북부상공회의소 인사노무 컨설팅
신청서」가 **현장클리닉**으로 들어갔다. note 에 「못 골랐다」고 적어 두었지만
계약에는 틀린 유형이 버젓이 박힌다.

★ **짐작기는 손대지 않았다** — 못 고른 까닭이 옳았다.
「인사노무컨설팅충남북부상의」와 「인사노무컨설팅서산」이 **둘 다 맞아** 하나를 못 찍은 것이다.
기계가 못 가리는 자리라, **서류를 보고 있는 사람이 고르는 것이 맞다.**

→ **사진첩에 유형 고르개를 두었다.** 짐작되면 미리 골라 두고(사람은 확인만),
안 되면 사람이 고른다. 둘 다 고르기 전에는 단추가 안 눌린다.
`ctReqForm` 은 이제 **찍지 않는다** — 요청이 들고 온 유형만 쓴다.

### 구멍 ② — 계약이 아닌 서류가 계약이 되었다

판독이 `서식(form)` 으로 묶는 범위가 계약보다 넓다. **위촉장**(회사 이름 1칸) ·
**등기사항전부증명서** · **「신청내용」** 이 계약으로 만들어지고 있었다.

→ **사업자번호로 가른다.** 실측이 깨끗하게 갈라 주었다:

| | 건 | 사업자번호 있음 |
|---|---:|---:|
| 진짜 신청서(인사노무·기술보호·현장클리닉 …) | 44 | **44** |
| 계약이 아닌 것(등기부·위촉장·신청내용) | 4 | **0** |

칸 수로 가르려 했으나 등기부도 4칸은 채운다 — **이 한 칸이 훨씬 깨끗하다.**
중복 검사도 이 번호로 해야 제대로 된다(이름만으로는 「총서/충서」처럼 OCR 이 한 글자
다르게 읽은 같은 회사를 못 잡는다).

### 고친 뒤 같은 49장으로 다시 재 본 값

| | 고치기 전 | 고친 뒤 |
|---|---|---|
| 단추가 아예 안 뜬다 | 2건 | **5건** (계약 아닌 서류 전부) |
| 계약이 만들어진다 | 6건 — 위촉장·등기부 포함, 유형 25/47 틀림 | **4건 — 전부 진짜 신청서, 유형 틀린 것 0** |
| 걸려서 안 만든다 | 41건 | 40건 (중복 36 · 사업자번호 충돌 4) |
| 사람이 유형을 골라야 | — | 22 / 44건 |

걸린 40건은 **이미 계약이 있는 회사들의 옛 신청서**라 자연스럽다.
사업자번호 충돌 4건은 정우산기(주) — **오늘 아침 담당자 연락처를 정리한 그 회사**이고,
검사가 제대로 잡은 것이다.

⚠ 검증하다 내 모의에서도 실수를 둘 했다 — 남겨 둔다.
① 푸른이알피 자료가 `{u, v}` 꼴인 것을 모르고 읽어 「업체 2건」이 나왔다.
② 만든 계약이 다음 판단에 반영되는 것을 빼먹어 실제보다 나쁘게 셌다(6건 → 실제 4건).
**모의가 틀리면 고칠 것을 잘못 고른다.** 둘 다 잡고 다시 쟀다.
