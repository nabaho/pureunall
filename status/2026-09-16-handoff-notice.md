# 전달함 — 고친 뒤 «그것을 넣은 사람»에게 무엇을 해야 하는지 간다

대표 지시 2026-09-16 「내가 고치고 난 이후에 데이터 입력자가 수정·변경 등이 필요한 경우 로그인 때 이 부분 어떻게 해야 되는지 자동으로 알림 만들어줘」
가지 `feat/handoff-notice` · 고친 곳 `pu-erp.html` (저장 층 + 머리줄) · 목업 `docs/mockups/handoff-notice.html`

## 어떻게 도는가

1. **관리자가 «남이 넣은» 기록을 고쳐 저장한다** → 저장 층이 알아챈다(`_handoffSpot`).
   기록마다 「누가 마지막으로 만졌는지」(`updatedBy`)가 이미 찍혀 있어, **대표가 고를 것이 없다.**
2. **화면 아래에 띠가 20초 뜬다** — 「이 건은 김보람 님이 넣었습니다 — 한마디 남기시겠습니까?」
   일을 안 막는다. 안 누르면 스스로 사라진다.
3. **누르면 한마디 창** — 자주 쓰는 말은 단추(다시 확인해 주세요 / 다시 입력해 주세요 / 앞으로 이렇게).
4. **그 사람이 다음에 로그인하면 창이 뜬다.** 「확인했습니다」를 누를 때까지 남고, 머리줄에 `📌 N` 배지로도 남는다.
   📍 줄을 누르면 **그 화면으로 간다**.
5. **보낸 쪽은 읽혔는지 본다.** 머리줄 `📤 N` — 내가 보낸 것 중 «아직 확인 안 한 것»이 있을 때만 보인다.
   하나도 없으면 단추가 아예 사라진다(늘 떠 있는 단추는 며칠 만에 배경이 된다).

## ⚠★ 어디에 담는가 — 이것이 이 작업의 핵심이었다

`data/handoff_notes/{받는사람 사번}/{키}`

- **최상위(`handoff_notes`)에 담으면 서버가 거부한다.** 살아 있는 규칙을 읽어 보니
  최상위 **63자리가 전부 이름으로 적혀 있고 이름 없는 자리(`$other`)가 없다.**
  `data` 아래에는 `$other` 가 있어 새 자리가 곧바로 산다.
- **받는 사람별로 자리를 나눈 까닭** — 그래야 각자 «자기 몫만» 구독한다.
  한 자리에 몰아 두고 `orderByChild('toSid')` 로 고르려면 색인(`.indexOn`)이 있어야 하고,
  **색인 없는 고르기는 전부 내려받아 브라우저에서 거른다** —
  온 직원이 남의 쪽지를 다 받게 된다. 자리를 나누면 색인이 아예 필요 없고,
  서버 규칙으로 「본인만」 막기도 쉽다.
- **`FB_EXCLUDE` 에 `handoff_notes` 를 넣었다.** 부팅 계획(`_bootKeyPlan`)은 `data` 아래 이름을
  통째로 훑어(shallow) 나온 것을 **전부 «표»로 보고 받아 간다** — 새 이름이 생기면 저절로
  포함되도록 일부러 그렇게 만들어 두었다. 전달함은 표가 아니라 사람별 쪽지함이라
  그 길로 들어오면 **온 직원이 매번 내려받는다.**

## 지킨 것

- **내가 넣고 내가 고친 것은 안 보낸다.** 이름으로 먼저 거른다 —
  사번 검사만 믿으면 내 이름이 붙은 «옛 계정» 앞으로 쪽지가 쌓인다(새 PC 에서 명단이 낡을 수 있다).
- **같은 이름이 둘이면 안 보낸다.** 엉뚱한 사람에게 가느니 안 가는 것이 낫다.
- **퇴직한 사람에게는 안 보낸다.**
- **한마디가 비면 안 보낸다.** 「대표가 고쳤습니다」만 가는 알림은 두 번째부터 아무도 안 읽는다.
- **관리자가 아니면 그물이 아예 안 돈다.** 표가 2천 줄인 곳이 있어, 아닐 때 견주면 저장이 느려진다.
  통째 저장 경로에서는 **처음 걸린 한 건에서 멈춘다.**
- **돈·주민번호를 쪽지에 안 담는다.** 이름표는 «이름표 칸»(업체명·제목·사건번호 …)에서만
  만들고, 금액 칸은 목록에 아예 없다.
- **확인 전에는 안 사라진다.** 로그인마다 다시 뜬다. 다만 «로그인당 한 번»만 저절로 열린다
  (`sessionStorage`) — 화면을 옮길 때마다 뜨면 일을 못 한다.
  ⚠ `localStorage` 로 바꾸면 한 번 보고 **영영 안 열린다.**
- **모르는 표는 「가기」 단추를 안 만든다.** 엉뚱한 화면으로 보내면 찾아다니는 것보다 나쁘다.

## 저장소의 안전장치가 내 실수를 잡았고, 그 덕에 규칙까지 올렸다

처음에는 규칙 만들개를 안 고치고 `data/handoff_notes` 를 쓰기만 했다.
`tests/rules-data-named.test.js` 가 **그 자리에서 걸었다** — 「data 아래 이름 없는 자리는
`$other` 로 떨어져 재직 직원 누구나 읽고 쓴다」. 그래서 만들개에 이름과 권한을 적었다:

```
data/handoff_notes/{사번}  ← 받는 사람 «본인»과 관리자만 읽고 쓴다
```

**그리고 콘솔에 올렸다**(`node scripts/rules-deploy.js --deploy`, 2026-09-16).
안전장치가 살아 있는 콘솔과 견줘 **새로 생기는 규칙 1개 · 값이 바뀌는 규칙 0 · 사라지는 규칙 0** 을
확인했고, 올린 뒤 다시 읽어 콘솔이 올린 것과 같음도 확인했다.
새 기준: `docs/firebase-rules-콘솔원문-2026-09-16.json`.

⚠★ **낡은 기억을 바로잡았다** — 「규칙 올리기가 #1225 에 막혀 있다」는 **2026-09-13 에 이미 풀렸다**
(`tests/photos-staff-share.test.js` 268~270줄이 그렇게 적어 두었다: 「#1225 가 main 에 들어온 뒤다」).
막혀 있다고 믿고 열린 채로 둘 뻔했다.

⚠ 규칙이 자리를 지켜도 **관리자는 모든 쪽지를 본다.** 그래서 금액·주민번호는 애초에 안 담는다 — 한 겹 더다.

## ⚠ 다음 사람이 밟을 자리

- **띠는 body 에 떠 있는 것이다.** Preact 가 그리는 머리줄 안에 날것 DOM 을 끼우면 다시 그려질 때
  밀려나고 다음 틱에 또 끼워진다 — 2026-09-16 아침의 깜빡임(#1374)이 바로 그것이었다.
  받는 쪽 창(`HandoffModal`)은 **Preact 가 직접 그리므로** 그것은 옳은 길이다.
- **`_handoffSpot` 은 `_recStamp` «앞»에서 불러야 한다.** 찍는 순간 `updatedBy` 가 나로 바뀌어
  누가 넣었는지가 사라진다. 저장 길 셋(`dbUpsert`·`dbPatch`·`dbSet`) 모두 그 순서다.
- **규칙을 고칠 때는 세 걸음을 함께** — 만들개 고치기 → 적용본·`docs/rules-paste.json` 다시 만들기 →
  `rules-deploy.js --deploy`. 짝 파일(`rules-paste.json`)을 빠뜨리면 `tests/rules-paste-copy.test.js` 가 건다.
- **`_handoffSpot` 호출은 `typeof` 로 감싼다.** 검사들이 `dbUpsert`·`dbPatch` 만 «잘라내» 따로 돌린다
  (`tests/month-close.test.js` 등). 안 감싸면 멀쩡한 검사가 `ReferenceError` 로 죽는다 — 실제로 죽었다.
- **색은 팔레트 안에서만.** `tests/color-palette.test.js` 가 27색 밖을 잡는다 — 실제로 걸렸다
  (`#0f172a`·`#f1f5f9`·`#a16207` → `#1e293b`·`#e2e8f0`·`#854d0e`).
