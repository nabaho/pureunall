# 계약관리 — 「걸린 요청을 보는 화면」 (2026-09-19)

## 왜 만들었나

사진첩→계약 자동 등록(PR #1466·#1475·#1480)이 막히면 지금까지는
토스트 한 줄로 끝났다. 화면을 새로고침하면 **무엇이 걸렸는지 사라진다** —
계약관리를 열 때마다 매번 `runContractRequests()` 가 다시 돌긴 하지만,
그 사이 자리를 비우면 걸린 채로 아무도 모른 채 쌓인다.

목업(`docs/mockups` 에 남기지 않고 파일로 보내 드림, 2026-09-19)을 보여 드리고
「니가 추천대로」 — **사진첩 원본 보기 단추는 넣지 않았다.** 다른 프로그램
(pu-photos.html) 창을 새로 여는 일이라 손이 더 가고, 신청서 이름만 적어 둬도
사람이 사진첩에서 찾을 수 있다.

## 무엇을 만들었나

- 계약관리 툴바에 **걸린 것이 있을 때만** 「⚠ 걸린 요청 N건」 배지.
  0건이면 배지 자체를 안 그린다 — 「있다/없다」가 색으로 갈리게.
- 눌렀을 때 뜨는 `BlockedRequestsModal` — 회사·걸린 까닭·유형·보낸 사람·신청서 이름을
  카드로 보여 준다. 단추 둘: **↻ 다시 시도** / **🗑 요청 지우기**.
- `data/contract_requests` 는 `FB_ALL_SYNC_KEYS`(={u,v} 배열) 방식이 아니라
  열쇠(id)로 된 그릇이라 `dbGet` 이 아니라 **제 것**(`fbDb.ref(...).on('value')`)으로
  따로 듣는다. 화면을 나가면 `.off('value')` 로 끊는다.

## ★★ 판단은 한 곳 — `processOneContractRequest`

무더기 처리(`runContractRequests`)와 「↻ 다시 시도」가 **같은 판단을 두 번 짜면**
한쪽만 고쳐지는 날이 온다(이 기능의 앞선 실수와 같은 모양). 그래서 요청 «한 건»을
만들어 보는 로직을 `processOneContractRequest(key, req)` 로 뽑아냈다 —
`erpDeferCoLinkIfNew` → `ctReqWhy` → (통과하면) `persistOne` 까지 **한 함수**가
지나고, 두 자리 모두 이것 하나만 부른다.

- **다시 시도**(`retryBlockedRequest`)는 겹쳐 누르는 것과 자료가 안 내려온 때를
  막는다(`_erpCtReqBusy`, `companies`/`contracts` 배열 확인) — 안 막으면 무더기
  처리와 동시에 같은 요청으로 계약을 두 번 만들 수 있다.
- **지우기**(`removeBlockedRequest`)는 `popConfirm` 으로 한 번 확인한다.
  사진은 그대로 두고 **요청 한 줄만** 지운다 — 사진첩에서 다시 누르면 새 요청이 생긴다.
- 이 화면은 **계약을 직접 만들지 않는다**(`dbUpsert`/`persistOne` 을 이 화면
  코드 안에 두지 않았다) — 다시 만드는 길은 「↻ 다시 시도」 하나로 모았다.

## 검사

`tests/photo-contract-auto.test.js` 에 6개 보탬(무더기·재시도가 같은 함수를
쓰는지, 겹쳐 누름·자료 미도착 방지, 확인 없이 안 지움, 실시간 리스너, 배지
있다/없다, 이 화면이 계약을 직접 안 만듦). 기존 3개는 로직이 옮겨간 자리
(`processOneContractRequest`)를 보도록 고쳤다 — 뜻은 그대로다.

- 되돌림(고장넣기) **6/6 걸림**.
- 전체 **18,299 통과 / 0 실패**(14 skip, 늘 그렇다).
- 실제 자료(업체 376·계약 160·직원 32)로 `processOneContractRequest` 를 직접
  돌려 봤다 — 걸리는 요청이 서버에 `{state:'blocked', why, handledAt}` 모양
  그대로 남는 것을 확인했다(화면이 그 모양을 그대로 읽는다).

## 남은 것

- 없음. 배포되면 계약관리를 열어 배지가 뜨는지, 실제로 걸린 요청이 하나
  생기면(예: 업체가 다시 안 맞는 경우) 눌러서 확인해 주시면 된다.
